# 模板：AI 研究/文档助手（v0.2.0-draft）

> 你是负责构建这个产品的 coding agent。这个文件告诉你怎么用这份模板，把产品**做到成熟**：不是做出一个能演示的 demo，而是做出一个通过全部验收、经得起真实团队使用的 SaaS。

## 先读什么

| 顺序 | 文件 | 读它是为了 |
|---|---|---|
| 1 | `spec/product.md` | 什么叫"成熟"，以及**容易做错的地方**（§6） |
| 2 | `spec/architecture.md` | 默认技术栈、数据模型、难点的设计要求、**假模型的行为**、启动约定、界面锚点 |
| 3 | `spec/api.yaml` | 接口契约：路径、字段、错误码 |
| 4 | `spec/decisions.md` | 哪些事要问人、默认值是什么 |
| 5 | `spec/landscape.md` | 这个品类已有的东西，以及哪些能用、哪些不能用 |
| 6 | `stages/S1…S4` | 当前阶段的范围和验收清单 |
| 7 | `spec/review-checklist.md` | 黑盒验收**看不到**、但会被独立审查员检查的东西。做完一个阶段后，先自己对照过一遍 |

## 怎么推进

1. **一次只做一个阶段**，按 S1 → S2 → S3 → S4 的顺序。不要提前做后面阶段的功能，除非当前阶段的验收需要它。
2. 每个阶段内部循环：实现 → 跑验收 → 读失败信息 → 修复，直到这个阶段的验收全部通过：
   ```bash
   cd <模板目录>/acceptance && npm ci   # 第一次
   node run.mjs --app <产品目录> --stage S1
   ```
   结果写在 `acceptance-results/<阶段-时间>/report.json`，应用日志在同一目录的 `app.log` 里。
3. 阶段全部通过后，**停下来**，向人汇报：通过了什么、偏离了哪些默认做法（`DECISIONS.md`）、有哪些问题等待回答（`QUESTIONS.md`）。人确认后，再进入下一阶段。

## 不可违反的规则

- **不要修改 `acceptance/` 下的任何文件。** 验收时会从模板重新拷贝一份测试，你的修改不会生效，只会让你自以为通过了。如果你认为某条测试本身错了，把理由写进 `QUESTIONS.md`，交给人决定。
- **不要针对测试写特例**，比如检测到测试账号就走另一套逻辑。验收测的是产品的真实行为。
- `TEST_MODE=1` 只用来启用假模型、outbox 和故障注入，不能改变业务规则，比如放宽权限或跳过预算检查。
- 测试模式下不能访问外网，也不能使用任何真实的 API key。
- **需求里有、模板里没有的内容，不要悄悄漏掉，也不要悄悄加上。** 用户的原话需求里提到、但这份模板的范围里没有的功能（比如网页链接导入），列在 `QUESTIONS.md` 的"需求里有而模板没有"一节，说明你没有做、做了会带来什么风险。如果确实要加（比如人已经同意），必须按 `spec/review-checklist.md` 的"请求体与资源"那几条设计，并写进 `DECISIONS.md`。
- 遇到 `spec/decisions.md` A 节列出的问题，先按默认值继续做，同时把问题写进 `QUESTIONS.md`。不要替人决定花钱、开账号、改动本机系统这类事。

## 产品仓库里必须有的文件

| 文件 | 内容 |
|---|---|
| `scripts/acceptance-start.sh` | 启动约定（`spec/architecture.md` §7） |
| `README.md` | 怎么在本地启动，以及需要哪些环境变量 |
| `DECISIONS.md` | 偏离默认做法的地方：改成了什么，为什么 |
| `QUESTIONS.md` | 等人回答的问题（每条附上你采用的默认值），以及"需求里有而模板没有"的内容 |
| `PROVENANCE.md` | 复制过的第三方代码片段：来源、许可证、commit（只用依赖包、没有复制代码时，写"无"） |

## 什么时候算完成

S4 的验收全部通过（`--stage S4` 会把 S1–S4 一起跑），并且人确认过 `QUESTIONS.md` 里的问题。验收通过只说明产品满足这份模板定义的"成熟"标准，**不等于**已经可以上线收费：真实模型、真实邮件、部署和商业化，都是之后的人工决策（`spec/decisions.md`）。
