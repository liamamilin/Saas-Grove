# 验收套件

这套黑盒测试定义了"成熟"的标准。它只通过 HTTP 接口和浏览器去操作产品，不看产品的代码。

## 运行

```bash
npm ci
node run.mjs --app <产品目录> --stage S2      # 跑 S1+S2
node run.mjs --self-check                     # 辅助检查：对空应用必须全部失败
```

runner 会：
1. 通过 `psql` 新建一个空数据库（默认连接 `postgresql://localhost:5432/postgres`，可以用 `--pg-admin` 或 `PG_ADMIN_URL` 修改）；
2. 如果产品的 `package.json` 里有 `build` 脚本，先执行 `npm run build`，保证测的是当前源码；
3. 用 `scripts/acceptance-start.sh` 启动产品，并等待 `/api/health` 返回 200。如果传了 `--app-sandbox <配置>`，构建和启动都在 macOS 沙箱里进行（harness 会这样用，让被测代码碰不到测试本身）；
4. 跑到指定阶段为止的全部测试，测试过程中可以通过控制接口重启产品（重启时不重新构建），也可以再启动**另外的实例**：每个实例有自己的端口、全新的数据库和日志，环境变量完全由测试指定（不继承 runner 的 `TEST_MODE`、`MODEL_*`、`EMBEDDING_*`、`FAKE_*`、`MAIL_*`，值为 `null` 表示去掉这个变量）。真实模式的测试靠它在非测试模式下启动产品，并配合 `lib/mock-model.ts` 里的假模型服务；
5. 停止产品、删除数据库，把 `report.json` 和 `app.log` 写到 `acceptance-results/` 下。

退出码：0 表示全部通过；1 表示有测试失败；2 表示产品没能启动；3 表示用法或环境有问题。

## 改测试的规矩

- **任何测试改动都要经过独立 agent 审查**（这是主要的把关手段）。审查由另一个会话或另一个模型来做，只读，不参与编写测试。它对照 spec 找出：spec 与测试之间的矛盾；测试依赖了 spec 没写的行为；脆弱或空洞的测试；`spec/product.md` §6 里没有被测到的要求。审查发现的问题修完之后才能用。
- 每条负向测试都要**先证明正向路径成立**（例如 owner 能读到），再证明负向（其他人读不到）。否则一个对什么请求都返回 404 的应用也能通过。
- 辅助检查：`node run.mjs --self-check` 应该报告 0 条空洞测试、0 条因测试自身错误而失败的测试。它跑得快，但只能抓出很浅的问题。
- 用到另外实例的测试（`lib/instance.ts`）不要同时碰主实例：等待实例启动的时候，主实例的空闲连接会被服务器关掉，下一个请求会失败。
- 测试里不要写死时间之类的环境假设；需要时用假模型的延迟和故障注入来控制节奏。
- 任何修改都要经过人确认，因为它改变的是"成熟"的定义。

## 已知局限

- 对空应用做的自检只能证明测试不是空洞的：大多数测试在第一步就失败了，后面步骤的逻辑要等真实产品出来才能检验。
- 涉及时间的测试（流式间隔、退避、并发预算、限流）已经留了余量，但在负载很高的机器上仍然可能偶尔失败。
- S4 的界面测试会在 `127.0.0.1` 的随机端口上起一个"客户网站"（`lib/widget.ts` 的 `hostPage`），用产品给的嵌入代码挂出小窗，所以小窗请求的 Origin 和产品不同。
- 界面测试只覆盖主流程；页面好不好用，还要靠人在阶段确认时看一眼。
