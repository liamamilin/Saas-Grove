
## 深度补齐附加核对（2026-10-31）

本单元是“列举同类主流产品”，不是“证明类型存在案例”。除上面的通用要求外，逐项核对：

1. **定义性核心**：每个入选产品都要满足本类型的定义性核心（看 `input.json` 的 definition）。例如服务台必须是“请求者的请求进入共享客服队列、成为持久工单、客服在工单上回复请求者、状态推进到解决”；通用问题跟踪、内部任务管理或纯聊天工具不算。
2. **去重**：本单元条目不得包含 `input.json` 的 `existing_products`；新建产品的 ID、仓库 URL、官网不得与正式库已有产品重复（工作区的 `CATALOG_INDEX.json` 列出了正式库全部产品的 ID、名称、track、官网和仓库，按需检索，不必通读）。
3. **已有产品补关系**：`candidate_dispositions` 中 `relation_added` 的条目必须复用原 ID，名称和 track 与 `CATALOG_INDEX.json` 一致，只是新增本类型关系并补来源。
4. **开源门槛**：仓库未归档、12 个月内有推送、许可证有 license API 和正文依据；SDK、库、模板、纯客户端不算。
5. **被拒候选**：`candidate_dispositions` 中 `rejected` 的原因要具体、有事实依据；如果拒绝原因明显与已读来源矛盾，列为 finding。
6. **数量**：没达到目标数量本身不是问题，只要 note 如实写明；但不能为了凑数收录不合格产品。
