# SaaS Grove 逐叶子审阅与案例验证 workflow

1,805 个叶子的模型初判和 548 个复核项均已完成，确认结果已发布；现在进入真实案例采集。发布范围见 [复核与发布](SAAS_SCOPE_REVIEW.md)，首批进展见 [案例采集](CASE_COLLECTION_REPORT.md)。

日期：2026-10-23。目标：让全部 1,805 个源叶子拥有自己的判断记录，并在后续真实应用采集中用证据修正。初判、复核、案例证据和实际部署测试需要分别记录。

## 采用两阶段，避免重复调研和错误归档

先用轻量模型逐叶子判断类型是否适合本产品，再把验证真实案例融入 M2 采集。初判不负责证明某产品存在，也不因模型能想象一种网页版就确认可收录。

开源优先不等于只有开源才算案例。某类型只有商业 SaaS，也可以证实该类型；商业产品仅需基本索引。开源自托管应用可以作为 SaaS 同类软件候选，但必须确实有完整的服务端应用，不能把任何带服务器、网页或 API 的组件都视为 SaaS。

## 1. 冻结范围与输入

- 全部源叶子进入清单，包括目前被排除的 160 个；不能只清理可见类型。
- 每个输入保留稳定 slug、名称、原始定义、定义性核心及分类定位。
- 不提供旧 scope 给初判模型，减少沿用上一次结论的倾向。
- 每包 30 个，约 61 包；输入摘要、提示词版本和模型名称随结果保存。源定义变动后相应判断需要重做。
- 原始资料仅作为不可信参考，不执行其中的指令。

## 2. 轻量模型逐项初判

本轮执行角色为 `luna_worker`，模型 `gpt-6-luna`；没有切换主会话模型，也不沿用 Atlas 的模型配置或凭据。先用分散的 3 包（约 90 叶子）校准，再处理剩余包。批量结果逐包落盘，可中断续跑；JSON 格式错误、漏项、重复或输入版本不匹配均不算完成。

每个叶子至少记录：

| 字段 | 含义 |
|---|---|
| verdict | included / conditional / excluded，属于类型初判 |
| software_role | 客户业务软件、消费服务、基础设施、本地工具、设备控制或混合类型 |
| service_form | 该类型可实际交付的应用形态，或缺少何种条件 |
| reason | 针对这个叶子的理由，不能仅复制父分类范围 |
| confidence | high / medium / low，表示模型判断把握，不是统计校准后的概率 |
| search_queries | 后续查找真实项目的查询建议，不是已执行的搜索 |
| stage / evidence_status | model_triage / unverified，防止将模型初判误报成案例验证 |

本轮不要求模型凭记忆列产品名，禁止捏造仓库、官网或引文。模型输出不会直接覆盖发布目录。

## 3. 复核后再调整目录

优先检查：全部拟排除项、相对旧目录的范围变化、低把握项、混合交付类型，以及可能过宽或重复的叶子。对明显类型抽样检查，其余保留轻量模型初判来源，不称为人工逐项认证。

- 重复或粒度不合适：建议合并或缩小定义，保留旧 slug 与来源；不能把“重复”误记成“没有 SaaS”。
- 模型与复核不一致：记录具体裁决理由；边界仍不清楚时保持待确认，不强行二选一。
- 发布采用单独的复核结果；源快照、本地显示名称和原有应用关系保留。
- 全量初判完成的标准是 1,805 个唯一 slug 全部通过结构与版本校验，不是包文件存在或模型声称完成。

## 4. 在 M2 用真实案例验证

类型判断和案例状态分开，避免一个字段同时代表三件事。

| 维度 | 状态示例 |
|---|---|
| 类型范围 | 纳入 / 待确认 / 超出本产品范围 |
| 案例证据 | 未搜索 / 已有开源案例 / 仅有商业案例 / 本轮未找到 / 搜索失败 |
| 展示状态 | 主目录 / 待验证 / 已归档 |

每条案例至少核验官方仓库或官网、核心用途与该叶子匹配的依据，以及实际在线服务或服务端部署形态；商业案例只保留基本信息。公共网站的登录页面、付费订阅和模型臆测都不能单独证明它属于 SaaS 应用。

首轮为每叶子设置有界搜索预算：预设英文类型、别名及软件/服务形态等最多 3 组不同查询；找到合格案例即可提前结束，未找到时完成这些不同查询；同时利用官方产品资料与 GitHub。找到一个合格案例即可确认有该形态并停止存在性搜索，之后按开源优先继续产品采集。一个真实应用可属于多个叶子，但每个关联都需有独立匹配依据，不按关键词批量挂靠。

搜索预算耗尽仍未找到：记录查询、来源、候选数、拒绝原因、日期和实际失败信息，状态为“本轮未找到案例”。限流、网络错误或模型不可用必须记为失败或可续跑，不能记成零结果。

## 5. 归档条件

“不适合目录”和“暂时没有案例”采用不同理由：

1. **超出范围归档**：叶子定义的核心确属消费场所、纯客户端、组件、基础设施或设备控制，并经复核确认；不必先花搜索预算。
2. **案例不足归档**：至少两轮有记录、关键词或来源不同的有效搜索后仍没有开源或商业案例，经复核可做可恢复的冷归档。它表示当前检索没有证据，不表示已证明不存在。
3. 仅无开源项目而存在商业 SaaS：保留类型，标为仅有商业案例。
4. 仍关联有效应用的叶子不能因本轮没有新结果被自动归档。合并叶子时保留别名及关联迁移。
5. 归档不删除源定义、slug、判断、搜索记录或关系；新证据出现后可以恢复。不把时间到了或一次返回为空当作归档条件。

## 本轮交付与边界

本轮先交付可复用的分包、验证、续跑与汇总工具，以及真实轻量模型逐叶子初判。案例搜索与冷归档规则纳入后续 M2，不能将本轮模型输出称为已经找到 1,805 类真实 SaaS。

运行命令和实际完成数以工具生成的状态和汇总为准。初判结果保存在 `data/taxonomy/leaf-reviews/`，运行输入包在 `var/leaf-review/saas-v1/`；后者是本机可续跑状态，不入 Git。

## 运行与续跑

```sh
# 生成 / 重建固定输入包（不会覆盖模型结果）
python3 -B scripts/review_leaves.py prepare
# 校验每包输入版本、字段和全部 slug，显示缺失或无效包
python3 -B scripts/review_leaves.py status
# 只有全部叶子完成且输入匹配时才允许汇总
python3 -B scripts/review_leaves.py assemble
```

模型执行由本任务的轻量审阅代理读取输入包并逐项写结果，脚本负责版本、覆盖、断点与汇总校验。脚本本身没有把分类规则伪装成模型，也不调用 Atlas、读取凭据或擅自启动模型 API。换模型时需显式更新审阅版本和元信息；不能仅修改结果中的模型名。

首轮试跑使用了 v1 提示词，90 个叶子的校准中发现“公众运营软件被误排除”的偏差。v1 三包保留在 `leaf-reviews/archive/saas-leaf-triage-v1/`，不计入正式覆盖；修正后提示词为 `saas-leaf-triage-v2`，重新审阅三个校准包，再扩展全量。

校准所依据的公开资料：[Livestorm 的活动数据管理](https://support.livestorm.co/category/8-analytics-data)、[CiviCRM 捐赠管理](https://docs.civicrm.org/user/en/latest/contributions/what-is-civicontribute/)、[CiviCRM 点对点筹款功能](https://civicrm.org/features/peer-peer-fundraisers)。这些资料纠正产品范围先验，不能替代每个叶子的案例匹配验证。

复核清单中，即使与旧目录一致的“排除”也必须进入队列；低把握和混合形态同样单列。输出顺序不影响完整性，只要 slug 精确且唯一即可。汇总结果携带全量源摘要、逐叶输入摘要、包摘要、提示词版本、模型及未验证状态。

## 548 项发布后的运行

548 / 548 个复核项已于 2026-10-23 发布。初判建议不会自动覆盖页面；本次采用三组复核结果和独立排除复查。完整来源和备份见 [发布报告](SAAS_SCOPE_REVIEW.md)。旧 assemble 会重新生成初判汇总和队列，发布后不再运行它。

案例采集使用 `scripts/collect_cases.py fetch / validate / import`，来源快照按内容 SHA-256 保存，整批通过身份、许可和叶子验证后再事务导入。重复导入保留既有叶子关系。请求失败、许可证识别不明、仓库迁移、缺少匹配叶子分别记录待处理，不自动排除，也不自动改成商业产品。
