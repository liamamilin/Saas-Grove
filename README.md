# SaaS Grove

**SaaS Grove** 是独立的 SaaS 应用发现与调研平台，名称于 2026-10-23 确认。产品副标题：发现开源 SaaS，了解商业选择。

本文件是项目当前唯一的方向文档。当前方向及收录边界由项目负责人于 **2026-10-23** 确认；以后变化以讨论结论为准，并同步更新这里。

## 当前产品方向

参考 Atlas 当前的真实项目目录，做一个**专门面向 SaaS 应用的发现与调研平台**。围绕真实应用组织资料，帮助使用者了解某个应用类型有哪些现成项目、各自能做什么及适用范围。

信息组织主线：**SaaS 分类（可多级） → 叶子类型 ↔ 真实应用／项目**。叶子代表 CRM、开票软件等应用类型；一个应用可归属多个叶子。**不需要场景层，不生成或存储场景实体。**

认知模板生产已退出当前产品主线。下方历史模板、构建及对比实验资料保留用于追溯，其模板有效性和经济性指标不作为新版产品的交付标准。

开发原则（2026-10-23）：**保证质量，完成比完美重要。** 数据真实、目录结构正确、核心流程可用是必要检查；非关键边界以明确标注和后续修订处理，不等待所有细节完美才交付。

## 收录范围与调研深度

**开源与商业都可以收录，分开展示；开源优先，商业只作基本索引。**

| 类型 | 优先级与深度 | 信息范围 |
|---|---|---|
| 开源 SaaS 项目 | 优先收录、深入调研 | 名称、仓库与官网、用途、所属叶子、核心功能、技术栈、部署方式、许可证、维护情况及资料来源 |
| 商业 SaaS 产品 | 补充收录、浅层记录 | 名称、官网、简短介绍、主要用途、所属叶子、资料来源；以“知道有这个产品”为目标 |

收录边界：围绕用户资料、协作或业务工作流提供可持续使用的在线软件；开源项目可以自托管为应用服务，不要求已有商业化或多租户。消费社交、内容与交易场所、纯客户端、底层组件及设备控制不会仅因联网而纳入。它们可能存在服务化变体，需按实际软件能力判断，而非声称整个领域不可能有 SaaS。

分类与叶子目录共用，开源项目与商业产品在浏览和搜索结果中清楚区分，优先展示开源项目。商业产品不安排与开源项目同等深度的功能、技术架构和部署调研。

资料来自真实项目或产品的公开来源，并记录来源及整理时间。公开源码、许可证待核验与已确认开源需如实区分；整理资料不代表已经部署或实测功能。

## 启动当前目录

首次克隆后，先恢复已复核的案例快照（只对全新空数据库执行；已有 `var/catalog.sqlite` 时跳过）。快照及计数见 [data/catalog-snapshot.json](data/catalog-snapshot.json)：

```sh
mkdir -p var
sqlite3 var/catalog.sqlite < data/catalog.sql
```

安装前端依赖并启动：

```sh
cd web
npm ci
cd ..
node scripts/dev.mjs
```

打开 <http://127.0.0.1:5288/browse>。需要 Python 3.10+、Node.js 22；首次恢复快照使用 SQLite 命令行；API 监听 `127.0.0.1:5299`，数据在本仓 `var/`，与 Atlas 分开。构建后单进程运行及测试命令见 [交付说明](docs/M0_M1_REPORT.md)。

`data/collections/sources/` 保存原始抓取网页，作为本地证据缓存，不提交 Git。仓库保留来源 URL、SHA 索引和复核报告；浏览目录及案例只需上述正式数据快照，重新克隆不包含原始证据正文。

## 历史方向：认知模板

以下保留 2026-10-17 起的旧方向、约定和实验设计供追溯，**不作为当前产品要求**。其中“现阶段”“第一版”“待审批”等均指当时的模板项目阶段。

### 目标

做一个**能卖的 SaaS & AI 工程产品**：以成熟商业化软件为目标，自己长期开发复用作为收益兜底。

- **卖给谁**：独立开发者、小团队、想给现有系统加 AI 的团队、用 Coding Agent 开发的人。
- **卖什么**：四类模板/积木：SaaS 通用模块、业务模板、AI 原生模板、给现有 SaaS 加 AI 的模块。
- **怎么算成功（North Star，2026-10-19 修订）**：两道门，都要过。
  1. **有效性门**（第一个项目上就能测）：模板组在**构建者看不到的留出测试**上优于对照组，且核实后的高/中危缺陷不更差。慢可以，质量必须提升；对照组在事先定好的预算内达不到的，记为"未达到"。质量不用构建者能看到的测试量，否则看得见测试的一组按构造就赢。
  2. **经济性门**：第二个同品类项目，达到事先定好的质量线所需的总时间（含改模板和人工时间）至多是对照组的一半，并且测试、安全、合规不打折。
  - **质量边界（2026-10-20）**：模板保证产品的**功能与形式质量**（功能齐全、不阻塞、权限/隔离/预算/安全/合规、模型调用接线正确），**不保证 AI 内容质量**（提示词打磨、模型选择、回答好坏）。后者属于产品团队后续的打磨，不进入模板和评测。结构性要求（如资料真的送进模型、答案真的进报告）属于形式质量，仍要测。
  - 对照组 = 只给用户需求和可测性契约。到目前为止的证据（ab-01）：契约 + 可执行验收贡献了质量；完整 spec + 分阶段尚未被证明比"契约 + 验收"更好。修订理由见 `experiments/ab-01/results.md` 的讨论。

### 关键判断

- **样板代码已经不值钱，认知才值钱。** coding agent 很快就能写出网页和 demo，但做不出成熟的 SaaS：它不知道这类产品有哪些现成的东西可用，也不知道一个"完整成熟"的产品到底包含什么。
- 所以**模板 = 交给 coding agent、让它把产品做到成熟的"说明书 + 契约 + 可执行验收"**。使用者不需要自己具备这些认知：把模板交给 agent，让 agent 按阶段开发即可。难点部分（租户隔离、计费账本、作业重试/取消、成本上限、权限）附验证过的参考代码。
- **模板分两种，都是"认知"而不是代码（2026-10-21）。** ① **模块模板**：next-forge 的模块清单（认证、数据库、支付订阅、邮件与通知、限流与安全、文件存储、webhooks 等，去掉供应商绑定）按我们的口径重写：该有什么、每项的正确行为、容易做错的地方、契约、可执行验收、人工决策点、验证记录；不含实现代码，验收能独立对任何声称实现了该模块的应用运行。② **产品模板**：由模块拼出来（引用，不复制）加产品自己的业务部分。买家的 agent 用自己的技术栈实现，用验收证明做对。模板的核心是**契约 + 可执行验收 + 人工决策点 + 产品定义**；评测包（留出测试、流程、参考实现、裁决）留在我们这边，不交给构建者；完整规格 + 阶段文档是可选档，等 `experiments/p2-support-bot` 的数据再定。
- **模板库的组织**：SaaS 清单分层——A 通用模块（取自 next-forge 并重写）、B 业务 SaaS、C AI 原生应用、D 给现有 SaaS 加 AI；每份模板标"草稿"或"已验证"，只有通过构建验证的才标已验证。应用（目录 + 验证报告）最后做，且先验证有人愿意买。
- **工厂是手段，不是目的。** 认知类产出（调研、功能清单、验收标准）可以批量生产；底座和契约手工打磨；独立验证是核心资产。不再追求"批量把开源仓库加工成模板"。
- **硬规矩：一个模板只有在 agent 真的照它做出产品、并通过它自带的验收之后，才算合格。**

### 现阶段的约定

- **优先级**：AI 相关优先，先做 AI 原生模板和 SaaS+AI 模块；其他类型需要时按需生成。
- **只给自己用**：商业化才需要的东西（销售用的许可证审查、发布流程等）推到商业化前再做。但每段复用代码的来源、许可证和 commit 现在就要记下来。
- **一人 + AI agent**：负责构建和负责验证的 agent 相互独立，人只在关键节点批准。
- **批量执行**：本地 opencode CLI，模型 `opencode-go/deepseek-v4.1-flash`。
- **产品的真实模型**：`deepseek-v4.1-flash`，接口地址和 key 由人填在根目录 `.env`（模板见 `.env.example`；`.env` 不入库）。验收永远使用假模型。
- **预算**：第一版暂不设上限。

### 模板格式 v0

```
blueprints/<模板名>/
  TEMPLATE.md        # 给 agent 的入口：怎么分阶段推进、什么时候停下来问人
  template.json      # 机器可读：阶段、决策点、默认技术栈、启动约定
  spec/
    landscape.md     # 品类认知：现成产品、开源项目、哪些复用、哪些自建（附许可证）
    product.md       # 成熟产品定义：角色、流程、功能清单（MVP → 成熟）、边界情况
    architecture.md  # 默认技术栈、数据模型
    api.yaml         # API 契约
    decisions.md     # 人工决策点及默认值
  stages/            # 每个阶段的目标说明
  acceptance/        # 每个阶段一组可执行验收测试（含难点负向用例）
  reference/         # 难点的参考实现（可选）
```

验收的独立性靠三点保证：
- **黑盒**：只通过 API 契约和少量浏览器流程测试运行中的应用；
- **每次从模板重新拷贝测试**：构建 agent 改测试没有作用；
- **测试本身要审查**：主要靠独立 agent 审查（另一个会话或模型，只读，对照 spec 找矛盾、遗漏和脆弱的测试）；辅助检查是对空应用跑一遍，必须全部失败。

### 第一版：把一条链完整走通

**第一个模板**：AI 研究/文档助手。默认技术栈固定为 TypeScript/Next.js + Postgres。验收时用"假模型"模式，不调用真实模型。

| 阶段 | 内容 | 关键验收（含负向） |
|---|---|---|
| S1 骨架 | 注册登录、组织/租户、权限 | 跨租户访问被拒 |
| S2 AI 作业 | 提交任务 → 后台多步执行，有进度、可取消、可重试 | 取消后不再继续执行；重试不重复执行 |
| S3 成本与产物 | 模型调用记账、用户额度、报告存储 | 超预算被拒；他人拿不到我的报告 |
| S4 成熟化 | 针对报告追问、运营后台、审计日志、数据导出 | 每个操作可追溯 |

**harness v0**：每个阶段先构建（opencode，在独立工作区里），再提交 git 快照，然后跑验收。不通过就把失败报告交回构建 agent 重做；通过后停下来等人批准，再进入下一阶段。全程记录用时、token、尝试次数、人工介入次数。

**对比实验**：A 组是 agent 拿着模板按阶段开发；B 组是同一个 agent 只拿到一句话需求，从空的 Next.js 项目开始。最后两组跑同一套验收，比较用时、花费、介入次数和通过率。

**顺序和人工节点**：
1. 写模板的 spec 和验收，由独立 agent 审查，并用空应用做辅助检查；
2. **人工审批 spec 和验收**（最重要的节点，它定义了什么叫"成熟"）；
3. 写 harness；
4. 跑 A 组，每个阶段人工看一眼；
5. 跑 B 组；
6. 复盘并修订格式；
7. 之后再考虑第二个模板和批量生产。
