## 第一部分：上线前必须修

7. 取消的结果会被"成功"覆盖：`finishSucceeded`（`server/jobs/engine.ts:656-670`）无条件把状态写成 `succeeded`，失败分支有"已取消就不覆盖"的保护（:641），成功分支却没有。如果在 synthesize 调用刚返回时取消，任务会变回成功，报告也会被保存。建议给 UPDATE 加上 `AND status <> 'canceled'`，并在写报告之前再检查一次状态。
8. `citationsOf(reportId)` 只按 reportId 查询，没带 `workspace_id`（`server/jobs/engine.ts:864`），违反 architecture §3 的"必须"。目前两个调用方都先经过按工作区校验的 `getReportRow`，所以不会泄露，但这是个潜在隐患。建议加上 `workspaceId` 参数和条件。
13. 生产环境缺配置时会悄悄用假模型：`MODEL_PROVIDER` 没设置时默认是 `fake`（`server/model/provider.ts:9`）；而"真实模式缺单价就拒绝启动"的检查（`scripts/check-config.mjs`）只在验收用的启动脚本里执行，`npm start` 不会经过它。两者叠加，正式部署时漏配一个变量，就会悄悄产出假报告、按假费用计费。建议：非测试模式下必须显式设置 `MODEL_PROVIDER`，否则拒绝启动；配置检查放到所有启动路径上（例如 instrumentation 或 `npm start` 的前置步骤）。
14. 真实模式下，预留费用可能低于实际费用：预估时把输出固定按 2000 个 token 计（`provider.ts:38`），实际输出更长时会超出预留，破坏"单个任务不超预算"这条不变式。没配单价时预估值是 0（`provider.ts:36`）。建议调用模型时传入 `max_tokens`，并用同一个值来计算预留。
18. 真实模式下已付费的调用可能没记进账本，破坏"已花费不超过预算"：(a) 模型调用成功后若 `input.signal.aborted`，直接抛 `ModelCanceled` 并释放预留，没写用量行（`engine.ts:546`、`chat/service.ts` 的 `signal.aborted` 分支）；(b) 研究任务里记账写库失败时只释放预留再重抛（`engine.ts:550-573`）；聊天里 `recordUsage` 失败时预留保持不动，这是保守的做法，不要改成释放，但要让重启恢复时能把它补记成一行用量；(c) 启动时 `releaseAllReservations()` 删光所有预留（`budget.ts:170`），正在进行的已付费调用既没有 spent 也没有 reserved。fake 模型下测不到。与第 14 条一起处理：调用成功就必须先记账，记账失败要保留预留（研究任务里也一样，不要释放），恢复时补记，而不是启动时一律删除。

另外，第 15 条和审查指出的几处内部查询（`stagesOf`、`jobStatus`、`stepsOf`、`citationsOf`，以及按 `jobId` 查报告）也只按 ID 查询，请和第 8 条一起，统一加上 `workspace_id` 参数和条件：

后台任务内部的几处查询（`stagesOf`、`jobStatus`、`citationsOf`，见 `engine.ts:98/411/1019`）只按 ID 查询，没带 `workspace_id`。目前调用方都在后台任务内部，或已先做过工作区校验，所以不会泄露。与第 8 条合并处理。

## 第二部分：健壮性问题

1. 登录限流不是原子操作：并发的失败请求可以同时通过"失败次数 ≥ 10"的检查，突破上限（`server/auth/service.ts:88-110`）。建议对计数做原子递增，或在事务里加行锁后再判断。
2. 登录失败记录只增不减，陌生邮箱的失败记录永远没人清理（`server/auth/service.ts:73-75`）。建议按时间窗口定期清理。
3. 注册不是原子操作：账号建好了但会话创建失败时，用户既登不进来，重试注册又会收到 409（`app/api/auth/signup/route.ts:15-17`）。建议放进同一个事务，或者失败时补偿删除账号。
4. 请求体没有大小上限，超大的 JSON 可能耗尽内存（`server/lib/http.ts:93`）。建议读取前先检查 `Content-Length`，例如超过 1 MB 就拒绝。
5. 邀请时"是否已是成员"的检查在事务外面；邮件在事务提交后才发送，发送失败了邀请却还在（`server/workspaces/service.ts:219-246`）。建议把检查移进事务；发送失败时记录告警，或撤销这次邀请。
9. analyze 阶段的进度不随子问题推进：`completed` 是用循环外的快照算的（`engine.ts:562/583`），进度一直停在第一个子问题的位置。
10. `document_chunks` 没有 `(document_id, idx)` 唯一约束。重启恢复和新建资料的后台处理同时进行时，可能插入重复的块（`schema.ts:126-138`、`service.ts:122-147`）。
11. `recoverStale` 里的文档恢复 SQL 实际上什么也没改，却会把所有处于 processing 状态的资料重新处理一遍，包括正在正常处理的（`engine.ts:286-294`）。
12. 真实模型输出 `[1,2]` 这种多编号引用时，系统不会为它生成引用记录，但前端会照样显示这个标记（`engine.ts:757` 和 `markdown.tsx:17` 的解析规则不一致）。假模型只输出单个编号，所以验收测不到。
19. 恢复失败后 worker 照常启动，且不再重试恢复：`ensureWorker` 先置 `started = true`，`recoverStale()` 失败后残留的 `running` 任务永远不会被恢复（`engine.ts:369-387`）。
20. 多次请求重置密码会并存多个有效令牌，旧链接在新令牌签发后仍可用，直到有人真正重置才清理（`auth/service.ts:126-172`）。
22. 追问没有引用时自动补的"依据："是硬编码的中文（`chat/service.ts`），回答是英文时会混语言。
