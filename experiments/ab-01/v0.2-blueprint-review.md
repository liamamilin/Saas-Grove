我已完成对 `blueprint/` v0.2 改动的只读审查。以下按严重程度排列，均附文件:行号证据。

---

## 1.【高】明文扫描只查 `public` schema，且 bytea 列实为 hex，与 §9 措辞不符（可绕过 + spec 失实）

- `acceptance/lib/db.ts:32` 用 `WHERE table_schema = 'public'` 取表；`db.ts:41` 与 `db.ts:53` 都靠 `row_to_json(t)::text` 做匹配。非 public schema（如自定义 schema 或 pg-boss 的 `pgboss`）里的表完全不会被扫。
- `architecture.md:154` §9 声称"在库里**所有**文本列（含 JSON 和**字节列**）里搜索"，但 bytea 列经 `row_to_json` 渲染成 `\x…` hex 字符串，明文令牌原样存 bytea 不会被 `strpos` 命中。

**影响**：构建者把令牌存到非 public schema 或 bytea 列即可躲过明文检测；同时 spec 承诺了测试做不到的覆盖，对照实验里这是实现细节而非契约。**建议**：遍历所有非系统 schema；bytea 列用 `convert_from(col,'UTF8')`，或在 §9 把范围收紧为"public schema 的文本/JSON 列"，做到措辞与实现一致。

## 2.【高】outbox 表名豁免可被轻易玩弄

- `acceptance/tests/s1/security.test.ts:8` `allowedPlain = (t) => /outbox/i.test(t)`：任何表名含 "outbox"（如 `session_outbox`、`user_outbox`）即豁免全部令牌明文检查。§6（`architecture.md:111`）与 §9（`:154`）明文允许，但豁免仅凭表名子串匹配，构建者把会话/邀请/重置令牌塞进一张 outbox 命名的表即可通过。密码不受此影响（`security.test.ts:55` 的 `whereStored(PASSWORD)` 未跳过任何表）。

**建议**：豁免应卡住"该表只存 invitation/password_reset 两种模板、仅 TEST_MODE 写入"这类结构约束，而非仅靠表名。

## 3.【中】"取消时中止在途调用"时序不稳健，可能空过

- `acceptance/tests/s2/jobs.test.ts:97-103`：`plan===1` 后仅 `sleep(600)` 就取消，全程没有断言 analyze 调用**已经开始**。plan 完成到 analyze 发起之间还有阶段持久化、检索/选块（§4.2、§5），若这段超过 600ms，取消发生在 analyze 发起之前，测试就"没测到中止"而通过——正是 CHANGES-WHY 想堵的"跑完再记账"式实现仍可能漏网。

**建议**：取消前轮询到 analyze 阶段进入 `running`（或首个 analyze 阶段记录出现）再取消，并保留后续"用量不再增加"断言。

## 4.【中低】`literal()` 白名单过严，可能误判合法实现

- `acceptance/lib/db.ts:26-29`：令牌/会话值含 `[A-Za-z0-9_\-.~+/=%@:$ ]` 之外字符（如 `!`、`,`、`'` 等合法 cookie/token 字符）会直接 throw，令测试以错误失败。该字符集在 `api.yaml` 或 §5–§9 里未规定，属 spec 未约束的实现细节。**建议**：改用正确的 SQL 转义/参数化，而不是白名单拒绝。

## 5.【低】一致性：`api.yaml` 版本号未随 v0.2 更新

- `spec/api.yaml:4` `version: 0.1.0`，而 `template.json:5` 为 `0.2.0-draft`；本版 `api.yaml` 本身也改了 audit 枚举（`:435` 移除 `workspace.deleted`）。测试数量方面核对无误：S1=24（auth 9 + workspaces 10 + ui 2 + security 3）、S2=23、S3=10、S4=10，共 67，与 `template.json`/`stages/*`/CHANGES-WHY 一致。

## 6.【低】公平性结论与 checklist

- 新增/改动测试强制的规则（数据在 DATABASE_URL、令牌哈希、argon2id/bcrypt、取消中止且不产生用量记录）**都已写进 §5–§9 或 `api.yaml`**，对"只拿可测性契约"的一组基本公平；唯一缺口是第 1 条的"public schema/文本列"实现细节未在 §9 写明。
- `spec/review-checklist.md` 整体准确，无明显误报项；仅 `review-checklist.md:26` 要求 real 提供方的 `fetch` 也接 AbortSignal，超出验收范围（§5.1 明确"验收永远是 fake"），建议标注为"人工审查标准"而非验收/契约要求，以免审查员误报。

**其余未发现问题**：`db.ts` 的 SQL 拼接无注入风险（`ident()` 正确转义标识符、`literal()` 白名单 + `table.replace(/'/g,"''")` 均安全）；`security.test.ts` 三条测试均带"数据确在库中/确有会话 cookie"的正向守卫，`run.mjs --self-check` 也会对空应用验证每条测试都应失败，未发现"找不到就当通过"的空洞路径。
