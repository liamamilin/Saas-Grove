# 这次运行暴露的模板缺口（留到 v0.2 处理）

实验进行中**不改**模板和验收，否则 A 组后面的阶段和 B 组的评分会失去可比性。这些问题都在实验结束后统一处理，处理完同样要经过独立 agent 审查。

## 验收没覆盖到的

1. **在 synthesize 阶段取消**（来自 S2 审查第 1 条）：现有的取消测试是在 plan 刚完成后取消的，没有覆盖"最后一次调用进行中被取消"这种情况。可以补一条：把假模型的延迟调大，等 synthesize 阶段开始运行后取消，然后断言最终状态仍是 `canceled`、`reportId` 为空，并且之后不再新增用量记录。
2. **进度要随步骤推进**（来自 S2 审查第 9 条）：现在只断言了进度"不倒退"。可以补一条：analyze 阶段内至少能观察到 2 个不同的进度值。
3. **引用标记的格式**（来自 S2 审查第 12 条）：spec 只说了 `[n]`，没有说多编号写法（`[1,2]`、`[1-3]`）怎么处理。要么在 spec 里规定"必须写成单个编号"，要么规定多编号要展开成多条引用。

## spec 写得不够明确的

4. 启动脚本是否要在启动时构建（已在 harness 层解决：runner 在验收前统一构建）。实验结束后，把这条约定也正式写进 v0.2 的启动约定。
5. "所有查询都要带 workspace_id"这条黑盒测试测不到，只能靠审查发现。可以考虑在 `reference/` 里提供一个带工作区作用域的查询辅助函数作为参考实现。

## 真实模式的安全默认值（来自 S3 审查）

6. spec 只规定了 `MODEL_PROVIDER=real|fake`，没规定默认值，也没规定"真实模式缺配置就拒绝启动"这道检查必须覆盖**所有启动方式**。这次的产品选择了默认用假模型，配置检查也只放在验收启动脚本里，于是正式部署会在不知不觉中退回假模型。v0.2 应该写明：非测试模式下缺少模型配置必须报错（失败时关闭），并在验收里加一条测试：不设 `TEST_MODE` 又不配模型时，产品要拒绝启动（或拒绝发起研究任务）。
7. 预算不变式在真实模式下要靠"预留上限 = 调用时传给模型的输出上限"来保证。spec §4.3 只说了"预留预估费用"，应该明确：预留必须基于输出 token 的硬上限，而不是一个估计值。

## 来自 S4（追问、审计、导出、删除）

8. **"真的删掉了"没有可测的定义**（S4 阶段目标 vs 验收）：阶段目标写"删除的东西真的删掉了"，验收只测了"列表里没有、不能被新任务和检索使用、工作区删除后全部 404"。builder 据此选了软删除，是合规的实现。v0.2 要么把目标改成"不可访问"，要么规定物理删除并增加一条测试，直接查数据库确认文本已不存在。
9. **已付费调用必须先记账**：spec §4.3 只写了预留和预算不变式，没说"调用成功后无论取消、记账失败还是重启，都必须留下一行用量或保留预留"。假模型下根本测不到，只能靠审查发现。v0.2 应写成显式规则，并在 `reference/` 里给出"预留 → 调用 → 记账 → 补记"的参考实现。
10. **S4 的 10 条测试对实现的约束比预想的弱**：63 条全绿，但审查仍找出了 3 处账本漏记、1 处恢复缺陷，都属于故障注入类的问题。假模型已有 fault injection 接口，可以补"记账失败"和"进程在调用返回后、记账前崩溃"两条。
11. **"邮件令牌在非测试模式送不出去"不是缺陷**：这是 H2 的默认值（只做测试 outbox 和日志发信器）。审查 agent 没读到 H2，把它当成了缺陷。v0.2 的审查提示应附上 `spec/decisions.md`，避免重复报已决定的事项。

## 来自集中修复轮（S4-r2）

12. **一轮集中修复会带来新缺陷，其中一个落在钱的路径上**：第 19 条的修复引入了"恢复重试与 worker 并发"的回归，被复审抓到；修复轮没有让验收变红。结论：修复轮之后必须再做一次独立审查，而且审查提示要点名"本轮改动引入的回归"。只靠回归验收不够。
13. **修了一半的修复**：第 4 条（请求体无大小上限）只修了 JSON，没覆盖 multipart 上传。清单里要写清"所有接收请求体的入口"，或者在 spec 里规定统一的请求体读取函数。
14. **真实模式的几条修得扎实**：缺配置时拒绝启动（我实测：非测试模式缺 `MODEL_PROVIDER`、真实模式缺 key 和单价，进程都立即退出码 1）、预留按 `max_tokens` 硬上限计算、已付费调用先记账再处理取消。这说明"把要求写成具体清单并要求写明验证方式"对 builder 有效。


## 来自 B 组对比（详见 `results.md`）

15–18 见 `results.md` 的"对模板 v0.2 的改动"：追问测试太脆弱、`workspace.deleted` 审计不可观察、界面状态要自动刷新、哪些要求该放进 B 能看到的契约。

## 来自重复的 B + 测试（详见 `results.md`）

19. **"令牌不得明文存库"和"密码用 argon2id/bcrypt"可以写成测试**：验收套件能连到 runner 建的测试数据库，扫描所有文本列即可，不依赖具体表结构。第 2 次 B + 测试出现了明文会话令牌，验收没抓到。
20. **取消要中止在途调用**：补一条测试，假模型加大延迟，调用进行中取消，断言任务很快变为 `canceled`、之后不再新增用量记录。两次 B + 测试都漏了这一条。
21. **请求体和上传大小上限**要有测试（413），和 A 的 backlog 25 是同一类。
22. spec 里只能靠读代码发现的几项（查询带 `workspace_id`、测试模式不放宽规则、`DECISIONS.md`、不引入 spec 之外的有风险功能如网页导入）整理成**审查员检查表**，而不是整套 spec。
23. **需求里写了"网页链接"，模板范围里没有**：A 没做也没提出来；B、B + 测试共 3 次运行都做了网页导入并带出 SSRF 风险（此前误写为 4 次；加上 B3 是 4/4）（DNS 重绑定、重定向绕过）。v0.2 要决定两件事：网页导入是否进模板（带 SSRF 安全设计、`reference/` 里的参考实现和测试）；以及无论是否进模板，都要求构建者把"需求里有而模板没有的内容"写进 `QUESTIONS.md`，并增加一个衡量"需求覆盖度"的评分（现在 63 条验收只测模板自己的范围）。

24. **bcrypt 强度契约没写**：§9 只说"argon2id 或 bcrypt"，`decisions.md` T5 另写 cost ≥ 12，构建者看不到；B3 用了 cost 10 并通过。bcrypt 哈希字符串里就带 cost（`$2b$10$…`），可以直接测。（v0.3 候选）
25. **生产配置默认值**：`MODEL_PROVIDER` 不设就静默用假模型（B3 审查严重 #1），检查表有这条但黑盒测试看不到。可以做成启动测试：不开 `TEST_MODE` 且不设 `MODEL_PROVIDER` 时应用必须退出或拒绝服务。（v0.3 候选，需要 runner 支持指定环境启动）
26. **真实模式的钱**：假模型测不到"请求带 `max_tokens`、预留上限等于它、按返回的 usage 记账"（B3 审查 #3；A 的 backlog 14/18 也是这一类）。可以在验收里起一个本地 OpenAI 兼容假服务，让产品用 `MODEL_PROVIDER=real` 连它，测真实代码路径。（v0.3 候选，较大）
27. **审查员会漏报**：B3 审查写"业务查询均带 `workspace_id`"，但 `worker.js` 里有四处只按主键查（我核实的）。审查员的"没发现"不等于"确认没有"；检查表上的项目，如果能写成机械检查（grep 出所有 `FROM <租户表>` 且 WHERE 不含 `workspace_id` 的语句交给审查员逐条看），比让审查员凭印象判断可靠。
28. 网页导入：B3 是第 4 次不带 spec 的运行做了它（4/4），并带出 SSRF（DNS 重绑定，已核实）；见 23，决定仍在用户手里。
29. **v0.3 做了 24–26**：bcrypt cost ≥ 12 进了 §9 和测试；缺配置拒绝启动的测试靠 runner 新增的"再起一个实例"；真实模式的钱用进程内的假 OpenAI 服务测（带 `max_tokens`、预算很小时不发付不起的调用、按 `usage` 记账）。27 的做法没变（检查表）。
30. **会说谎的假服务比审查员可靠**：B2 的"预留只按 900 token、却发 `max_tokens: 1600`"，两次审查都没发现，预算调低到 0.015 美元的假服务测试一下就抓住了。以后同类缺陷优先考虑做成"让对方撒谎的探针"。
31. **启动脚本里的默认值会掩盖应用的行为**：B、B2b、B3 的 `acceptance-start.sh` 都写了 `MODEL_PROVIDER:-fake`（B 还有 `TEST_MODE:-1`）；测试要在没有这些变量的环境里再启动，§7 因此多了一条"启动脚本不得补默认值"。
32. **runner 要能用另一组环境再启动产品**：这是配置类、生产模式类要求能测的前提，已加（`POST /instances`）。其他模板（别的品类）可以直接复用。
33. **B4（v0.3 测试下的 B + 测试）验证了 24–26**：bcrypt cost 12、缺配置拒绝启动、任务路径的 `max_tokens` 和预留，构建者看到测试后都自己做对了（B3 全漏）。n=1。
34. **测试到不了的路径，同类缺陷原样复现**：追问路径预留按 900、请求按 1400 发（和 B2 的任务路径缺陷同一类）。构建者不会主动把规则推广到测试没碰的路径。v0.4 候选：把追问纳入真实模式的钱测试（预留等于发出的 `max_tokens`）。
35. **假服务太"体贴"会掩盖缺陷**：假服务不管产品有没有要求都在流式最后一块带 `usage`，而 OpenAI 协议要求请求带 `stream_options: {include_usage: true}`；B4 没带，追问在真实服务上很可能按 0 记账（未用真实服务验证，按协议推断）。审查员没发现，是我读代码看到的。v0.4 候选：假服务只在被要求时才带，契约写明。
36. **审查员的"高"要降级核实**：B4 的审查员报了 3 条高；核实后一条属实（追问预留）、一条属实但窗口很窄（取消与完成赛跑）、一条规格根本没写（retry 权限）。同时它漏了流式 `usage`。和 27 一致：审查员的话只当线索。
37. **第一次全绿之后的时间**：B3 约 96 分钟、B4 约 73 分钟（占总构建时间的 78% / 51%）。这些时间是否提高质量没有证据，提速实验要先看这一段。
38. 网页导入：B4 是第 5 次不带 spec 的运行做了它（5/5）；见 23、28，决定仍在用户手里。
39. 契约没写、构建者看不到的两条再次出现：会话 30 天滑动续期（`decisions.md` T6）、retry 权限（`product.md` 没写）。要么写进契约，要么承认它们是审查员检查表里的人工项。
40. **B5r-beam 是个能过 70/70 的空壳（我读代码核实）**：analyze 阶段发给模型的是字面量 `Analyze: q1`，synthesize 发的是 `Synthesize report for: <问题>`，资料文本根本没进提示词；没有切块、向量化、检索；`[n]` 引用按 `chunks[(m-1) % len]` 硬映射。假模型的固定回复让所有测试通过。这是验收的一个**结构性漏洞**：只要假模型不依赖输入，"产品真的把资料交给了模型"就测不到。v0.4 候选：用会说谎的假服务（像第 30 条）——在上传的资料里埋一个唯一的暗号，断言发给模型的请求里含有这个暗号；断言 analyze/synthesize 请求里含有被检索到的原文。这比再加行为测试更优先。
41. **审查员这次抓到了测试漏掉的东西**（B5r-beam 审查第 1 条属实）：审查员的价值在"测试看不到的结构"，不在重复测试已有的行为。
42. **v0.4 候选测试（已有探针原型，`experiments/ab-01/probes/`）**：① 上传资料里的暗号必须出现在发给模型的请求里；② 模型的 synthesize 回答必须出现在报告里；③ 长文档下发给模型的请求不能是整篇文档、相关段落必须在里面；④ 追问的模型请求里必须带资料原文。四条都用现有的假 OpenAI 服务就能做，正对照 A、B4 都通过，能把 B5r-beam 和 B7-beam-1/2/3 分出来。
43. **"免费模型当构建者"的结论要靠探针，不能靠分数**：beam 4/4 次 70/70，但没一次做出追问带资料的产品。批量任务选模型，要把"验收之外的探针"算进去。
