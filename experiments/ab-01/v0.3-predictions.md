# v0.3 草案：跑已有产品之前写下的预测（2026-10-18）

v0.3 相对 v0.2（tag `blueprint-v0.2.0-draft`）新增三类检查，共 70 条（v0.2 是 67 条）：

1. 密码哈希：argon2id，或 cost ≥ 12 的 bcrypt；注册和重置两条路径都查，库里出现 cost < 12 的 bcrypt 就失败（S1，改动一条已有测试）。
2. S2 `real-mode.test.ts`（2 条）：真实模式配置完整时能启动、且没有 `/api/__test__/*`，缺任何一项（`MODEL_PROVIDER`、`MODEL_BASE_URL`、`MODEL_API_KEY`、两个单价）都要拒绝启动；每次调用带 `max_tokens`、按模型返回的 `usage` 记账。
3. S3 `real-budget.test.ts`（1 条）：预算只够一次小调用时，不能发出输出上限付不起的调用。

我对每个已有产品的预测（只凭我对它们代码的了解，没跑过）：

| 产品 | 预测 | 理由 |
|---|---|---|
| A | 70/70 | 已单独跑过新增的 4 条测试，全过 |
| B3 | 66/70：哈希 cost、配置、预算上限、按 usage 记账各挂 | bcrypt cost 10；`acceptance-start.sh` 和 `config.js` 都把 `MODEL_PROVIDER` 默认成 fake；真实请求没有 `max_tokens` |
| B2b | 挂：scrypt、取消中止、令牌明文（v0.2 已有）；新增里配置测试挂（启动脚本 `${MODEL_PROVIDER:-fake}`） | 看过启动脚本；其余未知 |
| B2 | 挂：scrypt、取消中止；新增部分未知 | |
| B | 挂得更多（v0.2 时已 60/67） | |

验证"新增测试有区分度"的标准：B3 的四个预期失败要真的出现；A 不能因为测试自身的问题挂掉；空应用自检 70 条全败（已通过）。

## 实际结果（审查意见处理后的最终版，提交 `b12bd07`，2026-10-18）

| 产品 | 预测 | 实际 | 失败的测试 |
|---|---|---|---|
| A | 70/70 | **70/70** | — |
| B3 | 66/70（哈希 cost、配置、预算上限、按 usage 记账） | **66/70** | 正是这四条 |
| B2b | 挂 scrypt、取消中止、令牌明文、配置 | **66/70** | 取消中止、配置、令牌明文、哈希 |
| B2 | 挂 scrypt、取消中止；新增部分未知 | **66/70** | 哈希、取消中止，**配置**（应用本身 `=== "real" ? real : fake`，默认假模型），**预算上限** |
| B | 更多 | **60/70** | 原有 7 条中的 6 条（重试 3 次、数据在库里、令牌、预算、UI、PDF，哈希），加配置（启动脚本 `TEST_MODE:-1`，非测试模式下仍挂载测试接口）、按 usage 记账、预算上限 |

意外和核实：

- **B2 的预算上限失败是真缺陷**（我读了代码）：`estimatedCallCostUsd` 对非 synthesize 阶段只预留 900 个输出 token，而 `realChat` 默认发 `max_tokens: 1600`。预算为 0.02 美元时这个差距看不出来，改成 0.015 才暴露。之前对 B2 的两次审查都没有发现。
- B2b 创建任务时就返回 402（在预算 0.015 下，它按保守估算认为付不起），没发出任何调用，所以预算测试按"拒绝也算安全"通过。这是合法行为，不是漏掉。
- B、B2b、B3 的启动脚本都写了 `MODEL_PROVIDER:-fake`（B 还有 `TEST_MODE:-1`），按新的 §7 都不合规；B2 的启动脚本没写，是应用代码本身默认假模型。

变体测试（改 A 的拷贝）：只按 300 个输出 token 预留、仍发 `max_tokens: 2000` → 被预算测试抓住；记账改成固定价、不看 `usage` → 被"按 usage 记账"抓住。
