# ab-01 结果：带模板（A）对比不带模板（B）

日期：2026-10-18。同一个构建模型（`deepseek-v4.1-flash`）、同一份冻结的用户需求、同一套 63 条验收、同一个审查员（`deepseek-v4-pro`）。每组只跑了一次。

## 一句话

模板（加上可执行验收）把质量托住了，但**没有让第一个项目更快**：A 组用了 B 组约 2.4 倍的构建时间。追加的 B + 测试对照（做了两次）显示：验收套件本身托住了绝大部分质量，两次都是 63/63；完整 spec 加四个阶段相对只给测试，额外多出来的价值集中在一小块黑盒测试看不到的要求（会话令牌哈希、取消时中止在途调用、argon2id 等），代价是 2.2–3.5 倍的构建时间。North Star（第二个同类项目省 ≥50% 的时间）这次没有测，也不能说达到。

## B 组没通过的 5 条，原因分类

| 失败的测试 | 原因 | 类别 |
|---|---|---|
| 一次调用最多重试 3 次、退避逐次翻倍 | B 写成最多 6 次、固定 150 毫秒 | 模板才有的要求（architecture §4.2，不在 B 拿到的契约里） |
| 任务不得超过预算 | 没有"调用前先预留"，超支 0.04 > 0.035 | 模板才有的要求（§4.3） |
| 解析 PDF 上传 | 它用的 pdf-parse 读不了测试用的 PDF（"Command token too long: 128"） | 实现缺陷 |
| 界面：资料处理完显示 `ready` | 登录后点进研究页，页面会把数据加载两次，第一次加载后输入的内容被重新渲染清空，点提交时什么请求都没发出（我用测试同样的流程直接探测过：整个过程里没有 `POST /documents`）。用注册后直接进入的流程则正常，所以是时序相关的界面缺陷 | 实现缺陷 |
| 追问只能依据报告自己的资料 | B 的假模型把问题原文回显在答案里，测试检查"答案不含 beacon logs"，而问题本身就含这个词 | **测试太脆弱**，B 的行为并不违反 spec |

所以：5 条里 2 条是 B 看不到的要求，2 条是 B 自己的缺陷，1 条是测试的问题。这 1 条按"不为通过而改验收"的规矩，这次不改，留到 v0.2。

## 审查发现

B 的最终审查（`B-ab01/records/reviews/final-r1.md`）共 8 条：2 高、3 中、3 低。我对着代码核实了其中 7 条（未核实：URL 导入的 SSRF 重绑定窗口）：

- **来自 B 看不到的 spec**：没有预算预留；重试次数和退避不对；用 SQLite 替代了 Postgres 且没写 DECISIONS.md；没有每工作区并发上限（全局单线程）。B 的需求里写着"避免重型服务"，选 SQLite 是对需求的合理回应。
- **B 自己的缺陷**：`sendMail` 不管是不是测试模式都把明文令牌写进 outbox 表，永不清理（测试模式下 outbox 是契约要求的，A 只在测试模式写）；检索 SQL 没带 `workspace_id`；自己加了"导入网页"功能，带出 SSRF 风险；传入 `postgres://` 的 `DATABASE_URL` 时悄悄改用本地 SQLite 文件，只打一行警告，和 A 的"缺配置时悄悄用假模型"是同一类问题。
- **一条 spec 和测试的矛盾**：`workspace.deleted` 审计事件。B 没写，验收照样通过。工作区删除后审计日志本身就查不到了，这条要求测不出来。
- 审查报告里"生产环境不发邮件"一条不算缺陷：A 和 B 都按 H2 的默认值只做 outbox 和日志发信器（B 在自己的 `QUESTIONS.md` 里也列为待确认）。

**和谁比**：对比基线必须是 A 在 S4 放行前的审查（`S4-r1.md`，冻结点），不是修复轮之后的复审。S4-r1 的结果是：

- 1 高：真实模式下已付费的调用可能没记进账本（违反 §4.3 的预算不变式，窄口径的竞态和重启问题）；
- 1 中：analyze 阶段进度卡在 40%；
- 2 低：部分内部查询没带 `workspace_id`、恢复失败后 worker 不重试；
- 另有 1 条是 H2 的默认值，不算缺陷。

修复轮之后的复审（`S4-r2.md`）：1 高（修复轮自己引入的恢复重试回归，会重复执行和重复计费，违反 §4.2）、1 中（上传先整读内存）、2 低。

**能成立的说法**：两组在"真实模式下的钱的路径"上都有假模型测不到的错误。A 的错误是窄口径的竞态和重启问题，预留机制本身存在；B 是完全没有预留，一次调用就能超支，并发时没有上限。A 在 S1–S4 的审查里没有出现"整块漏掉模板里已有要求"的问题；但不能说 A 没有违反模板里的要求，S4-r1 和 S4-r2 各有一条。差距是真实的，比我最初写的要小。

审查次数不可直接比：A 审了 6 次，B 只审 1 次；B 的审查是拿 B 没见过的 spec 去对照，对 B 偏严。

## 这次实验支持什么、不支持什么

支持：
- 用模板加可执行验收，同一个模型能把"成熟产品的隐含要求"（重试、预算预留、租户隔离、恢复、Postgres）做对，并且能验证；不用模板，同一个模型会漏掉这类要求，而且自己说 DONE 时并不知道漏了。
- 独立审查有用：它在 A 里抓到了测试漏掉的约 20 条真问题（backlog 的 27 条去掉重复、已决定的默认值和待产品决定的几条），包括修复轮自己引入的回归。

不支持：
- "模板让第一个项目更快"。数据是相反的：A 的构建时间约 2.4 倍，output token 约 2 倍。
- North Star。它问的是第二个同类项目，这次没有测。

## 时间差的可能原因（假设，尚未验证）

1. A 的 builder 手里有验收套件，反复跑到全绿（S4 就跑了 7 次），B 没有测试可跑，自己说 DONE 就停了。给 B 同样的测试，它也会多花时间。
2. A 分四个阶段，每个阶段都有"构建、验收、审查"的节奏，还要写 DECISIONS.md、PROGRESS.md、探针脚本。
3. A 的代码量约为 B 的 1.33 倍，但时间是 2.4 倍，说明多出来的主要是验证和文档，而不是功能。

要判断"相同质量下谁更快"，需要以下任意一个对照，这次都没做：（a）给 B 同样的测试让它迭代到全绿；（b）去掉 A 的阶段划分，一次性给完整 spec 和测试。

## 局限

- 每组 n=1，一个模型，一份需求；构建模型有随机性。
- B 拿到的契约列出了全部接口，等于透露了功能清单，所以 A 与 B 的差距是模板价值的**下限**。
- B 的最终审查用的是它没见过的 spec，对 B 偏严；A 经历了 6 次审查和 1 次集中修复，对 A 偏有利。
- 我在核对 B 的失败原因时，把验收跑在 B 的目录上（复现单条测试和直接探测界面），所以 `B-ab01/project/app/data/` 里多了几个 SQLite 文件，以及 `B-ab01/records` 之外没有别的改动；以后做取证时要知道这一点。
- 验收、审查提示在实验中途没有改动，但 B 组的审查步骤是在 A 组 S4 检查点之后才加的（同一审查员、同一提示、仅改一句话），A 组 S1–S3 的审查没有对应的 B 组版本。

## 对模板 v0.2 的改动

已有的 1–14 条见 `template-learnings.md`。这次 B 组新增：

15. 追问测试改为检查引用的 `documentId`，不要检查答案文字；或在契约里写明假模型不得回显问题。
16. `workspace.deleted` 审计事件在删除后不可观察：要么从事件列表里去掉，要么写清楚怎么观察，要么保留删除后的审计日志。
17. 契约里补一句"资料处理完，界面要自动刷新状态"，B 的失败说明这条不是显而易见。
18. 把"重试 3 次、退避逐次翻倍""调用前预留"这类要求，放进 B 能看到的**可测性契约**里是否合理，要决定：放进去，B 的差距就缩小，但契约就变成了半份 spec。

## 追加对照：B + 测试（`B2-ab01`，2026-10-18）

只比 B 多一样东西：可以自己运行的验收套件（`blueprint/acceptance/`，63 条）。仍然没有 spec、没有阶段划分、没有模板说明。构建者和 B 一样是 `deepseek-v4.1-flash`，同一份需求，一轮构建，做到自己说 `DONE`。

| | A 放行 S4 时 | A 修复轮之后 | B（无模板） | **B + 测试** |
|---|---|---|---|---|
| 验收 | 63/63 | 63/63 | 58/63 | **63/63** |
| 构建用时 | 186.2 分钟 | 233.8 分钟 | 78.2 分钟 | **53.6 分钟** |
| agent 总用时 | 221.2 分钟 | 283.0 分钟 | 82.2 分钟 | **59.6 分钟** |
| output token | 336k | 432k | 162k | **143k** |
| reasoning token | 734k | 813k | 430k | **172k** |
| 人工介入 | 3 放行 / 1 反馈 | 5 / 2 | 0 | 0 |
| 技术栈 | Next.js + Postgres | 同左 | Vite + Express + SQLite | Vite + Express + Postgres |
| 最终审查 | S4-r1：1 高 1 中 2 低 | S4-r2：1 高 1 中 2 低 | 2 高 3 中 3 低 | 2 严重 2 中 2 低 |

（审查的严重程度是审查员自己标的，不同次之间标准会漂，只能看数量级。）

### B + 测试审查里的 6 条

我对着代码核实了第 1、2、3 条，其余没有逐条核：

1. **取消不会中止在途的模型调用**（核实）：`callWithRetry` 只在每次尝试之前查任务是否被取消，调用本身没有 AbortController；调用返回后照常记账。验收的取消测试仍然通过，因为假模型很快。真实模式下一次调用最长 120 秒，取消之后还会扣这一笔。A 在这一点上做对了（用 AbortController 中止）。
2. **追问的预算预留可能永久泄漏**（核实）：`reserveCall` 之后到 `try/finally` 之前还有好几次数据库查询，任何一次抛错都不会释放预留；预留存在内存里，累加到最后会把该工作区的所有后续任务和追问都卡成 402。
3. **追问里查任务没带 `workspace_id`**（核实）。目前不会越权，但是和 A 的同类问题一样。
4. 密码哈希用 scrypt，不是 spec 里要求的 argon2id 或 bcrypt，也没有 `DECISIONS.md`。
5. 记账和保存阶段结果之间有崩溃窗口，恢复后可能重复计费（A 的复审也有同类问题）。
6. `TEST_MODE` 下关掉了注册和找回密码的限流。

### 这个对照说明什么

1. **验收套件是质量的主要来源。** 有了套件，同一个模型在一轮之内就做到 63/63，而且比没有套件的 B 还快（53.6 对 78.2 分钟）：它不用靠猜去补隐含要求，也不用在做错之后才发现。B 丢的那几个失败测试（重试次数、预算预留、PDF）它全部做对了。
2. **相对 B + 测试，A 额外多出来的东西，在这次的指标上没有看到清晰的质量提升：** 验收同为 63/63；对最终代码的一次性审查，数量和严重程度在同一个量级（A 1 高 1 中 2 低，B + 测试 2 严重 2 中 2 低）。A 的构建用时是它的 3.5 倍。按用户的标准，"质量没有提升还变慢"这一条，在 A 相对 B + 测试这里是成立的，只是证据很弱（每组只有 1 次）。
3. **spec 的确还有一小块测试覆盖不到的价值。** B + 测试漏掉的 4 项（取消时中止在途调用、argon2id、查询带 `workspace_id`、测试模式不放宽规则）都是黑盒测试看不见、只有 spec 或审查才会发现的东西；A 在其中前两项上做对了。另外 A 留下了 `DECISIONS.md`、`QUESTIONS.md` 和可恢复的、落在数据库里的预算预留，B + 测试把预留放在内存里。
4. **所以更像是这样：** 模板的核心是"契约加可执行验收"；spec 的价值收缩到"测试看不到的那一小块"，更合适的形态是给 builder 一份短清单加给审查员的检查表，而不是一整套 spec 加四个阶段。

### 这个结论的可信度

- 每组只有 1 次，构建模型有随机性；B + 测试可能只是运气好，A 也可能只是运气差。
- 审查员的数量和严重程度判断是噪声很大的指标。
- 测试套件是照着 spec 写的，所以"测试的价值"里有一部分其实是 spec 的价值，只是换了载体。
- 审查次数仍然不对等：A 在不同阶段审过多次，这里用的是对最终代码的那一次（S4-r1、S4-r2）。

### 重复一次 B + 测试（`B2b-ab01`）

同样的输入再跑一遍，用来看上面的结果是不是运气。

| | B + 测试 第 1 次 | B + 测试 第 2 次 |
|---|---|---|
| 验收 | 63/63 | 63/63 |
| 构建用时 / 总用时 | 53.6 / 59.6 分钟 | 83.4 / 91.2 分钟 |
| output / reasoning token | 143k / 172k | 134k / 229k |
| 代码量 | 约 6,780 行 | 约 5,300 行 |
| 最终审查 | 2 严重 2 中 2 低 | 1 高 2 中高 1 中 3 低 |

第 2 次审查里，我核实了第 1 条和第 4 条的事实：

1. **会话令牌明文存在数据库里**（核实，`security.js` 的 `createSession` 把令牌原文当作 `sessions.id`，按原文查询）。spec §7 明确写了"服务端保存哈希"，而验收没有测这一点。数据库一旦泄露就能重放令牌接管账号，这是真正的安全问题。第 1 次没有这个问题，A 也没有。
2. 取消不中止在途的模型调用：**两次都有**，A 没有。
3. 自己加的"导入网页"功能，重定向可以绕过 SSRF 检查（未核实）。B 第 1 次也加了同类功能。
4. 重试没有归属检查：**不算缺陷**。api.yaml 没有对 retry 限制角色，审查员这条是自己的判断。
5. 没有记 `workspace.deleted` 审计、scrypt 而不是 argon2id、并发上限写死为 2：这三条测试都看不到，**两次里 argon2id 都出现了**。

### 两次合起来看

- **验收稳定**：两次都是 63/63（n=2）。用时波动很大（53.6 对 83.4 分钟），所以 A 比它们慢 2.2–3.5 倍。
- **漏掉的东西有固定的类别**：取消时不中止在途调用（2/2）、argon2id（2/2）、`workspace_id`（1/2）、会话令牌哈希（1/2）、测试模式放宽规则（1/2）。它们的共同点是：**黑盒测试看不到**，只有读 spec 或读代码才会发现。
- **所以前面"A 额外多出来的东西没有清晰的质量提升"这句话要收回一部分**：第 2 次出现了 A 没有的真正安全缺陷。更准确的说法是：A 的 spec 加阶段确实多买到了这一小块质量，但是代价很大；而这一小块里，有几项其实可以变成测试。

### 一个对 A 不利、之前漏掉的事实：网页链接

冻结的用户需求里写着"大家把各种资料（**网页链接**、PDF、笔记）丢进去"。模板的产品范围只有粘贴文本和上传 `.txt` / `.md` / `.pdf`，没有网页导入。结果是：

- A 的构建者忠实地按模板做了，**没有做网页导入，也没有在 `QUESTIONS.md` 里提出"需求提到了网页链接但模板没有"**；
- 不带 spec 的运行（B 一次、B + 测试两次，后来的 B3 也一样）**全都做了**网页导入；其中 B 和 B3 的 DNS 重绑定窗口我核实过，B + 测试第 2 次的重定向绕过未核实，第 1 次的没看。（这里原来写的是「4 次、各两次」，数错了，已更正：当时只有 3 次。）

两点含义：第一，A 在审查里没有 SSRF 问题，是因为它没做这个功能，不能算它的安全优势；第二，我们的 63 条验收只测模板自己的范围，**没有衡量"是否覆盖了用户需求"**，所以 A 在"完整度"这一项上其实输给了 B 一族。这是模板的缺口，不是 A 的构建者犯错：模板应该要么把网页导入作为功能写进去（带 SSRF 安全的设计和测试），要么明确要求构建者把"需求里有、模板里没有"的内容列在 `QUESTIONS.md`。网页导入正是"成熟产品一定会被问到、做错有安全后果"的那类知识，很适合放进模板的 `reference/`。

### 这一小块里，哪些可以变成测试

这些都不需要知道产品的内部结构，只需要验收套件能连到它自己建的那个测试数据库：

| 要求 | 怎么测 |
|---|---|
| 会话令牌、邀请令牌、重置令牌不得明文存库 | 登录后拿到 Cookie 里的令牌，导出数据库里所有文本列，断言原文不在其中 |
| 密码用 argon2id 或 bcrypt | 同样扫描数据库文本，断言存在 `$argon2id$` 或 `$2` 开头的哈希，且找不到明文密码 |
| 取消时要中止在途调用 | 假模型加大延迟，调用进行中取消，断言任务很快变为 `canceled` 且不再新增用量记录 |
