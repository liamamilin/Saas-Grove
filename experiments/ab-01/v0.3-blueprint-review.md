## 高：`real-budget.test.ts` 的固定输入 token 会冤枉合法实现

**文件:行号** `blueprint/acceptance/tests/s3/real-budget.test.ts:27`（`promptTokens: 500`）、`:50-51`（`spentUsd ≤ BUDGET_USD + EPS`）、`blueprint/acceptance/lib/helpers.ts:14`（`EPS = 1e-9`）

**问题**：假服务每次回复的输入 token 固定为 500，与产品实际发送的提示词无关；而 `EPS` 只有 1e-9，即最终 `spentUsd` 允许的超出量是 $0.000000001。输入单价 $1/百万 token，即**低估 1 个输入 token（$1e-6）在接近预算边界时就会失败**。

**为什么重要**：`spec/architecture.md:104` 只要求"输入估算 × 输入单价"，`§5.2:114` 只承诺假服务"对每次调用都用满 `max_tokens`"（只讲输出），**从未规定输入 = 500**。一个合法实现会用自己的分词器估算真实提示词（本题两篇短文档 + 问题，估 300–400 token 完全合理），并按 usage 记账。假服务按 500 收费，导致预留偏低、实际花费超出预算几角里（例如低估 200 token = $0.0002），被零容差断言判死。这属于测试隐式强加了一条契约里没有、构建者也无法推导的规则（"输入估算必须 ≥ 500"）。

**建议**：任选其一——(a) 在 `§5.2` 写明"假服务每次回复的 `prompt_tokens` 固定为 500"；(b) 让 mock 按请求 body 实际内容估算输入 token；(c) 放宽或删除第 50–51 行的 `spentUsd ≤ budget` 断言（`:19-23` 的 `problems` 检查已经能抓住"没有 max_tokens / 输出上限付不起"这两个目标缺陷，`spentUsd` 只是额外收紧）。

## 中：拒绝启动检查的 20 秒超时与守卫不对称，可被慢启动产品钻空

**文件:行号** `blueprint/acceptance/tests/s2/real-mode.test.ts:22`（守卫 `launch(complete, 90)`）vs `:42`（拒绝 `launch({...}, 20)`）；`blueprint/spec/architecture.md:112`（"进程退出，或者一直不健康，都算拒绝"）

**问题**：守卫给了 90 秒证明"完整配置能启动"，但拒绝检查只给 20 秒。`probe()` 把"超时未健康"和"进程退出"都归为 `healthy:false`（`run.mjs:162`），测试只看 `healthy === false`。于是**一个启动要 25–30 秒、且根本不校验缺失配置的产品**：守卫在 90 秒内通过（25 秒健康），拒绝检查在 20 秒处超时 → 被判"已拒绝"，白白通过全部 5 条拒绝断言。

**为什么重要**：这正是你要防的"空洞"——守卫只证明"能启动"，没证明"启动够快"，而 20 秒 < 90 秒 < 主进程的 300 秒（`architecture.md:142`），三者不对称，构建者只要在启动路径上睡 25 秒即可绕过"缺配置必须拒绝"的规则。契约说"一直不健康"，测试却只等 20 秒，二者矛盾。

**建议**：拒绝检查用与守卫相同（≥ 90 秒）或更长的 `startupTimeout`，使"没在同等窗口内健康"才等价于"拒绝启动"。
