# A/B 测试协议 v1.2（草案，v1.1 已过一轮独立审查；v1.2 的 §5 待复核，待用户批准）

用途：每个项目、每个品类都用这一套。ab-01 是试点（pilot），不是基线：各组契约版本不一致、A 只有 1 个样本、剔除测试用了事后规则。试点结论不能据此认定模板有效或无效。

本协议第一层只写**角色约束**，不写具体模型名、文件名或技术栈；这些在每轮的评测包里写明，随 tag 冻结。数字以 harness 的 `journal.jsonl` / `STATUS.md` 为准。

## 第一层：协议（跨项目不变）

### 1. 组与样本
- **对照 C**：简报 + 契约。**B+T**：契约 + 可运行验收。**A**：完整规格 + 阶段 + 验收。**A−阶段**（可选）。
- 每组 **n ≥ 3**，同一轮用同一版蓝图 tag 和同一版 harness tag。各组**交错执行**（不按组连续跑），避免 provider 负载随时间漂移。
- 每组事先固定最大轮数和墙钟上限。超时或没到 DONE 记为**未达到**，计入样本，不许换一次重跑。
- 主比较只比质量。用时另做小样本串行对照，不并入判定。

### 2. 角色与模型（角色约束；具体模型写在评测包）
- 构建者、审查员、缺陷核实员、测试裁决员、留出测试作者、模拟用户：**核实员与裁决员的模型家族必须与构建者不同**；两位作者家族互不相同，且都不与裁决员同家族。审查员与构建者同家族是已知局限（盲区相关），在每轮报告里注明。
- **流程作者**：模型家族须与构建者、裁决员都不同（构建的与验证的相互独立）。
- 免费模型只用于写留出测试和辅助活，不当构建者。

### 3. 冻结点（git tag，之后不改）
1. 评测包冻结（构建前）。2. 构建完成。3. 打分完成。
冻结后唯一允许的改动：第 4 条的盲审剔除，且必须同时报告剔除前和剔除后两套分数。

### 4. 测试有效性
- 一条测试只能断言它所引用的条款**明确写出**的内容。
- **准入**：每条留出测试在**空应用上失败**、在**参考实现上通过**（参考实现不得是被打分的产品）。
- 构建前，独立裁决员逐条对照条款检查，剔除不成立的。
- 构建后，只有同一裁决员能推翻某条测试，且只看「测试 + 条款 + 匿名失败响应和日志」，**不看代码，也不看有几个产品失败**。每次剔除都留记录。
- 不得用被打分产品的结果决定剔除哪条测试。

### 5. 指标与判定规则（先于数据写下）
**质量边界**：只评功能与形式质量，不评 AI 内容质量（见 README）。

**功能清单（分母）**：只从**每组都看得到的输入**生成——用户简报 + 契约（对照组看到的就是这两样，契约 api.yaml 已列出全部功能）。只出现在完整规格里的要求放进 spec 桶，只报告、不入判定。清单由独立 agent 起草；不再让各组各有分母，也不因某组没被告知就把功能从它的清单里拿掉（那正是模板价值的体现）。

**完整度流程**：对清单中每个功能写一条**脚本化界面流程**，通过与否只有两种结果（例如「报告页显示一条指向资料 X 的引用」），用假模型跑。流程只用**契约里写出的角色、文案和 testid** 定位元素，对所有构建者**不可见**；与留出测试同等对待：构建前写好；在空应用上必须失败，在参考实现上必须通过；冻结在评测包里。**没通过的一律算失败**：报错、超时、没跑（NOT RUN）、应用起不来。

**判定，三步，按顺序：**
1. **门槛**：必须通过探针，且完整度（流程通过率）≥ **80%**；有自带验收的组（B+T、A）还须通过自带验收，对照组 C 没有验收，以契约里的冒烟检查代替。没过门槛记「未达到」：计入样本，主指标按实际通过率计分，应用起不来的按 0 计。
2. **主指标**（两项须**同向**，且各自达到最小差距）：流程通过率差 ≥ **10 个百分点**（分母是流程条数）；留出测试 contract 桶通过率差 ≥ **5 个百分点**（分母是测试条数）；并且两组的范围不重叠。n=5 时规则不变。
3. **护栏**：经核实的高危/中危缺陷（所有组只审最终快照、同一提示、代码匿名、不同家族核实员复现）的中位数**更低或相等**——比 README 的「优于」略宽，README 已同步注明「缺陷项为不更差」。**只在过了门槛的产品之间比，每组至少 3 个过门槛的样本**，不足则判「不确定」。

只有三步都成立，才判形态 X 优于 Y。主比较事先指定：**B+T 对 C**（验收是否有价值）、**A 对 B+T**（完整规格 + 阶段是否有额外价值）；其余组只做描述。差距不够或两项不同向，判「不确定」，可补到 n=5，补跑规则：不看数据，直接补到 5，只补一次。打平选更简单、更便宜的形态。**不合成总分，不再加主指标。**

**描述性指标（报告，不入判定）**：spec 桶结果、模拟用户发现的阻塞问题、用时、花费、人工介入次数。用时不当指标：做得少的往往更快。

### 6. 卫生（由 harness 强制）
- 运行 id 不得复用；记录并发数；每个实验启动前写好预测文件，事后只填「实际」。
- 留出测试与可见验收做去重标注；流程与留出 contract 测试之间也做去重标注，同一功能在判定中不重复计分；打分时报告去重前和去重后两套。
- 免费作者写出过错误测试（`toBeVisible`、辅助函数自己断言状态码）——准入规则（第 4 条）为此而设。

## 第二层：每个项目一份评测包（目录形状固定）
`experiments/<项目>/pack/`：
- 简报、契约、验收；技术栈、模型版本、文件名写在 `pack/CONFIG.md`。
- `holdout/contract/`、`holdout/spec/`：两位不同家族的作者写；构建前经裁决员审过、通过准入、打 tag。
- `checklist.md` 与 `journeys/`：功能清单和对应的脚本化界面流程（见 §5）。
- `invariants/`：品类不变量探针（核心价值路径真的执行）。**探针在构建前用参考实现验证能过，再用人为植入缺陷的版本（空壳、整篇塞进提示词等）验证会失败**，不得用被打分的产品当正对照。
- `usersim/`：模拟用户脚本（假模型，见下方），逐步记录是否完成、是否阻塞、报错文字、困惑点；「阻塞」由不同家族的评判者盲判。
- 质量线（contract 桶失败数上限 + 探针全过 + 0 条已核实高危缺陷）在**第一个项目冻结时**写死；第二个项目单独建评测包，引用这条质量线，经济门表 `economics.md` 在第二个项目里填（总用时含模板适配 + 人工时间）。

## 模拟用户（已决定）
独立 agent 当用户去使用产品（只拿到产品地址和用户目标，不看代码、测试、契约），**产品内部的模型用假模型**；只评流程、阻塞、报错是否看得懂，不评内容质量。每产品跑 2 次，「阻塞」由不同家族的评判者盲判。不与 CLAUDE.md「验收永远用假模型」冲突。
