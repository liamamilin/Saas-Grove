# A/B 测试协议 v1（草案，待独立审查和用户批准）

用途：以后每个项目、每个品类都用这一套，不再为新项目重新设计。ab-01 是试点（pilot），不是基线：它的各组用了不同版本的契约，A 只有 1 个样本，剔除测试用的是事后规则。ab-01 的结论只作为试点发现。

## 第一层：协议（跨项目不变）

### 1. 组（按模板形态）
- **对照 C**：简报 + 契约（api.yaml、testability.md）。
- **B+T**：契约 + 可运行验收。
- **A**：完整规格 + 阶段 + 验收。
- **A−阶段**（可选）：完整规格，不分阶段，看速度。
- 每组 **n ≥ 3**；同一轮实验里，所有组用同一版蓝图（git tag）和同一版 harness（git tag）。

### 2. 固定角色与模型
- 构建者 `opencode-go/deepseek-v4.1-flash`；审查员 `opencode-go/deepseek-v4-pro`。
- 缺陷核实员和测试裁决员：**不同模型家族**（minimax-m3 或 glm-5.3），不与构建者、审查员同家族。
- 免费模型只用于写留出测试和辅助活，不当构建者（证据：results.md「免费模型当构建者」）。

### 3. 冻结点（每个打 git tag，之后不改）
1. **评测包冻结**：在任何一次构建之前。
2. 构建完成。
3. 打分完成。
冻结后唯一允许的改动：按第 4 条由裁决员盲审剔除测试。

### 4. 测试有效性（避免循环）
- 一条测试只能断言它所引用的条款**明确写出**的内容。
- 构建前：独立裁决员逐条对照条款检查全部留出测试，剔除不成立的。
- 构建后：只有同一裁决员能推翻某条测试，且**盲审**——产品改名 P1..Pn、隐藏所属组，同一裁决适用于所有产品。
- 不得用被打分的产品的结果去决定剔除哪条测试（ab-01 用 A、B4、B6a 做参照，是事后规则，不再使用）。

### 5. 指标与判定规则（先于数据写下）
主指标：
1. 留出测试失败数（冻结后的评测包）。
2. 经核实的高危/中危缺陷数：核实员能复现，或能指出代码行，才计入。
3. 品类不变量探针是否通过（核心价值路径真的执行，见第二层）。
4. 模拟用户体验中的阻塞问题数。
次指标：用时（只在串行运行间比较）、花费、人工介入次数。

判定：形态更丰富的组，要同时满足「留出测试失败数中位数更低」且「经核实缺陷数不更高」，才算赢；打平则选更简单、更便宜的形态。

### 6. 由 harness 强制的卫生
- 运行 id 不得复用（opencode 会话 id 由运行 id 派生，复用会接上旧会话）。
- 记录并发数；用时只在串行运行间比较。
- 每个实验在启动前写好预测文件，事后只填「实际」。

## 第二层：每个项目一份评测包（目录形状固定，内容因品类而异）
`experiments/<项目>/pack/`：
- `brief.md`、`contract/`、`acceptance/`（构建者可见的部分）。
- `holdout/contract/`、`holdout/spec/`：两个桶，由两位**不同家族**的作者用 `harness/holdout.mjs` 写；构建前经裁决员审过并打 tag。
- `invariants/`：品类不变量探针（例如 AI 研究助手：资料原文进模型请求、答案进报告、检索有选择性、追问带原文）。每个品类必须在构建前声明自己的探针。
- `usersim/`：模拟用户的脚本场景（固定脚本、真实模型、浏览器，每产品跑 2 次，逐步记录是否完成、是否阻塞、报错文字、困惑点）。
- `economics.md`：同品类第二个项目的经济门表（总用时含模板适配 + 人工时间，对照第一个项目）。
