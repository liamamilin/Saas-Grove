# nt-01：有模板 vs 没模板（草案，启动前等用户确认）

问题：认知模板到底有没有用。之前的 C/B+T/A 都带契约，比的是契约之上的附加物，不回答这个问题。

## 输入（两组相同，2026-10-21 按用户意见改）
一般人 vibe coding 只有一句模糊想法。输入就是这一句（取自 p2 简报头注释的 Idea 行），不给长简报。构建者提问或汇报时，由独立的用户模拟 agent（同一人设：懂产品运营、不懂后端的创业者）模糊地回答，不主动补技术要求；两组用同一人设、同一回答策略、同样的轮数上限。需要在 harness 里实现"构建者回合结束 → 用户模拟回答 → 下一回合"的循环（尚未实现）。

## 两组
- **N（无模板）**：只有想法 + 用户模拟 + 一份两组共有的**最小运行约定**（见下）。
- **T（模板包）**：想法 + 用户模拟 + 运行约定 + 要卖的那一套：契约（api.yaml + testability.md）、可执行验收（自带 75 条）、`product.md`（成熟产品定义与"容易做错的地方"）、`decisions.md`。不给 stages、landscape、reference、评测包。
- 构建者：`opencode-go/minimax-m3.1-flash-free`（用户 2026-10-21 指定）。审查员也是它。该模型比 deepseek 弱，结果不与 deepseek 轮的数字混用。无兜底（它自己就是兜底模型）；额度/不可用错误中断时续跑。
- n=3 每组，交错启动，并行，用时不比较。

## 最小运行约定（两组都给）
为了让评分能启动并使用任何产品，又不泄露认知：`PORT`、`DATABASE_URL`（空 Postgres）、模型走 OpenAI 兼容接口 `MODEL_BASE_URL`/`MODEL_API_KEY`/`MODEL_NAME`（评分时指向我们的假模型服务）、`npm install && npm run build && npm start` 启动、README 写明怎么用。不规定路径、testid、错误码、测试钩子。T 组另外有契约，那个契约要求的东西 N 组不知道。

## 评分：成熟度清单
- 30–40 条二值条目，来自 `product.md`/架构 §4 的认知和简报本身的要求，用行为描述，不出现路径和 testid。样例：跨工作区读不到别人的资料；预算用完后访客得到兜底而不是报错；库里没有明文会话令牌；登录失败多次被限流；知识库没有答案时不编造；中文资料能被检索；上传坏文件给出失败原因。
- 评判者：与构建者不同家族（Claude 子代理），读产品自己的 README，用接口和界面实际操作，每条 PASS 附证据（请求/响应或数据库行）；UNKNOWN=失败；分母固定。不给它看 blueprint 和简报之外的东西。
- 录入规则：每条在参考实现 P2-REF 上必须通过、在空应用上必须失败；清单经独立 agent 审查，打 tag 冻结，之后不改。
- 局限：T 组产品会长得像契约，评判者无法完全盲；评判者是 LLM，有噪声（对 REF 重复评判两次测一致率）；假模型下只量形式质量。

## 判定（事先写定）
- 清单通过率中位数 T 比 N 高 ≥15pp，且区间不重叠 → "模板有用"，解锁批量生成。
- 差 5–15pp 或区间重叠 → 不确定，补到 n=5 一次。
- <5pp 或 N 更好 → 认知模板在这类项目上没有可测价值，回头重想。
- 防守：核实后的高/中危缺陷中位数 T 不高于 N。
- 不合成总分。

清单条目带来源标签（idea / category / template-only），分别报告通过率；T 只赢在 template-only 条目上则领先打折扣。
