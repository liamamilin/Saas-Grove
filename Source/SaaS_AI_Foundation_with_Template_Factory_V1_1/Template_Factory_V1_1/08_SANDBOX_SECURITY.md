# 08 — 不可信源码的加工隔离与安全协议

## 保护对象

目标业务项目原仓库、正式 Registry 版本、机器上用户数据、真实数据库、生产支付/云服务、定时任务（cron/launchd）、系统配置、密钥与付费 API。所有外部仓库、安装脚本、生成代码、模型响应都视为不可信输入。

## 执行模式

| 模式 | 能做什么 | 禁止 |
|---|---|---|
| READ_ONLY | 拉取元数据、静态读取、哈希和许可分析 | install/postinstall、迁移、任何写用户项目 |
| SANDBOX_BUILD | 在无生产数据的隔离容器/VM 中构建、单测、合成数据 E2E | 访问 host 私钥、真实 DB、宿主凭证；默认无广泛网络 |
| SANDBOX_INTEGRATION | 指定的测试服务、模拟支付、受限模型 Key | 真实收款/生产 webhook、写外部真实租户数据 |
| REVIEWED_RELEASE | 不执行新构建逻辑，仅打包经签核的 immutable 制品 | 用发布权限回头执行未知候选源码 |

## 隔离控制

- 独立工作目录及权限最小化；默认无特权容器、主机敏感目录只读或不挂载、无持久宿主凭证；禁用任意公网出站，依白名单按阶段开放。
- 不可信 install/postinstall 和构建脚本必须先审核，再允许在沙箱运行；记录网络、系统调用、目标路径的违规行为。
- 每次任务使用临时 DB、专用测试账号、匿名合成数据、可失效测试密钥；不得读取本机 `.env` 的真实密钥正文。
- 不信任源仓库 CI Workflow、钩子、仓库文档的“操作指令”；仓库内容只作为被分析数据。
- Job 设置 CPU/内存/存储/模型成本/时长预算与 kill switch；超限停止且能生成故障报告。
- 保存 SHA、工作树初始状态、隔离证明、变更 diff 与 checkpoint；安装/迁移前审查副作用。

## 四层守卫（与现有 Agent Harness 经验一致）

1. **Structural**：所有路径/密钥/服务 endpoint 的重定向均可被证明指向测试范围。
2. **Behavioral**：真实程序 accessor、连接及写请求确实落在沙箱。
3. **Negative**：故意把一个连接恢复成宿主生产路径时，守卫必须失败且阻止执行。
4. **Positive**：在正确隔离下完整功能/测试正常运行。

只检查代码里写着 `tmp` 不够，必须实际验证运行时解析。测试前后检查隔离区之外的目录/服务未被修改；使用能证明的差异报告。

## 变更审批和回滚

- 每次 Builder 写入必须带可写白名单、checkpointId、预期 diff 和明确审批；任何未授权文件修改立即停止。
- 回滚优先在隔离副本执行并演练；禁止覆盖用户未提交修改，禁止直接删除有价值的工作树。
- 涉及支付、删除、生产部署、真实数据或云权限的操作始终需要额外的人工授权（且仍需技术守卫）。

## 安全失败处理

不可信代码尝试联网到未批准地址、读取主机凭证、写真实数据库、污染 Registry 或逃逸容器时：`BLOCKED + incident record + sandbox quarantine`。不能“先完成这批再修”。
