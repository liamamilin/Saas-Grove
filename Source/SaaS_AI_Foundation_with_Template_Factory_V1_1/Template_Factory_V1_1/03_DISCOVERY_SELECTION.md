# 03 — 候选发现、审计与选型标准

## 发现流程（默认只读）

1. 解析 Target：核心能力、业务领域、地域与架构限制。
2. 从官方仓库/登记来源检索至少一个可验证来源；同类若存在多个合理候选则做横向对比，不为了配额补凑。
3. 锁定每个候选：仓库 URL、commit/tag SHA、license 原文路径、发行与维护信息、部署说明；记录获取时间。
4. 静态检查：项目实际能力、关键路径、测试、依赖/资产许可证、漏洞公告、Upstream 活跃度、可能的未完成项。
5. 在允许的隔离环境中做受控安装/构建/测试（需额外批准）；只读阶段**不能执行第三方 install 脚本**。
6. 给出方案：`NATIVE` / `FORK` / `INTEGRATION` / `COMPOSE` / `BUILD_NEW` / `ABANDON`。

## 硬门优先，评分其次

先排除**无法按预期商业使用**、存在不可接受的安全缺陷且无隔离缓解方案、无法合法再分发素材、核心能力不存在或证据无法确认的候选。许可证争议只能标 `REVIEW_REQUIRED`，不能自动批准。GPL/AGPL/SSPL/BSL/自定义条款进行使用方式相关评估，不一概假定不可使用，也不能假定可以闭源复制。

对通过初筛的候选做透明的、可配置权重评分：业务覆盖、架构适配、质量与测试、维护可持续性、改造成本、依赖/地域成本。**评分是选型辅助，不抵消硬门，也不证明实际成功。** 缺失数据必须记录置信度或 UNKNOWN，不伪造评分依据。

## SelectionDecision 所需内容

`targetId`、候选列表（含拒绝理由）、最佳方案与替代方案、source SHAs、许可证结论/未决项、保留/移植范围、需新增能力、TCO 估算方法与不确定性、核心风险、审批人、日期、决策状态。

## 多源组合的特殊规则

- 先确认每个代码片段、设计资产与依赖的使用和再分发条件，再合并或链接。
- Provenance 追踪到文件/包；保持作者 Notice，记录改造 diff。
- 同名能力/数据结构冲突时确定一个权威契约，不能悄悄拼接不同项目数据库。
- 更换核心来源必须重新评估测试、许可、性能、上游升级路径。

## 不合理选择示例

只凭 GitHub Stars 高、README 写有“production-ready”、MIT badge、演示界面精美，就认定某个 CRM 是合格的可销售模板；这是不允许的。至少需要来源/代码级验证与对应环境的真实测试证据。
