# 02 — 产品线与功能范围

## 1. 四条产品线：交付类型不混淆

| 产品线 | 基本单位 | 交付内容 | 不等于 |
|---|---|---|---|
| L1 SaaS Core | `module` | 安装说明、接口、代码、测试、运维说明 | 简单第三方 SDK 再导出 |
| L2 Business SaaS | `template` / `integration` + `prototype-resource[0..N]` | 完整业务应用骨架、业务模型与可选多原型 | 单个页面截图 |
| L3 AI Native | `template` + `prototype-resource[0..N]` | 完整 AI 产品流程、计费、后台任务及可选多原型 | API Hello World |
| L4 SaaS + AI | `module` + `adapter` + `reference` | 通用 AI 能力及特定 SaaS 适配范例 | 复制 N 套 AI Chat |

## 2. L1 — SaaS Core 模块清单

- P0：统一 Billing（订单、支付、权益、用量、账本）；Stripe / 支付宝 / 微信支付适配；认证与基础组织边界；RBAC/资源权限边界；后台任务；运营后台最小闭环；错误与审计记录。
- P1：文件存储（本地、S3 兼容、国内 OSS）；站内/邮件/短信通知；国际化；Webhooks；标准 CRUD/列表与筛选；后台数据导出。
- P2：高级财务对账、发票/税务集成、高级促销/优惠券、复杂审批、多地区部署。

**P0 并不意味着同时实现所有供应商的全部功能。** 必须针对每个渠道/业务场景声明支持矩阵，如一次性付费、退款、订阅、支付平台限制；不支持则显式拒绝。

## 3. L2 — Business SaaS 模板库

优先研究而不是默认重写：

| 类别 | 首个完整场景 | 必备业务模型/流程 | 初始形态 |
|---|---|---|---|
| 项目管理 | 项目→任务→状态→看板 | 项目、成员、任务、活动、权限 | Native 或开源 Fork 评估 |
| CRM | 客户→商机→跟进 | 客户、联系人、机会、活动 | Fork / Integration 优先评估 |
| 知识库 | 文档→空间→权限→版本 | 文档、空间、权限、修订 | Native / Integration |
| 工单系统 | 提单→分派→处理→解决 | 工单、优先级、SLA、评论 | Integration 优先评估 |
| CMS/电商/教育 | 暂不锁定 | 由资产成熟度和真实需求决定 | Research backlog |

**原型资源关系：** 一个 Business SaaS Template 可关联 0..N 个 `Prototype Resource`；例如 CRM 可选「企业表格型」「销售看板型」「移动优先型」。同一业务能力契约下允许不同页面信息架构及交互流程。原型资源不是独立的第五产品线；单个原型不等于业务 SaaS 模板。具体规范见 [`12_PROTOTYPE_RESOURCE_SPEC.md`](12_PROTOTYPE_RESOURCE_SPEC.md)。

三种交付形态：

- **Native Template**：直接建立在我们的 SaaS Core 上，便于强模块组合。
- **Fork Template**：合规改造成熟开源产品，许可证、分发方式、维护成本独立核查。
- **Integration Template**：原业务系统保留独立服务，统一接入 AI/支付等能力，避免强行移植技术栈。

## 4. L3 — AI Native 应用模板库

| 类别 | 完整闭环 | 首批级别 |
|---|---|---|
| Chat | 会话、模型、流式响应、历史、限额、审计 | P0 |
| Workflow | 输入→阶段执行→进度/重试→产物 | P0（首个 AI Native 验证对象） |
| Generator | 输入→生成任务→文件产物→预览/下载 | P1 |
| Agent | 工具注册、审批、执行、失败恢复、日志 | P1 |
| Research | 检索、来源、主张、交叉验证、报告 | P1 |
| Knowledge | 导入、解析、索引、权限检索、引用 | P2 |

共同复用：模型提供商适配、调用记录、费用/额度、作业状态、产物生命周期、错误恢复、用户/租户上下文。

**AI Native 同样适用原型资源模型：** 如 AI Workflow App 可有「向导型」「画布型」或「任务列表型」原型，必须声明所需的工作流/产物能力；不因替换原型而强制改写工作流执行核心。

## 5. L4 — SaaS + AI 功能模块库

| 模块 | 复用核心 | 业务适配内容 | 优先级 |
|---|---|---|---|
| AI Copilot | Chat UI、对话、工具调用、确认 | 页面上下文、动作、权限 | P0 |
| AI Search | 查询、召回、引用 UI | 数据源、索引策略、ACL | P1 |
| AI Analytics | 意图→查询/分析→可解释结果 | 指标语义层、数据权限 | P1 |
| AI Automation | 触发→推理→任务执行→审计 | 事件源、可执行动作 | P1 |
| AI Agent | Agent runtime、工具/审批/轨迹 | 领域工具、状态与授权 | P1 |

规则：每个模块必须提供 `core + adapter contract + reference integration`。首个 AI Copilot 至少在一个 next-forge 示例及一个不同业务边界的示例中可用；后续有条件时再验证跨技术栈。

## 6. 核心使用旅程

**新建产品**：需求→选择应用模板→选择兼容原型（可选；若存在多个则展示差异）→许可/依赖提示→能力绑定验证→配置→初始化→运行测试→部署说明。

**已有 SaaS 加 AI**：扫描架构→选择 AI 模块→生成业务 adapter→授权检查→沙箱演练→人工批准→灰度启用→审计。

**升级**：冻结当前版本→生成影响报告→迁移预览→测试→灰度→回滚。

## 7. V1 目标与排除

**规划 V1.0 覆盖所有四库的设计；商业首发 GA 不必覆盖所有四库的全部条目。**

建议首个可销售版本至少：稳定 SaaS Core；一个完整 AI Native Workflow 模板；一个 SaaS + AI Copilot 模块及两个验证集成；一个可运行的基础业务模板及其**至少两个完成真实能力绑定与回归验证的原型变体**；文档、安装、升级、许可与支持体系。其他模板可先交付一个原型；不要求第一版为每类模板提供多种 UI。是否把中国支付三渠道都作为 GA 硬条件，待 Phase 0 审计和商户资质可得性确认后冻结。
