# 06 — 开源、品牌与商业许可策略

## 1. 许可战略

目标是**拥有独立商业品牌并能合法商业发布**，不是消除上游作者的版权归属。

- 默认优先选择 MIT、Apache-2.0、BSD 等相对宽松的授权，但仍要遵守具体文件/项目的条款。
- 严格区分：源代码许可证、**原型/设计资源许可证（Figma 设计稿、组件库、图标、插画、字体、布局素材）**、商标、商用 API/云服务条款、模型服务条款、数据授权。
- AGPL/GPL/SSPL/BSL/自定义 Source Available 项目应进入特别审查，不直接复制到闭源发行包。
- 具体义务依「使用方式、修改、组合、分发、网络服务」不同而异；涉及复杂 copyleft 必须由律师或专业合规人员复核。

## 2. next-forge 现状

来源：`https://github.com/vercel/next-forge`；仓库根 `license.md` 为 MIT，标注 `Copyright (c) 2025 Vercel`，允许复制、修改、销售、再许可等，但要求在软件副本或实质部分保留版权与许可声明。

**未完成事项**：固定 SHA；扫描整个依赖树（包含间接依赖）；核查品牌资产、插图、字体、模板内容、演示数据；识别私有商业集成及其服务条款。

## 3. 更名原则

- 产品名称、Logo、UI、域名、营销表达使用我们自己的品牌。
- 保留第三方的授权声明和必要 NOTICE；避免让用户误以为本产品由 Vercel 或其他上游官方支持。
- 对外文档可说明「基于 / 使用部分开源组件」并列出来源，不冒用商标授权。
- `LICENSE` 管我们自行版权材料；`THIRD_PARTY_NOTICES.md` 或许可证清单保留第三方义务；不能只删上游 LICENSE 后换上新名字。

## 4. 资产登记要求

每个引入资产至少记录：

`name | upstream URL | commit/tag | SPDX/license text | author/copyright | usage type (vendored/dependency/API/reference) | files reused | modification notes | redistribution obligation | trademark/assets | security status | reviewer | date`

不能靠 GitHub 页面顶部单一的 License 标记替代检查：部分仓库子目录、图片、字体、示例或 Enterprise 组件另有许可。

## 5. 许可证检查发布门禁

- [ ] 产生源代码 SBOM / 依赖锁文件；审查高风险直接和传递依赖。
- [ ] 对 vendored 代码检查文件级许可证与版权标记。
- [ ] 生成并随发行包携带第三方通知及必需许可证全文。
- [ ] 核查收费版是否违反上游禁止品牌更换或商业再销售的特殊条款。
- [ ] 检查图标、图片、字体、示例数据、模型权重和 Prompt 素材的授权。
- [ ] 原型资源逐项登记设计文件来源、UI 套件许可证、可修改/可重新分发范围、作者署名及演示数据授权；设计工具访问权限不等于可再销售授权。
- [ ] 检查外部 API 的付费、限流、地域、日志/训练政策。
- [ ] 记录合规责任人与未解决项；硬风险未关闭不得发行。

## 6. 业务模板的三条路线

1. **Native**：自产业务代码，依照引用库的条款履行义务；最容易控制许可证。
2. **Fork**：必须先逐项核对许可证与上游升级方式；对 AGPL、定制许可等作单独决定。
3. **Integration**：保持外部程序独立，通过 API/SDK/MCP 接入；不等于天然规避一切合同和许可义务，仍需核查。

## 7. 原型资源与衍生设计

原型即使不含可执行代码，也可能涉及独立版权、商标与素材许可。来自第三方的原型模板、截图、字体、组件库和设计系统，必须按实际复用文件记录来源与再分发权限。禁止凭“网上可见”“可下载”或“已购买使用权”认定可以纳入我们闭源商业模板包；使用受限时可只保留外部链接或自己重做设计，不打包受限资产。

## 8. 合规报告结构

`OSS_AUDIT.md` 至少含：资产清单、发现项、许可结论、需保留声明、商业服务依赖、修复动作、阻断项、证据链接、审阅人、审阅日期。

未取得证据时状态为 `UNKNOWN`，绝不能自动写为 `PASS`。

## 9. 法律提醒

本文为产品工程合规要求，不是正式法律意见。正式对外销售、重新分发含第三方代码的产品之前，应由合适的法务/专业人员复核相关义务。
