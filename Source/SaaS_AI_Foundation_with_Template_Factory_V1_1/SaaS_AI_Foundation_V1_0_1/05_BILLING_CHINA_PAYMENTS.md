# 05 — 计费与中国支付设计

## 1. 核心决策

**不要把 Stripe/支付宝/微信支付并列成三个独立账本。** 使用统一的 Billing Domain，并为每家支付渠道建立 Provider Adapter。

Billing 不仅是 API 调用；必须包含订单、支付意图、状态机、Webhook、退款、权益发放、使用量、成本、对账，以及异常人工处理工具。

## 2. 数据实体（建议）

| 实体 | 作用 | 必要约束 |
|---|---|---|
| Product / Price | 产品、价格与币种 | 价格版本化，金额最小货币单位整数 |
| Order | 内部订单 | 唯一编号；状态不可由前端任意修改 |
| PaymentAttempt | 某一次渠道支付尝试 | provider/channel IDs，幂等键 |
| PaymentEvent | 已验签的渠道事件 | 唯一事件 ID，去重，原始事件审计 |
| Refund | 退款请求及结果 | 重试安全，累计退款≤可退金额 |
| Entitlement | 当前可用权益 | 唯一授予来源，变更可追溯 |
| UsageLedger | 模型/任务用量 | append-only，按租户/应用/模型归属 |
| BillingLedger | 扣费、充值、退款等业务账 | append-only；对账修正用补偿分录 |

## 3. 支付状态（内部状态建议）

`CREATED → PENDING → SUCCEEDED / FAILED / CANCELED`；成功后可产生 `REFUND_PENDING / PARTIAL_REFUNDED / REFUNDED` 的退款派生信息。

原则：**实际支付状态以可验证的服务端渠道事件或主动查询为准**。所有状态变化事务化并留审计；事件重复/乱序不得重复授予权益；未知渠道事件进入待核查队列。

## 4. 渠道矩阵（拟支持，非已实现）

| 渠道 | 首阶段关注能力 | 依赖 / 待验证 |
|---|---|---|
| Stripe | Checkout、Webhook、退款、订阅 | Stripe 账户、产品/区域适用性 |
| 支付宝 | 单次收款、查单、回调验签、退款 | 商户资质、具体 PC/H5/当面付场景 |
| 微信支付 | Native / JSAPI 等指定场景的收款、查单、回调、退款 | 商户号、AppID、域名、证书/公钥、场景申请 |

必须维护每项能力的真实 `supported / unavailable / pending-verification` 状态；不能因为 API 有文档就宣称商户已获相应能力。尤其不要将所有渠道的订阅/自动扣费当作统一默认功能。

## 5. Webhook 安全与幂等

1. 使用供应商指定的**原始请求体**和必要 header 进行验签。
2. 校验时间戳/Nonce/证书及响应规则；防重放。
3. 在数据库唯一键下记录渠道事件，不重复授予权益。
4. 成功事件→内部支付状态→权益发放在可恢复的事务/消息模式下处理。
5. 渠道回调丢失：通过主动查单/对账补偿；网络失败要能安全重试。
6. 退款失败、迟到成功、支付竞态等均具备人工处理路径。
7. 不把密钥、证书或原始敏感支付信息记入应用日志。

微信支付 APIv3 官方文档明确涉及请求签名、响应与回调验签、加密回调解密。相关接入场景还要求商户查单和成功回调；需按具体产品场景核对。

## 6. 验收用例（P0）

- [ ] 相同渠道事件重复投递 10 次，权益只发放 1 次。
- [ ] 签名错误、内容被篡改或时间戳异常：拒绝处理。
- [ ] 订单金额/币种/归属不一致：拒绝完成订单。
- [ ] 丢失回调后，经查单最终恢复一致状态。
- [ ] 同一订单多次创建支付意图：不会产生重复业务收费结果。
- [ ] 支付成功但权益发放失败：可恢复、可审计、不会重复发放。
- [ ] 原路/部分退款按渠道已声明能力正确处理。
- [ ] 关键支付流程在 sandbox/test mode 验证；真实商户支付另行审批且使用低金额受控测试。

## 7. 不应提前决定的事项

- 不提前承诺中国平台「周期自动扣费」能力与普遍可得性。
- 不将支付、AI token 用量和内部余额混成一张可任意改写的表。
- 不以 UI 显示支付成功作为正式履约依据。
- 不在尚无资质时编造支付全链路实测通过记录。
