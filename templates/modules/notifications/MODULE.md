# notifications 模块 · 必读（先看这一页）

**是什么**：站内通知（收件箱 + 未读数 + 已读）、通知偏好（分类 × 通道、摘要频率）、通知摘要（把一段时间的通知聚合成一条）。它是"业务事件 → 用户知情"的中枢：别的模块只说"发生了 X"，本模块负责"以什么形式、什么频率、送到谁、能不能关掉"。

**边界**：只管**站内**通知与**偏好/摘要编排**。邮件发送属 email-transactional，认证属 auth，成员权限属 workspaces-and-permissions，限流属 rate-limiting。

**8 个概念**（宿主在 `module-map.json` 里映射，路径由宿主定）：

| 概念 | 作用 |
|---|---|
| `notifications.list` | 收件箱列表（分页、倒序） |
| `notifications.unread-count` | 未读数 |
| `notifications.mark-read` | 标记已读（按 id 或全部） |
| `notifications.preferences.get` / `.update` | 读写偏好（分类 × 通道、摘要频率） |
| `notifications.announce` | 工作区公告派发（需发送权限） |
| `notifications.view-token` | 领取一次性查看令牌 |
| `notifications.view` | 凭令牌看未读快照（免登录） |

**最容易翻车的 6 条**

1. **幂等**：同一业务事件重试不能产生两条通知。派发必须带 `idempotencyKey`，重放返回同一个 `announcementId` 而不是再发一遍。
2. **隔离**：列表、未读数、标记已读都只作用于"当前用户的"通知；他人或不存在的 id 一律 404，且响应体完全一致（403 会泄露存在性）。
3. **偏好要在派发时生效**：关掉 email 之后连通知都不该生成，而不是先生成再不发（邮箱仍在库里，关闭等于没关）。
4. **令牌只存哈希**：明文只在签发时返回一次；用完即废、过期即废，且"不存在/已用/过期"三种失败必须给一模一样的响应。
5. **未读数必须与列表一致**：同一过滤条件下 `unread` 等于列表里未读条数，否则角标和点进去的条数对不上。
6. **客户端 IP 取 `X-Forwarded-For` 最右侧的非受信跳**，绝不取最左值——否则改一个头就能无限发公告。

**验收怎么跑**：见 `acceptance-plan.md`，只依赖 HOST.md 的钩子与 `module-map.json`。

## 这个模块是什么

通知不是"发个邮件"，而是一条**可寻址、可去重、可退订、可回顾**的信息投递链：某个事件（有人评论了你的文档、账单已支付、任务即将超时）被翻译成一条有分类、有正文、有落地链接的通知，投给**当时该收到它的人**，落到收件箱里；用户可以看未读、标记已读、按分类关掉某些通道、或者选择"别一条条发，攒成摘要给我"。

三个子域：**收件箱**（投递的落点与已读状态）、**偏好**（用户对投递方式与频率的控制权）、**摘要**（把高频噪声压成一条）。三者互相咬合：偏好决定派发产生什么，摘要决定未读怎么被消费，未读数是用户对系统最直接的一次投票。

成熟与否不看功能多少，看**边界是否守得住**：通知是全站最容易被横向越权读取的资源之一（里面天然含"谁在什么时间做了什么"），也最容易因重试而重复骚扰用户。

## 成熟版应该有什么（按 MVP → 成熟分层）

### MVP（没有它就不能上线）
1. **站内通知落库 + 列表**：分页、倒序、字段稳定（`id/category/title/body/link/createdAt/readAt`）。
2. **未读数**：一个便宜接口，供顶栏角标轮询。
3. **标记已读**：按 id 批量与"全部已读"，幂等。
4. **派发入口**：任何模块都能推一条通知进来，必须能带幂等键。
5. **分类**：`announcement`（公告）、`system`（强制类）起步。
6. **基础偏好**：至少能关掉某分类的站内通知。
7. **统一错误体**：所有失败都是 JSON，带机器可读的 `error.code`。
8. **租户隔离**：通知只属于一个用户和一个工作区，跨工作区不可见。

### 成长（能被运营）
9. **偏好矩阵**：分类 × 通道（`inApp` / `email`）逐项开关 + 全局摘要频率（`off/daily/weekly`）。
10. **默认偏好**：新用户拿到的默认值必须明确（站内开、邮件关、摘要关）。
11. **强制分类**：`system`（安全、计费这类必须送达的）不可被用户关掉。
12. **邮件通道接入**：把公告与摘要交给 email-transactional 投递，模板名 `notifications.announcement` / `notifications.digest`，链接放 `data.link`。
13. **摘要**：按周期把未读聚合成一条，带条数 `count`，同一周期只生成一次。
14. **一次性查看令牌**：让收件人从邮件点进摘要页免登录查看，令牌一次性、短时效、只存哈希。
15. **保留期与清理**：通知不永久留存，过期自动不可见。
16. **分页界限与输入校验**：`limit`/`offset` 有界，`link` 只允许站内相对路径，正文有长度上限。
17. **派发限流**：防止一个人或一个脚本把全工作区刷屏。

### 成熟（能长期跑）
18. **并发幂等**：重复事件与并发重试都只产生一组通知（去重键 + 数据库唯一约束，不是靠应用层判断）。
19. **偏好原子性**：一次非法更新必须整体失败，不能改一半。
20. **失败语义统一**：不存在/他人/禁用账号三种情况的响应完全一致，枚举不出东西。
21. **数据生命周期联动**：账号删除时通知与偏好一并清除；导出请求覆盖通知内容。
22. **可观测**：派发量、投递失败率、未读总量、摘要聚合量进指标与日志（observability）。
23. **文案可治理**：通知正文走 internationalization，模板与分类分离。
24. **降级与成本治理**：大批量事件合并与限流，避免单次风暴（配合 usage-metering-and-budgets）。
25. **事件化分析**：通知点击、关闭偏好等行为进 analytics，而不是靠猜。

## 每项的正确行为

| 能力 | 正确行为 | 典型错法 |
|---|---|---|
| 列表 | 只含本人；`createdAt` 降序；同刻时次序稳定；`limit` 1..100 | 用 `id` 排序导致新通知排中间；`limit` 无上限被一次拉爆 |
| 未读数 | 与列表同口径，标记后立刻自减 | 缓存了计数不失效；与列表过滤条件不一致 |
| 标记已读 | 幂等，`readAt` 保留首次时间；只作用于本人 | 每次标记都刷新 `readAt`；`all=true` 顺手清了他人 |
| 派发 | 必须带幂等键；重放返回同一个 id 且不新增 | 靠前端去重；重试直接再插一条 |
| 权限 | 先过工作区权限再写库；不足一律 403 | 先写库再判权限；用 403/404 差异泄露工作区存在性 |
| 偏好 | 部分更新；非法更新整体失败；按用户隔离 | 覆盖式 PUT 把没提到的分类重置；失败时改了一半 |
| 偏好生效点 | 在**派发时**判断通道 | 落库后在发送时过滤，导致"关了还在库里" |
| 摘要 | 跨周期物化一条，带 `count`；同周期幂等；不改原通知已读状态 | 每次刷新都多一条摘要；摘要顺手把原通知标已读 |
| 摘要频率 | `off` 就不产摘要；空周期不产空摘要 | 默认给所有人发摘要邮件；无未读也发"本周无更新" |
| 一次性令牌 | 明文只返回一次；库中只存 sha-256；用/过期即废；失败响应一致 | 明文入库；可重放的"永久"令牌；三种失败给三种错误码 |
| 邮件通道 | opt-in；模板名 `notifications.<名>`；链接在 `data.link` | 默认给所有人发邮件；令牌存进自己的表 |
| 链接 | 只允许站内相对路径 | 允许 `javascript:`、`//evil.com` 造成开放重定向 |
| 限流 | 客户端 IP 取 XFF 最右侧非受信跳 | 取最左值，改头即绕过 |
| 错误体 | 固定 `{"error":{"code","message"}}` | 各路由各写各的，前端只能靠字符串猜 |

## 容易做错的地方（具体到会出什么事故）

1. **重试没有幂等键**：支付回调重试 3 次 → 用户收到 3 条"支付成功" → 客诉"重复扣款？"。
2. **按 id 取通知不做归属判定**：把 `id` 换成别人的 → 读到"谁在什么时候审了哪条" → 横向越权泄露，事故级别最高。
3. **他人资源返回 403、他人与不存在返回不同 message**：可枚举出"哪些通知 id 存在" → 摸清别人收件箱规模与活动规律。
4. **偏好在发送时过滤而不是派发时过滤**：用户关掉邮件后通知仍带着邮箱落库 → 投诉"我明明关了还在收"，等于没关。
5. **摘要把原通知标成已读**：角标清零 → 用户以为处理完了 → 实际没看 → 漏处理工单、漏审内容。
6. **未读数与列表不同步**：角标显示 3、点进去 0 条 → 用户不再相信角标，通知功能整体失效。
7. **令牌明文入库**：数据库泄露 = 全部通知内容与未读状态泄露，且能免登录访问摘要。
8. **令牌可重放或不过期**：邮件链接被转发或被爬虫抓到 → 攻击者长期读取他人收件箱概览。
9. **三种令牌失败给不同错误**：可判断"某个令牌是否曾经存在"，配合过期时间探测他人行为。
10. **XFF 取最左值**：攻击者每次换一个头 → 限流形同虚设 → 一天刷爆全工作区通知流。
11. **默认开邮件通道**：上线当天被投诉或标记垃圾邮件 → 发件域名信誉下降，后续邮件全进垃圾箱。
12. **只校验链接不校验长度**：超长正文进收件箱 → 客户端渲染卡死；塞进富文本渲染会造成存储型 XSS。
13. **跨工作区投递不隔离**：A 工作区公告出现在 B 工作区成员收件箱 → 跨租户泄露。
14. **关闭站内通知时顺手删历史**：用户"关掉提醒"后历史也没了 → 申诉"我的记录呢"；关闭只该影响之后的派发。
15. **并发下双写**：两个重试同时到达 → 两条通知同时生成 → 幂等只在串行下有效；要靠唯一约束 + 冲突转幂等重放。
16. **"从库里重算哈希"兼容旧令牌**：明文不可重算；正确做法是并行校验两套哈希，等旧令牌自然过期。

## 与其他模块的接口

| 模块 | 接口含义 |
|---|---|
| auth | 当前登录用户身份与会话有效性；账号状态影响通知可见性；账号删除事件触发本模块数据清除 |
| workspaces-and-permissions | 成员名单与角色决定公告收件人；"发送公告"权限的判定结果 |
| rate-limiting | 派发端点的限流键与 429 语义（客户端 IP 取最右侧非受信跳） |
| email-transactional | 公告/摘要的邮件投递（模板 `notifications.announcement` / `notifications.digest`，链接放 `data.link`，令牌放 `token`） |
| async-jobs | 摘要物化、过期通知与保留期清理的调度触发 |
| audit-and-data-export | 导出与删除请求的范围包含通知与偏好 |
| usage-metering-and-budgets | 若通知发送计入用量，节流与预算口径 |
| payments-billing | 支付成功/失败等业务事件触发站内通知 |
| feature-flags | 按开关决定某类通知是否派发 |
| observability | 派发量、投递失败率、未读总量等指标与日志 |
| analytics | 通知点击、偏好变更等行为事件 |
| internationalization | 通知标题与正文的文案来源 |

## 不做什么

- 不做邮件/短信/IM 的实际发送（属 email-transactional），只决定"要不要发、发什么模板、链接是啥"。
- 不做认证与会话（属 auth）。
- 不做成员、角色与工作区权限模型（属 workspaces-and-permissions）。
- 不做限流器的实现（属 rate-limiting），只声明本模块端点需要的限额与 IP 取法。
- 不做营销活动编排、用户分群、A/B 测试（属 analytics / feature-flags）。
- 不做 AI 文案生成与内容审核，不做实时推送通道（websocket 属可选增强）。
- 不做计费、配额与用量结算（属 usage-metering-and-budgets）。
- 不存附件与文件（属 file-storage），不做出站 webhook（属 webhooks-outbound）。
- 不承担其他模块的业务状态：本模块的分类与正文是"告知"，不含业务实体的读写真相。
