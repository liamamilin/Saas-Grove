# notifications 模块：需要人来拍板的决定

每条给出**推荐默认**与选别的后果。实现方可在契约允许范围内自选，但必须写进自己的文档。

## D-1 一次性令牌的用途与可见范围

- **推荐**：令牌只换取"未读数量 + 分类名"这一层快照（免登录），有效期 ≤24h、一次即废、只存 sha-256。
- **备选**：令牌换取完整通知正文/可点的落地链接。
- **后果**：选完整内容，邮件链接一泄露就是整箱通知内容泄露（还可能是别人的），邮件客户端的预取与日志记录会放大暴露面；选快照则泄露面小，但用户点邮件看不到细节，需要登录。

## D-2 摘要什么时候被物化

- **推荐**：谁先触发谁物化——调度任务（async-jobs）在周期末生成，或用户读列表时惰性生成；两条路都按 `(用户, 频率, 周期)` 幂等。
- **备选**：只靠调度任务生成。
- **后果**：只靠调度，宿主没跑调度器时摘要永远不会出现（验收会直接暴露）；只靠惰性，用户不打开收件箱就永远收不到摘要邮件。两者都做则实现更复杂，但行为可预期。

## D-3 摘要频率的默认值

- **推荐**：`off`（用户主动订阅才开）。
- **备选**：`weekly` 或 `daily`。
- **后果**：默认开 = 上线即向全量用户发邮件，容易被判垃圾邮件并伤及发件域名信誉；默认关 = 站内通知仍全量到达，代价是用户要自己开摘要。

## D-4 摘要是否替用户把原通知标记已读

- **推荐**：不标。原通知保持未读，摘要只是"换个方式告诉你有多少"。
- **备选**：摘要生成后把周期内未读自动标为已读。
- **后果**：自动标已读 = 角标清零，用户以为处理完了实际没看 → 漏审、漏处理工单；这是本模块最容易造成业务损失的一条。

## D-5 关闭某分类的站内通知，是"不生成"还是"不显示"

- **推荐**：**不生成**（派发时就不落库），但关闭前已存在的通知仍可见、可查。
- **备选**：照常落库、读取时过滤。
- **后果**：落库再过滤 = 通知内容与收件人邮箱仍留在库里，"关闭"名存实亡，隐私诉求落空；只拦新消息 = 历史不会凭空消失，用户申诉时无法自证。

## D-6 幂等键的作用域

- **推荐**：`(工作区, idempotencyKey)` 唯一，键由业务侧生成（建议用业务事件 id）。
- **备选**：全局唯一（跨工作区）。
- **后果**：全局唯一 = 两个工作区若碰巧用了同一个键（例如都用 `order-123`）会互相吞掉通知；作用域太大还会让去重键跨租户泄露事件结构。

## D-7 邮件通道默认开还是默认关

- **推荐**：默认关（opt-in），`email` 通道需用户显式打开。
- **备选**：公告类邮件默认开。
- **后果**：默认开 = 公告会外发到所有成员邮箱，退订与投诉成本高；默认关 = 需要在偏好页做好引导，否则公告只停留在站内。

## D-8 公告是否也发给发布者自己

- **推荐**：发（收件人 = 目标工作区全体成员，含发布者），实现与计数最简单。
- **备选**：排除发布者。
- **后果**：排除发布者 = 少一条噪音，但"收件人数"的定义、幂等重放与摘要计数都要多一个例外分支。

## D-9 通知保留期

- **推荐**：90 天；到期后不再出现在列表与未读数，并由清理任务删除。
- **备选**：永久保留，或 30 天。
- **后果**：永久保留 = 与个人数据删除请求长期冲突，库里长期堆着可定位到人的活动痕迹；30 天 = 用户回看"上个月谁审了我"时扑空。

## D-10 列表分页用 limit/offset 还是游标

- **推荐**：`limit`（1..100）+ `offset`，实现与验收都简单。
- **备选**：游标（keyset）。
- **后果**：offset 在高频写入下会漏读或重读（插入的行把行号挤走），游标稳定但要额外返回 `nextCursor`；通知量通常不大，先用 offset 更划算。
