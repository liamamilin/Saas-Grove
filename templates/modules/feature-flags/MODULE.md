# feature-flags 模块 · 认知模板

> 本文件讲"成熟版应该长成什么样"，不是实现指南。写码前先读必读摘要，再看 `contract.md` 与 `acceptance-plan.md`；宿主通用约定见 `../HOST.md`，本文不重复。

## 必读摘要（一页）

**定位**：feature-flags 拥有"这个行为现在开不开、给谁开、灰度到多少"的真相，把它收敛成一个任何调用方都得到同一答案的判定：给定 `(flag key, 主体, 工作区, 请求上下文)` → `值 + 命中来源`。判定是纯函数，只允许额外记一次曝光。

**唯一的决策顺序**（顺序错了必出事故）：`kill switch` → `租户覆盖` → `拒绝名单` → `允许名单` → `IP 规则` → `属性规则` → `灰度百分比` → `默认值`

**七条不可让步**

1. 灰度必须**确定性分桶**：`bucket = H(flagKey + 服务端盐 + 主体 id)`，同一主体永远落同一桶。禁止每次请求随机。
2. **提高百分比只能新增人群**，不能踢掉已命中的人；降低百分比是"回收"，要当危险操作记录。
3. **kill switch 必须在下一个求值请求就生效**，任何求值缓存都不许挡住它。
4. **租户覆盖只作用于它所属的工作区**；跨租户读和跨租户写都必须是 403。
5. 管理写操作要求**flag 管理权**（默认目标工作区 owner/admin）；普通成员 403；不同工作区互不串权。
6. 邀请令牌与服务令牌：服务端**只存哈希**，明文只在创建时返回一次，之后任何接口不再返回。
7. **枚举安全**：按邮箱 / 用户 id 触发的接口，在"存在 / 禁用 / 未验证 / 不存在"四种账号状态下，状态码与响应体必须完全一致。

**动手前自问三题**

- 客户端 IP 是不是取自 `X-Forwarded-For` 的**最左侧**？（是 → 可被伪造的漏洞）
- kill switch 是不是只把 `defaultValue` 改成 `false`？（是 → 白名单租户仍在使用已关停的功能）
- 谁能读到 rollout 盐、allow 名单里的邮箱？（能 → 灰度可被反推、可被绕过）

**边界**：只回答"开不开 / 用哪个值"。不回答"你是谁"（auth）、"你能不能做"（workspaces-and-permissions）、"这次曝光算什么"（analytics）、"怎么通知人"（email-transactional）、"审计存哪"（audit-and-data-export）。

## 这个模块是什么

一个**运行时的行为开关系统**，拥有三类状态：定义（flag 有什么、默认什么）、定向（谁命中）、覆盖（这个租户特殊对待）。三类调用方使用它：**服务端业务代码**（执行前问"这个行为开了吗"）、**服务端基础设施**（灰度新依赖、关停出问题的下游、给某租户临时开能力）、**客户端 UI**（决定渲染哪套界面；权威值必须来自服务端，客户端只做装饰性降级）。

成熟版要同时拥有四个操作面：**定义面**（谁可以定义/改）、**求值面**（读，快，可缓存）、**覆盖面**（租户级例外）、**紧急面**（kill switch，能一键止血）。

参考实现里值得保留的只有三点：默认关闭、未登录主体回落到默认值、definitions 只暴露元数据。必须丢掉的是：把判定外包给第三方 SaaS、把调试工具绑死在某个厂商密钥上、没有服务端权威与审计。

## 成熟版应该有什么（按 MVP → 成熟分层）

### MVP（缺了就不叫开关系统）

- **M1 Flag 定义**：`key`（稳定、不可改名）、`type`（`boolean|string|number|json`）、`defaultValue`、`description`、`status`（`draft|active|archived`）。
- **M2 服务端求值面**：`feature-flags.evaluate`，一次求多个 key，返回每个 key 的 `value / source / reason`。
- **M3 定向规则**：允许名单 / 拒绝名单（`user` 或 `workspace` 两种主体），条目用 id，不用邮箱。
- **M4 生命周期状态**：新建、启用、归档（归档不是删除）。
- **M5 写权限**：只有具备 flag 管理权的账号能改（默认工作区 owner/admin）；其他 403。
- **M6 definitions 元数据面**：给客户端与调试工具用，只给元数据，不给主体的值。

### 成熟版（在 MVP 之上逐层加固）

- **A1 灰度百分比**：确定性分桶、0% 全关 / 100% 全开、提高只增不减。
- **A2 租户覆盖**：按工作区指定值、可设过期、可删除、互不串扰。
- **A3 kill switch**：独立端点、必填原因、全局压倒一切、下一次求值即生效、可解除。
- **A4 作用域**：`workspace` 作用域按租户分桶（同租户成员结论一致），`user` 作用域按人分桶。
- **A5 IP / 属性规则**：IP 规则用 CIDR；属性规则只吃服务端权威属性（套餐、角色、权益）。
- **A6 邀请式租户开通**：管理员给一个工作区开 beta；令牌一次性、有 TTL、邮件投递、枚举安全。
- **A7 服务令牌**：服务端到服务端的求值凭据，哈希存储、只显示一次、可吊销。
- **A8 外部系统对接**：变更审计走 audit-and-data-export、曝光事件走 analytics、指标与日志走 observability（本模块只调接口，不自建审计表 / 曝光流水表）。
- **A9 未知 key 的宽容期**：客户端缓存了已归档 flag 时不能崩，按默认值回落。
- **A10 缓存与失效策略**：默认不缓存；一旦缓存，kill switch 必须旁路。

## 每项的正确行为

- **M1**：key 匹配 `[a-z0-9][a-z0-9._-]{0,63}`，创建后不可改；`defaultValue` 必须与 `type` 一致；重复 key 报冲突。
- **M2**：请求里的每个 key 恰好返回一条结果，值类型与 flag 类型一致，并带 `source` 说明命中哪一层；未知 key 整单失败，不返回半截结果。
- **M3**：名单条目用 id，不用邮箱；拒绝名单先于允许名单判定；名单内容不出现在 definitions 响应里。
- **M4**：`archived` 的 flag 仍可被求值，返回 `defaultValue` 且 `reason=archived`；对已归档 flag 写入报冲突；归档不是硬删除。
- **M5**：非本工作区成员、非管理员一律 403，错误信息不区分"不存在"与"无权限"。
- **M6**：definitions 只返回 key / type / default / description / scope / status / 可选值集合，不含主体结果、名单 id、rollout 盐、IP 规则、覆盖内容、邮箱。
- **A1**：百分比是 0..100 整数；0 全关、100 全开；同一主体重复求值结果一致；盐由服务端持有，客户端既不能写也不能读。
- **A2**：覆盖只作用于所属工作区；带 `expiresAt` 的覆盖到期自动失效；删除后立刻回到继承。
- **A3**：kill 激活后所有主体都拿到 kill 值（压过覆盖与名单）；必带非空原因；记录激活人与时间；解除后原定向恢复。
- **A4**：`workspace` 作用域下，同一工作区的不同成员求值结果必须相同。
- **A5**：IP 规则命中客户端 IP，客户端 IP 取 `X-Forwarded-For` 最右侧的非可信跳数；peer 不可信时整个头被忽略。
- **A6**：邀请请求对所有账号状态响应一致；只有启用且邮箱已验证的工作区成员收到邮件；令牌一次性、并发只成功一次、过期失效、库里只有哈希。
- **A7**：令牌明文只在创建响应里出现一次；列表只给元数据（id / name / createdAt / revokedAt）；库里只有哈希。
- **A8**：变更审计走 audit-and-data-export，曝光走 analytics，指标日志走 observability，本模块不建审计表与曝光流水。
- **A9**：客户端拿着过期 key 求值，得到"默认值 + archived 原因"，不是 500。
- **A10**：求值缓存 TTL 上限 30 秒；kill 激活后第一次求值就必须看到 kill 状态。

## 容易做错的地方（具体到会出什么事故）

- **灰度用 `Math.random()`** → 同一用户每次刷新都在开/关之间横跳，客服工单爆炸。
- **灰度桶用用户 id，但 flag 是租户级的** → 一个租户的几百个员工被当成几百个独立样本，50% 灰度实际变成"约一半员工可见"。
- **kill switch 只把 `defaultValue` 改成 false** → 已被 allow 名单和租户覆盖放行的用户**照旧使用**被关停的功能（最需要止血时的漏网场景）。
- **kill switch 生效有缓存延迟** → 事故期间流量继续冲向下游，止血无效。
- **租户覆盖存成用户 id，或用 `userId` 去比工作区** → A 租户的覆盖泄漏到 B 租户，或给单个员工开了"公司级"后门。
- **把 `X-Forwarded-For` 最左侧当客户端 IP** → 攻击者自己填 `X-Forwarded-For: 203.0.113.7` 就骗过 IP 规则、限流与审计溯源；peer 不可信却照单全收 XFF 同理。
- **definitions 带上了 allow 名单邮箱和 rollout 盐** → 灰度人群可被反推，盐泄露后可离线算出"谁在灰度里"。
- **客户端把"是不是 enterprise 套餐"当属性传上来** → 改一个请求参数就拿到高级功能；属性规则只吃服务端权威数据。
- **删除而不是归档 flag** → 客户端缓存里还留着旧 key，服务端突然 404/500，全量用户白屏。
- **轮换哈希密钥时重算并改写已存摘要** → 全量在途令牌瞬间失效，用户被反复登出；正确做法是双密钥并行校验，等旧令牌自然过期。
- **邀请令牌可重复使用** → 链接被转发或被抓包后，别人也能开通同一个租户的 beta。
- **邀请接口按账号状态返回不同结果** → 邮箱枚举接口，可批量拉用户库；过期令牌回 410 Gone、非法回 404 也等于告诉攻击者"这个令牌曾经有效"。
- **rollout 盐写死在代码里且随部署轮换** → 每次发版灰度人群整体重排，已命中用户被踢出灰度。
- **kill 状态可以用普通 update 接口改** → 没有原因、没有审计人，事故复盘查不到是谁关的。
- **把 flag 当配置中心用**（存 API 地址、阈值、模板文案）→ 两套变更流程混在一起；把秘密或 PII 写进 flag 的 value 则会被 definitions 发给浏览器。
- **求值接口顺带改状态**（顺手写覆盖、顺手建 flag）→ 重试一次就重复生效；求值必须是纯函数。

## 与其他模块的接口

| 模块 | 接口含义 |
| --- | --- |
| auth | 提供当前会话主体、账号状态（enabled / disabled、email 是否已验证）、用户 id 的解析 |
| workspaces-and-permissions | 提供工作区列表、成员资格、管理员能力判定；本模块的 403 依据来自这里 |
| analytics | 接收暴露事件（flag key、变体、主体、时间）；判定不由它负责 |
| audit-and-data-export | 接收 flag 定义 / 覆盖 / kill 的变更审计 |
| rate-limiting | 承载邀请申请等可枚举接口的限流计数 |
| email-transactional | 承载邀请邮件；模板名 `feature-flags.tenant_override_invite`，链接放 `data.link`，令牌放 `token` |
| observability | 接收求值失败率、kill 触发、灰度分布、令牌使用情况 |
| web-security | 提供浏览器请求的 Origin / CORS 策略来源，本模块据此拒绝跨站请求 |
| usage-metering-and-budgets、payments-billing、ai-model-gateway、ai-retrieval、async-jobs、notifications、webhooks-outbound、llm-observability-and-evals、prompt-injection-and-guardrails、file-storage、internationalization | 开关的消费者：只调 `feature-flags.evaluate`，本模块不感知其内部语义 |

## 不做什么

- 不做身份认证（auth）、不做授权判定（workspaces-and-permissions）。
- 不做限流实现（rate-limiting）、不做邮件发送（email-transactional）、不做审计存储（audit-and-data-export）、不做分析存储（analytics）。
- 不做实验统计与结论（"这个变体转化率更高"属于 analytics）。
- 不做通用配置中心 / KV：flag 是行为开关，不是配置存储。
- 不把秘密、PII、用户邮箱列表放进 flag 的 `value` / `description`。
- 不让浏览器本地计算权威值；客户端只做装饰性降级。
- 不做实时推送（websocket / SSE 广播）：客户端轮询 `definitions` 足够。
- 不做跨组织的 flag 交易市场，不做"按人数自动停灰度"这类自动决策。
- 不在求值路径上做任何写操作。
