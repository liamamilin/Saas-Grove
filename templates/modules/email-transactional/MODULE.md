# email-transactional（事务邮件）模块 · 认知模板

## 必读：一页速览

- **定位**：把"发一封邮件"做成一个可重试、可审计、不会误发、不会误退订、不会泄露令牌的子系统。它是**投递层**：谁要发、发什么由别的模块决定。
- **三件事必须分开**：① 内容（模板 + 变量契约）② 时机（入队、投递、重试、状态）③ 可达性（退订、退信抑制、投诉）。三者混在一起就会出事故。
- **最小可用（MVP）**：发送接口入队即返回 `202 + id`；模板名带模块前缀；变量在请求时校验；异步投递 + 有上限的重试；状态可查；退订令牌一次性、只存摘要；每收件人限流。
- **可用**：按类别的订阅（强制类 vs 可选类）；退信/投诉抑制名单（软退信不抑制）；退订链接 + 一次性确认 + 偏好页；幂等键；令牌 TTL 与过期清理；记录保留期与到期清除。
- **成熟**：模板注册表（`<模块>.<名>` 命名空间）；瞬时/永久失败分类 + 指数退避；抑制名单带原因、可人工解除；反馈回调签名 + 防重放；投递指标；灰度开关；模板本地化；发送量计量与预算拦截。
- **三条红线（最容易出事故）**：
  1. **同步发信**（在请求里等 provider 返回）→ provider 一抖动，业务接口一起超时；上游重试再叠一层，变成重试风暴。
  2. **GET 退订链接即消费令牌** → 邮件安全扫描器会预取链接，用户被动退订，收不到密码重置与安全通知。
  3. **强制类邮件也能退订/也会被抑制** → 用户退订后收不到安全通知，等于把账号交出去。
- **验收只信黑盒**：HTTP 状态码与错误体、`outbox` 测试钩子、测试时钟、限流清空钩子、数据库只读查询。契约里"看不见"的（代码结构、加密、耗时）一律不写成 MUST，放进 contract 的"建议，验收不测"。

## 1. 这个模块是什么

事务邮件 = 因某个已发生的业务事件而自动发出的邮件（欢迎、找回密码、订单确认、告警）。它的特征与营销邮件相反：**每封都有归属事件、都有时限、都会含一次性链接**。

本模块负责：模板注册与渲染、发送队列、投递重试与失败分类、provider 反馈（退信/投诉）处理、订阅与退订、发送限流、发送记录的生命周期。

本模块**不负责**：谁触发发送（由 auth、payments-billing、notifications 等模块触发）、邮件正文里的业务逻辑、账号与权限判定。

一条成熟的事务邮件链路长这样：

```
业务模块 ──▶ email.send（入队 202 + id）
                    │
                    ▼
              队列 → worker 渲染模板 → provider 投递
                                        │
              provider 反馈 ◀───────────┘（退信/投诉 → 抑制名单）
                                        │
              收件人点退订 ─▶ 一次性令牌 ─▶ 偏好变更（按类别）
```

## 2. 成熟版应该有什么（MVP → 可用 → 成熟）

| 层级 | 能力 | 合格线（外部可观察） |
|---|---|---|
| MVP | 入队即返回 | `POST` 发送返回 `202`，带 `id`、`status=queued`；业务请求不等待 provider |
| MVP | 模板命名空间 | 模板名形如 `<模块>.<名>`（`email-transactional.contact`），跨模块不撞名 |
| MVP | 变量契约 | 缺变量 / 多变量在**请求时**报错，不是在渲染时静默出错 |
| MVP | 异步投递与重试 | 投递失败自动重试，尝试次数有硬上限，不无限重试 |
| MVP | 状态可查 | 单封邮件可查状态：`queued/sent/failed`，含尝试次数与最近错误 |
| MVP | 退订令牌 | 单次使用；入库只存摘要；明文只在邮件内容与测试 `outbox` 出现 |
| MVP | 发送限流 | 同一收件地址在窗口内发送次数有上限，超限返回 `429` |
| 可用 | 订阅类别 | 强制类（安全/交易类）与可选类分开；强制类不可退订 |
| 可用 | 抑制名单 | 硬退信/投诉 → 该地址不再收信；软退信**不**抑制 |
| 可用 | 退订闭环 | 邮件内链接 + 一次性确认（可被 provider 一键 POST 调用）+ 偏好读取/修改 |
| 可用 | 幂等 | 同一个幂等键重复提交 → 同一个 `id`、只有一条记录；载荷不同 → 冲突报错 |
| 可用 | 时效治理 | 令牌 TTL、限流窗口、重试退避、保留期全部由同一个时钟驱动，可被测试推进 |
| 可用 | 保留与清除 | 到期记录被清除；删除请求（配合 audit-and-data-export）能清掉本模块的记录与偏好 |
| 成熟 | 模板注册表 | 模板与变量契约集中注册；宿主可扩展但命名空间与类别必须声明 |
| 成熟 | 失败分类 | 瞬时失败重试（退避），永久失败立即终态；失败原因有机器可读码 |
| 成熟 | 抑制可运维 | 抑制条目带原因与时间；支持人工解除；默认永久有效 |
| 成熟 | 反馈鉴权 | provider 回调必须带签名，防重放；类型非法直接拒绝 |
| 成熟 | 投递指标 | 按模板/类别统计 sent/failed/bounced/suppressed 与重试次数 |
| 成熟 | 灰度与预算 | 新模板、新发送策略可灰度；发送量计入预算，预算用尽则不入队 |
| 成熟 | 本地化 | 模板文案按 locale 取版本，变量契约不随语言变化 |

## 3. 每项的正确行为

- **入队**：`202` + `id` + `status=queued`。参数错误在入队前就被拒（`4xx`），此时不得留下任何记录。
- **模板**：名字必须是 `<模块>.<名>`；未知模板与变量不匹配要分得清错误码（未知模板 ≠ 缺变量 ≠ 多变量）。
- **变量**：模板声明的必需变量集合与实收集合**完全相等**；相等才入队。多一个键往往是把变量名拼错了，静默渲染成空字符串是最难查的故障。
- **状态机**：`queued → sent → bounced`、`queued → failed`、`queued → suppressed`，单调不回退。`suppressed` 表示从未投递过（尝试次数为 0）。
- **重试**：瞬时失败重试，退避间隔随次数增长且由测试时钟推进；尝试次数到上限即 `failed`，并且**不能**带 `sentAt`。永久失败（地址非法、模板渲染失败、provider 明确拒绝）一次都不重试。
- **反馈**：硬退信 → 该地址在非强制类别被抑制；投诉 → 所有类别被抑制；软退信 → 只记录不抑制。三者对"后续还能不能发"的影响完全不同。
- **退订**：令牌一次性；**GET 只展示确认页，不消费**（扫描器会预取）；真正生效靠一次性确认（POST）；只影响令牌指定的那一个类别；强制类永远处于订阅状态。
- **令牌**：不可预测（≥32 字符随机值），入库只存 SHA-256 十六进制摘要，明文不进任何业务表。
- **幂等**：同键同载荷 → 同 `id`、同一条记录；同键不同载荷 → `409`，不能静默覆盖。
- **限流**：每收件地址有上限（窗口内），超限 `429` + `Retry-After`；窗口随时钟推进而失效。
- **客户端 IP**：只采信来自可信代理的 `X-Forwarded-For`，并且取**最右侧的非可信跳**，绝不取最左项（最左项由客户端伪造）。
- **Origin**：浏览器发起的写接口校验 `Origin`；但 provider 的一键退订 POST 是机器调用，不能被同一规则拦掉。

## 4. 容易做错的地方（会出什么事故）

| 错误做法 | 事故 |
|---|---|
| 在请求里同步调 provider | provider 抖动 → 业务接口超时；上游重试叠加 → 重复发信 + 重试风暴 |
| GET 退订链接直接改状态 | 安全扫描器预取 → 用户被静默退订，收不到找回密码与安全通知 |
| 强制类邮件也带退订/也被抑制 | 用户退订后收不到安全通知 → 账号可被接管（找回密码形同虚设） |
| 令牌明文入库 | 数据库泄露 = 全量令牌可被直接使用（可退订、可重置） |
| 只存摘要还"重算旧摘要" | 老令牌全部失效、用户点旧邮件链接报"无效" |
| 软退信也抑制地址 | 用户偶发退信被永久拉黑 → 收不到任何通知 |
| 硬退信一刀切（含强制类） | 账号投递失败后连安全邮件都发不出 → 用户永久失联 |
| 取 `X-Forwarded-For` 最左项 | 攻击者伪造 IP 绕过每 IP 限流 → 垃圾邮件/轰炸 |
| 把 Origin 校验套到一键退订 POST | 退订链路全线失效（provider 不带 Origin） |
| 变量拼错静默渲染为空 | 用户收到"亲爱的 ，"这种空模板，客服查不出原因 |
| 没有幂等 | 上游超时重试 → 重复扣费、重复通知、重复建单 |
| 令牌比对不判时限 | 泄露的旧令牌长期可用；暴力猜测无上限 |
| `4xx` 也返回"已受理" | 监控显示发送量正常，实际一封都没发出去 |
| 模板名不带模块前缀 | 两个模块各出一个 `welcome` → 后注册覆盖先注册，收件人收到别的模块的文案 |
| 把"provider 接受"当成"已送达" | 退信率被当成 0，触达率虚高，问题被推迟到用户投诉 |
| 记录里存渲染后的正文/链接 | 个人数据与令牌扩散到备份、日志、分析表，删除时清不掉 |

## 5. 与其他模块的接口（只列模块名与接口含义）

| 模块 | 接口含义 |
|---|---|
| auth | 发送前的身份来源（会话/服务凭据）；认证类邮件由 auth 发起，模板命名空间 `auth.*` |
| workspaces-and-permissions | 收件人是工作区成员时，成员身份与角色由它判定；本模块只负责投递 |
| usage-metering-and-budgets | 每次入队计一次发送量；预算不足时不得入队 |
| async-jobs | 队列、worker、重试调度由它承载；本模块只定义投递语义与状态流转 |
| notifications | 跨渠道分发由它决定；邮件偏好以本模块为准 |
| rate-limiting | 账号/IP 维度的通用限流在它那里；本模块只做每收件人/每客户端 IP 的发送上限 |
| web-security | CSRF/Origin 规则、代理信任链、`X-Forwarded-For` 解析口径由它定 |
| audit-and-data-export | 邮件记录（收件人、模板、时间）属于可导出、可删除的个人数据 |
| observability | 投递成功率、重试次数、抑制数量作为指标与告警信号 |
| feature-flags | 新模板、新发送策略的灰度开关 |
| internationalization | 模板文案的多语言版本与 locale 选择 |
| payments-billing | 发票/订阅类邮件由它发起，本模块只投递 |

## 6. 不做什么

- 不做营销群发、受众名单、分群、AB 发送。
- 不做站内通知、推送、短信（属于 notifications）。
- 不做模板可视化编辑器与拖拽设计器。
- 不做打开/点击像素与行为分析（属于 analytics）。
- 不做 SPF/DKIM/DMARC 的 DNS 配置与送达率运营。
- 不做账号、会话、登录、权限判定（属于 auth 与 workspaces-and-permissions）。
- 不做附件存储与文件下载（属于 file-storage）。
- 不做发票、订阅、支付（属于 payments-billing）。
- 不保证真实送达：第三方 provider 一律用假实现，模块只保证"按规则投递并记录结果"。
- 不追求 UI 美观与邮件视觉设计。
