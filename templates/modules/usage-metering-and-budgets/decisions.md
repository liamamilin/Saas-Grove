# usage-metering-and-budgets — 决策点

下面的"推荐默认"已写进 `contract.md` 的 MUST 规则。改默认值等于改契约，必须同步改契约与 `acceptance-plan.md` 的用例。

| # | 决策点 | 推荐默认 | 选别的会怎样 |
|---|---|---|---|
| D1 | 超预算时 `usage.record` 是否拒绝 | 不拒绝：永远 201 入库，只把 `over_budget` 置真；硬停只作用在 `budget.reserve` | 若拒绝：已真实发生的用量被丢弃 → 少收钱、无法对账、事后无凭据；若闸门之外无人拦截 → 上限形同虚设，客户直连 API 绕过 |
| D2 | 月窗口用哪个时区 | 租户计费时区，默认 `UTC`，按 IANA 换算 | 用服务器本地时区：边界随部署环境漂移，月初用量错月；固定 UTC 偏移：夏令时地区少/多一小时 |
| D3 | 支持哪些预算周期 | 只支持自然月；周/滚动 30 天等自定义周期暂不做 | 每多一种周期，已用金额、阈值锁存、幂等、对账都要多一个维度键，账单侧也要同步改，复杂度线性上升 |
| D4 | 预留是否占用额度、TTL 多长 | 占用额度；TTL 5 分钟（界限 30..86400 秒），超时自动释放 | 不占用额度：并发必然超支；TTL 太短：模型调用慢于 TTL 时额度被释放两次，等于白送额度；TTL 太长：崩溃请求长期占死额度 |
| D5 | 幂等键的作用域与保留期 | 作用域 (租户, 键)，保留 ≥24 小时 | 全局作用域：不同租户撞键 → 互相拒绝服务或串号；保留太短：客户端隔天重试（常见 24h+）→ 重复扣费 |
| D6 | 要不要"一次性放行"机制 | 要：管理员签发、一次性、有 TTL、只存哈希、错误响应统一 | 不要：超支只能改预算，而改预算影响整个窗口且没有审计痕迹；客服只能求改额度 |
| D7 | 计量密钥的明文与轮换 | 明文只在签发那一次返回；只存哈希；列举只显示前缀与末 4 位；轮换走新旧双密钥并行 | 明文可回读：一次泄漏即长期泄漏；轮换立刻废旧密钥：老客户端批量报错；用新密钥重算旧密钥摘要：旧凭据不可验证（不要这么做） |
| D8 | 阈值通知的粒度与是否锁存 | 每窗口每阈值只发一次（锁存）；阈值是 limit 的整数百分比 | 每笔都发：通知轰炸，用户关掉全部邮件，连硬停告警也收不到；不锁存：用量抖动时同一问题反复告警 |
| D9 | 未知资源类型怎么处理 | 400 拒绝上报，绝不按 0 价记账 | 静默 0 价：新业务线用量全部漏收，且没有任何告警，直到对账才发现 |
| D10 | 迟到事件（已关闭窗口）怎么办 | 按 `occurred_at` 归入历史窗口并计入该窗口已用金额，不拒绝 | 拒绝入库：上报延迟即丢数据；归入当前窗口：账单与真实用量对不上，客户看到"这个月突然多了一截" |
| D11 | 幂等重放返回什么状态码 | 200 + 同一个 `event_id`（不是 201，也不报错） | 返回 201：客户端当成新建，可能再触发一次下游副作用；返回 409：正常重试被当成错误，客户端会放弃或告警 |
| D12 | 放行令牌明文投递渠道 | 只走 outbox 邮件（模板 `usage-metering-and-budgets.allowance_grant`），HTTP 响应不含明文 | 把长期凭据放进管理 API 响应：网关与日志可能记录；只走邮件：客户自助换密钥做不到（密钥明文仍只在签发响应） |
| D13 | 跨源写请求的检查放哪 | 本模块自己保证：涉钱写接口拒绝外域 `Origin`（通用 CSRF/CORS 归 `web-security`） | 完全依赖 `web-security`：宿主若没实现该模块，跨站 POST 可直接写用量与改预算 |
| D14 | 币种能否切换 | 租户级固定，同一窗口内不可切换 | 窗口中途切换：同一笔金额含义改变，客户看到"同价不同数"，账单无法解释；跨币种汇总需要 `payments-billing` 统一汇率来源 |
