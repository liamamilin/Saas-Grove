# analytics · 认知模板（产品分析：事件 / 漏斗 / 隐私同意）

## 0. 一页速读（必读）

**是什么**：把"用户在产品里做了什么"记成可查询的结构化事件，回答三个问题——多少人卡在某一步流失、改版后转化有没有变、某个人的数据能不能被彻底删掉。

**三块能力**：① 采集 ingest ② 查询 aggregate + funnel ③ 同意 consent 与删除 purge。

**最小可用形态（能上线且不出事）**
- 事件 schema 固定：name / actor / anonymousId / occurredAt / properties
- 存储只存摘要：actor、anonymousId、token、IP 都不落明文
- 同意默认拒绝（deny by default），判定发生在**写库之前**
- 撤回同意 = 撤销 + 删数据（有界时间内可验证）
- 每条查询按 workspace 隔离，跨租户不可见
- 事件名/属性有白名单形状，客户端入口校验 Origin

**六个最常见的坑**（细节见 §4）
1. 把 email/用户名塞进 event properties → 变成无授权的个人数据仓库
2. 同意做成"弹过窗就算" → 法律上无效同意
3. 撤回只改标志不删数据 → 删除承诺落空
4. 代理后面取 X-Forwarded-For 最左边 → 所有用户被算成同一个 IP
5. 漏斗按事件数而不是按人去重 → 转化率虚高
6. 客户端采集端不校验 Origin → 被任意站点灌入事件

**边界**：图表与仪表盘属前端；实验显著性属 feature-flags；用户画像与推荐不在本模块；导出与删除请求属 audit-and-data-export。

**文件顺序**：本文件（心智模型）→ contract.md（机器可验收的契约）→ acceptance-plan.md（黑盒用例）→ decisions.md（需要人拍板的点）。

## 1. 这个模块是什么

**职责边界**

| 做 | 不做 |
|---|---|
| 采集产品事件、聚合计数、按步骤算漏斗 | 图表渲染、看板 UI |
| 同意状态机、写前判定、撤回与删除 | 实验分流与显著性检验 |
| 事件数据的最小化存储与保留期 | 用户画像、推荐、生命周期营销 |

**术语**（全模块统一叫法）
- `event`：一次带名字的属性记录，如 `checkout_completed`
- `actor`：已登录用户（响应与库里只以 `subjectId` 摘要出现）
- `anonymousId`：未登录访客标识（同样只存摘要）
- `workspace`：租户；所有聚合按 workspace 隔离
- `purpose`：同意用途，最少 `analytics` 与 `marketing`
- `consent status`：`unknown`（从未表态）/ `granted` / `denied` / `withdrawn`（合同枚举）
- `funnel step`：有序步骤；`conversion window`：一步到下一步允许的最大间隔
- `retention`：原始事件的保留天数；到期必须删除

**事件模型**（示例载荷，形状固定）

```json
POST analytics.track
{
  "name": "checkout_completed",
  "anonymousId": "anon_9f2c…",
  "workspaceId": "ws_current",
  "occurredAt": "2026-03-01T10:22:31Z",
  "properties": { "plan": "pro", "items": 3 }
}
```

**这个模块的成熟度刻度**：开源最小实现通常只是"把事件转发给某个第三方分析 SDK"（客户端 + 服务端两处埋点、可选密钥、缺失即静默降级）。那是 MVP 的**采集半边**——它没有同意判定、没有自有存储、没有删除、没有漏斗语义。成熟版指的是：事件**先落自有存储**，同意与删除由本模块自己负责，第三方只是可选的下游副本（未配置时不报错、不采集、不影响主流程）。

## 2. 成熟版应该有什么（MVP → 成长 → 成熟）

### 2.1 MVP：诚实可用（缺一项就会出事）
1. **自有事件存储**：事件表字段固定（name、subject 摘要、anonymous 摘要、workspace_id、properties、occurred_at、received_at、policy_version）
2. **统一采集端点**：客户端与服务端用同一套事件名与属性；校验 + 限流 + 幂等
3. **聚合查询**：count、uniqueSubjects、按事件名分组、时间窗
4. **漏斗**：有序步骤、按人去重、转化窗口、逐步转化率
5. **同意状态机**：多 purpose、写前判定、默认拒绝、撤回即删
6. **最小化存储**：actor/anonymousId/token 摘要化，IP 截断，PII 属性丢弃
7. **租户隔离**：所有读路径按 workspace 授权
8. **保留期与清理**：到期数据不得再可读回、不再计入聚合
9. **错误契约**：统一错误封装与状态码，不泄露内部细节
10. **自身可观测**：丢弃原因、失败率、延迟发到 observability

### 2.2 成长版：能回答业务问题
11. 事件目录：事件名与属性有 owner、有 schema、有废弃流程
12. 留存/队列（cohort）矩阵、自助分段查询
13. 漏斗可保存、可复用、可按属性切分
14. 同意偏好中心：多 purpose、批量撤回、撤回影响预览
15. 身份缝合（登录后把匿名历史归属到本人）——**默认关闭**，需显式决定
16. 成本控制：采样、事件体积配额、与 usage-metering-and-budgets 对齐计费口径
17. 审计：同意变更、导出、删除请求进 audit-and-data-export
18. 迟到事件与时钟漂移处理（客户端时间不可信时以 received_at 为准）

### 2.3 成熟版：可证明、可治理
19. 隐私工程：subject 摘要索引表 + 密钥轮换（双密钥并存，见 decisions.md）
20. 可证明删除：删除回执（subject、时间、行数），可被导出模块引用
21. 数据质量看板：事件量断崖、未知事件名占比、时钟漂移告警
22. 与 feature-flags 对接：分组写入事件，漏斗按分组切分
23. 跨设备/跨会话归并策略与"错归并"的回滚手段
24. 按 purpose 分别设定保留期与冷热分层（原始短期、聚合长期、聚合可复算）

## 3. 每项的正确行为

### 3.1 事件生命周期
1. **校验在前**：name 形状 `^[a-z][a-z0-9_.-]{0,63}$`；properties 只接受标量值，嵌套对象与数组拒绝；属性个数与请求体字节数有上限。违反 → 4xx 且不落库。
2. **同意判定在写库前**：不满足同意 → 整条丢弃，**不做"匿名化后保留"**，且不入任何聚合。响应如实告知未存（调用方本来就能读到自己的同意状态，不构成信息泄露），但不得泄露**他人**的状态。
3. **时间**：occurredAt 缺省用服务端时间；客户端时间过旧或超前过大 → 拒绝；迟到事件以 received_at 参与窗口统计。
4. **最小化在落库前**：属性键命中 PII 名单（email/phone/token/password/…，见 contract R-T9）时该键值对整对丢弃；actor、anonymousId 写成域分隔 HMAC 摘要；IP 存 /24（IPv4）或 /48（IPv6）截断前缀。（值形态识别如 email 形态、≥9 位数字是成熟版增强，不在契约 MUST 内。）
5. **幂等**：Idempotency-Key 同键同体只入库一次；同键异体 → 409。
6. **限流**：超限 → 429 + Retry-After。

### 3.2 同意生命周期
- `unknown`（从未表态）→ 发确认邮件（状态仍是 `unknown`）→ 令牌确认后 → `granted` / `denied`
- `withdrawn`：撤销 + 触发删除；删除在有界时间内完成，且 stats/funnel/events 都看不到
- 同意记录带策略版本 `policyVersion`；文案改版后按策略重新征求
- 同意记录本身也要被审计，且**不得**被算作分析事件

### 3.3 查询语义
- `stats`：`count`=事件条数，`uniqueSubjects`=去重主体数（按摘要去重，同一人多设备需显式归并规则）
- `funnel`：步骤按序、主体去重、步骤间隔 ≤ 转化窗口；每步计数单调不增；逐步转化率与总体转化率都在 [0,1]
- 时间窗：`from`/`to` 缺省为最近 24 小时；漏斗相邻步骤间隔受 `funnelWindowSeconds` 约束

### 3.4 错误与限额
- 所有错误体 `{"error":{"code","message","details"}}`；code 是稳定机器码；message 不含堆栈、SQL、路径、密钥，也不回显用户提交的个人数据
- 同一情形固定一个状态码；不存在与无权访问返回**相同**结果，不做存在性探测

### 3.5 隔离
- 每个读接口都带 workspace 维度；未显式指定时用"当前 workspace"
- 事件明细只返回调用者本人的事件，同 workspace 其他成员看不到

### 3.6 保留与删除
- 到期事件不得再被读回、也不再计入聚合；物理清除由 async-jobs 调度（黑盒不可测，见 contract §5）
- 撤回同意删除该主体该 purpose 的全部事件（含其他工作区的），且删除后仍能对账

### 3.7 模块自身
- 采集丢弃、错误、延迟要被度量并进 observability；产品分析与运行监控**分开两套指标**，不要互相污染

## 4. 容易做错的地方（具体到会出什么事故）

1. **同意=弹窗** → 用户点过"知道了"不等于同意；监管问询时拿不出"主动选择"证据，数据只能整体删除，损失全部历史。
2. **PII 进 properties** → 数据库变成影子 CRM；一次越权或一次备份泄露就变成大规模个人信息泄露通报。
3. **撤回只翻标志** → 用户要求删除却没删，被认定为违反删除承诺；导出请求无法闭环。
4. **取 XFF 最左** → CDN 后面所有人共享一个 IP：限流误伤所有人、风控与地理画像全错、"匿名化"假象。
5. **漏斗不去重** → 同一用户十次点击算出十次转化，转化率虚高，团队按错数据改产品。
6. **采集端不管 Origin** → 任意第三方站点可以让访客浏览器向你的域名灌事件，污染数据且消耗配额。
7. **未配置第三方密钥就抛错** → 部署即 500，整个应用起不来（成熟实现应静默降级为 no-op）。
8. **进程内缓冲等 flush** → 无服务器/短生命周期环境里冷启动即丢事件，或重复发送造成计数翻倍。
9. **匿名历史自动缝到账号** → 未同意的历史被追溯归属到自然人，同意范围被悄悄扩大。
10. **摘要用了裸 SHA-256(userId)** → 可被字典反查回明文，等于没摘要；必须用带服务端密钥的 HMAC 且域分隔。
11. **换密钥时重算存量摘要** → 待用令牌批量失效、删除对不上；正确做法见 decisions.md 的双密钥并存。
12. **错误体回显提交的 email** → 把 PII 又写进日志与监控面板。

## 5. 与其他模块的接口

| 模块 | 接口含义（谁找谁） |
|---|---|
| auth | 提供当前登录身份与会话；analytics 只读取身份，不自己管密码或会话 |
| workspaces-and-permissions | 提供当前 workspace 与成员/角色判断；analytics 的读写与隔离依据它 |
| rate-limiting | 提供限流计数与 429/Retry-After 行为；analytics 声明自己的额度 |
| async-jobs | 承接保留期清理、撤回后的批量删除、历史回填等长任务 |
| email-transactional | 发送同意确认邮件（模板 `analytics.consent_confirm`，链接放 `data.link`，令牌明文只放 `token`） |
| audit-and-data-export | 接收同意变更、导出与删除请求；analytics 提供按 subject 定位与删除的执行能力并回报回执 |
| observability | 接收 analytics 自身的错误率、丢弃原因、延迟指标 |
| feature-flags | 提供分组标识写入事件属性，漏斗按分组切分 |
| internationalization | 提供同意文案与其版本，版本变更触发重新征求同意 |
| usage-metering-and-budgets | 事件量计费口径（采集体积、保留期） |

## 6. 不做什么

- 不做图表、看板、仪表盘 UI
- 不做实验分流与显著性检验
- 不做用户画像、推荐、生命周期营销触达（notifications 负责送达）
- 不做数据仓库建模与 BI 报表
- 不做账号体系、权限判定、限流器的自研实现（分别属于上述模块）
- 不做实时流式（秒级流处理）；分钟级批处理足够
- 不在事件里保存自由文本的 PII；不保存支付凭据、密钥、密码
- 不把产品分析与运行监控混成一套指标
