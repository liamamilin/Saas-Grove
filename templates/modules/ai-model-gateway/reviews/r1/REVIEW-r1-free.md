# ai-model-gateway 模块独立审查（轮 1）

审查对象：`module/MODULE.md`、`module/contract.md`、`module/acceptance-plan.md`、`module/decisions.md`；对照 `HOST.md`、`modules.json`。未读取任何密钥文件。

## 0. 总体判断

契约骨架完整（R1–R36、A01–A30）、错误码/状态码映射清晰、黑盒可观测性整体较好。但存在 1 条会把客户端 IP 记录污染成可伪造值的安全规则，以及若干跨文件语义冲突与未定义边界，不能直接判定为可用。

## 1. 安全 / 领域正确性

### 1.1 [安全] 无受信代理时仍信任 `X-Forwarded-For` 右侧条目（阻断）
- 文件：`contract.md` §3 R36 与 §5 `trustedProxyCidrs`
- 引用：R36“记录里的 clientIp 取 `X-Forwarded-For` 最右侧的第一个非受信代理跳，不得取最左端。”；参数表“`trustedProxyCidrs` | 受信代理网段 / 列表 | 空”。
- 为什么：默认受信网段为空，但规则仍取 XFF 中“最右侧非受信跳”。在没有可信代理的部署里，XFF 整个头都由客户端控制，攻击者发送 `X-Forwarded-For: 1.2.3.4` 即可把任意 IP 写入调用记录，审计/风控被污染。这与提示词里“信任最左 X-Forwarded-For”的危险模式同源，只是把攻击面从最左移到了“空信任列表下的右值”。
- 修法：定义 `trustedProxyCidrs` 为空时完全忽略 XFF、使用连接对端 IP；或要求至少配置一个受信代理才允许解析 XFF，并在契约中写明回退行为。

### 1.2 [安全] 凭据存放位置在决策与契约间自相矛盾（应修）
- 文件：`decisions.md` D2；`contract.md` §2/§3 R4、R5
- 引用：D2“凭据与端点走环境变量（启动必需），运行时配置只放非敏感开关（别名、限值）”；R4“配置读接口只回掩码+指纹”；R5“改配置需管理员…”。
- 为什么：若凭据只能来自环境变量，运行时 `GET/PUT config` 就不该出现凭据掩码/指纹；若运行时可轮换凭据，则 D2 的“尽量不落库/环境变量必需”过时。实现者无法判断 PUT config 是否允许写入凭据。
- 修法：明确配置对象中凭据字段是只读回显还是可写；若不可写，从 §2 形状与 R4/R5 中删除凭据相关字段。

### 1.3 [安全] 空幂等键未定义，可能造成跨请求碰撞（建议）
- 文件：`contract.md` §2 请求形状
- 引用：“`idempotencyKey` ≤128 字节（或 `Idempotency-Key` 头，二者同时给出须一致）。”
- 为什么：只给上限，未规定空字符串/空白是否算“未提供”。若实现把空串当有效键，所有未传键的请求会共享同一幂等结果，造成跨用户响应复用。
- 修法：明确定义“缺省或空值 = 不启用幂等”，且空值不得写入幂等表。

## 2. 可观察性

### 2.1 [可观察] 配置变更审计在黑盒下无观察入口（应修）
- 文件：`contract.md` §3 R5；`HOST.md` §3/§4
- 引用：R5“成功变更写审计”；`HOST.md` 仅提供 health/outbox/clock/rate-limits/fake-model/只读 DB，无审计查询钩子。
- 为什么：黑盒验收无法确认“写审计”是否发生，除非宿主恰好实现 `audit-and-data-export` 并暴露查询。契约把不可直接观察的要求写进了 MUST。
- 修法：指定审计留痕的可观察载体（如 `audit-and-data-export` 的查询接口或约定表名/字段），或把该项降为“建议，验收不测”。

### 2.2 [可观察] 退避抖动写入 MUST 但 §8 又声明不测（建议）
- 文件：`contract.md` §3 R24 与 §8
- 引用：R24“退避指数+抖动”；§8“退避抖动算法…建议，验收不测”。
- 为什么：MUST 与“建议不测”并存，审查/验收口径不一致。
- 修法：把抖动从 MUST 移到 §8，或给出可观察的代理断言（如耗时分布/最小间隔）。

## 3. 一致性

### 3.1 [一致] usage 形状未定义缓存/推理 token 的额外字段（应修）
- 文件：`contract.md` §2 数据形状 与 §3 R20
- 引用：§2“`usage{inputTokens,outputTokens,totalTokens,source}`”；R20“缓存/推理 token 只作额外字段，不重复计入。”
- 为什么：R20 要求额外字段，但 §2 的 usage 对象没有这些字段名，宿主可能自造字段名，验收无法比对。
- 修法：在 §2 明确可选字段（如 `cachedInputTokens`、`reasoningTokens`）及其不计入 total 的规则。

### 3.2 [一致] `rate-limiting` 拒绝“原样透传”与统一错误体冲突（应修）
- 文件：`contract.md` §3 R28、R32
- 引用：R28“非 2xx 体固定 `{"error":{code,message,retryable,requestId}}`”；R32“`rate-limiting` 拒绝原样透传。”
- 为什么：“原样透传”可能保留限流模块自己的响应体，破坏 R28 的固定形状；若强制改写，又可能丢掉限流模块的 `Retry-After` 或细节。两者没有优先级。
- 修法：明确限流拒绝必须保留状态码与 `Retry-After`，但响应体按网关统一形状输出，并说明 code 来源。

### 3.3 [一致] 上游 408 的分类与重试策略未定义（建议）
- 文件：`contract.md` §3 R23、R32 与 §4 错误表
- 引用：R23“仅瞬时类（连接错/超时/上游 429/5xx）可重试”；R32“上游 4xx 除 408/429 → `provider_rejected`”。
- 为什么：408 被排除在 `provider_rejected` 之外，但又不在 R23 的可重试列表里，出现 408 时既不算可重试也不算已定义的 502 分类，实现只能猜。
- 修法：把 408 明确归入超时/可重试，或归入 `provider_rejected`。

## 4. 可执行性

### 4.1 [可执行] Content-Type 等价类型无法按 HOST 声明（应修）
- 文件：`contract.md` §3 R14；`HOST.md` §2
- 引用：R14“等价类型须在 module-map 声明”；`HOST.md`“宿主在根目录放 `module-map.json`，把契约里的'概念'映射到自己的真实路径”。
- 为什么：`HOST.md` 的 `module-map.json` 只定义 method/path，没有内容类型字段，验收无法读取“等价类型声明”。
- 修法：扩展 HOST/module-map 约定以包含响应内容类型，或删除 R14 的等价类型条款。

### 4.2 [可执行] A10 隐含模型上限不超过全局上限（建议）
- 文件：`acceptance-plan.md` A10
- 引用：A10“响应 `effectiveMaxTokens=M`（且 ≤ `P.maxOutputTokens`）”。
- 为什么：R11 的生效值是 `min(请求值, 模型上限, 全局上限)`。若模型上限 M 大于全局上限，生效值应为全局上限，A10 的期望 `M` 会失败。
- 修法：把期望改为 `min(M, P.maxOutputTokens)`。

## 5. 追溯

### 5.1 [追溯] R24 整体超时上限没有用例断言（追溯缺口）
- 文件：`contract.md` §3 R24；`acceptance-plan.md` A19、A22
- 引用：R24“整次 ≤ `requestTimeoutMs`（超时 503 `provider_unavailable`）”；A19 只断言“耗时 ≥ `P.retryBaseDelayMs`”；A22 只断言熔断期间“耗时 < `P.attemptTimeoutMs`”。
- 为什么：没有用例验证总耗时不超过 `requestTimeoutMs`，契约的超时不变量无法被验收。
- 修法：在 A19 或新增用例中增加“总耗时 ≤ P.requestTimeoutMs + 容差”的断言。

### 5.2 [追溯] R21“上游全败记 0”没有用例断言（追溯缺口）
- 文件：`contract.md` §3 R21；`acceptance-plan.md` A20
- 引用：R21“上游全败记 0 并带 status”；A20 只断言“attempts=1 且 502/429”，未断言 usage 条数或 token 数。
- 为什么：上游全败时的记账不变量（0 token）没有被直接验证。
- 修法：扩展 A20 断言 usage 记账 token 为 0 且记录 status 为 failed。

### 5.3 [追溯] R30 幂等键哈希存储没有用例验证（追溯缺口）
- 文件：`contract.md` §3 R30、§6；`acceptance-plan.md` A23
- 引用：R30/§6“键只存 SHA-256 摘要，不得存明文”；A23 只验证 id/usage/上游计数。
- 为什么：存储安全要求无法从现有用例确认，HOST 允许只读 DB 检查哈希，但 A23 未使用。
- 修法：在 A23 或 A04 类用例中增加只读 DB 检查：幂等表中无明文键，仅存摘要。

### 5.4 [追溯] R27 半开成功后关闭熔断没有用例断言（追溯缺口）
- 文件：`contract.md` §3 R27；`acceptance-plan.md` A22
- 引用：R27“超时后一次半开探测，成功即关闭”；A22 只说“推进时钟 `P.circuitOpenMs` 后可再试”。
- 为什么：半开探测成功后熔断是否关闭没有直接断言，恢复路径未覆盖。
- 修法：扩展 A22：推进时钟后发送一个成功请求，再发请求应正常打上游（熔断关闭）。

## 8. 缺口（资深审查者会攻击的点）

### 8.1 [缺口] 流式响应的重试语义未定义（应修）
- 文件：`contract.md` §3 R23/R25；`acceptance-plan.md` A13/A14
- 引用：R23“仅瞬时类…可重试”；V2“顺序 `start → delta* → usage → done`”。
- 为什么：流式一旦发出 delta，重试会产生重复输出或交错事件；契约未说明重试只允许在首个 delta 之前，或流式完全不重试。
- 修法：新增规则：流式在发出首个 delta 前可重试；发出 delta 后失败必须发 `error` 终止且不重试。

### 8.2 [缺口] 熔断作用域未定义（应修）
- 文件：`contract.md` §3 R27
- 引用：“连续失败达 `circuitFailureThreshold` → 打开”。
- 为什么：未说明熔断按 provider、provider+model 还是工作区维度；不同作用域直接影响租户隔离与测试构造。
- 修法：明确熔断键（建议 provider+model 或 provider 全局）及是否租户隔离。

### 8.3 [缺口] 回退触发条件未定义（应修）
- 文件：`contract.md` §3 R25
- 引用：“重试耗尽后按配置回退”。
- 为什么：未说明认证失败、4xx 拒绝等非瞬时错误是否触发回退；若一律回退，会把配置错误掩盖成“换模型成功”。
- 修法：明确仅瞬时错误耗尽后回退；非重试类错误直接返回，不回退。

### 8.4 [缺口] 熔断半开失败后的状态未定义（应修）
- 文件：`contract.md` §3 R27
- 引用：“超时后一次半开探测，成功即关闭。”
- 为什么：半开探测失败后是重新打开一个完整窗口还是继续半开未定义。
- 修法：明确失败则重新打开 `circuitOpenMs`。

### 8.5 [缺口] token 估算算法未定义，上下文预算难以稳定复现（建议）
- 文件：`contract.md` §3 R12/R19
- 引用：R12“估算输入+`effectiveMaxTokens` > 模型 `maxInputTokens`”；R19“没报才估算”。
- 为什么：不定义估算方法（字符、分词、宿主声明），A11 的边界构造在不同实现间不可复现。
- 修法：指定估算算法或允许宿主通过 params/模型字段声明。

### 8.6 [缺口] 并发护栏与幂等/预算的顺序未定义（建议）
- 文件：`contract.md` §3 R30、R31、R33
- 引用：R31“超出 → 429…不记账、不调上游”；R33“耗尽 → 402…不调上游、不记账”。
- 为什么：并发占位、幂等命中、预算检查的先后顺序未定义，影响 429/409/402 的优先级与计数。
- 修法：给出固定顺序（建议：上下文/校验 → 幂等 → 预算 → 并发占位 → 上游）。
