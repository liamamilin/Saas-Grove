## 阻断

**B1 [安全] 全局配置由「工作区管理员」可写，且端点可被改写（contract R5、§0「管理员」；plan A03/A05「改的是全局配置」）**
- 为什么：A03/A05 自己承认 config 是全局的，但改配置的权限只是 workspaces 里的工作区管理员。多租户 SaaS 里任意租户的管理员就能改全局别名、回退链、限值、provider 端点。端点还可改成攻击者地址，网关随后带着上游 API Key 发请求，等于把平台密钥外送；改成内网地址（云元数据等）是 SSRF。R5 还要求「schema 合法但端点不可解析也必须写入」，等于强制允许把全网关搞挂。
- 修法：
  - 区分平台管理员（宿主级角色，由宿主声明）和工作区管理员。全局配置只允许平台管理员写，工作区管理员最多改本工作区的可见模型/别名覆盖。
  - 端点与凭据只走环境变量（与 D2 一致），不进 config.update；若必须可写，则限制 https、禁止内网/链路本地/回环地址，并校验主机白名单。
  - R5 把「可写入不可用配置」改成 MAY，或改为 422 拒绝；A03 保留为「宿主未声明」分支即可。

**B2 [可观察] 「usage 记账条数」没有任何观察途径（contract R9/R21/R30/R31/R33、不变量 1/5；plan A08/A09/A17/A19/A21/A23/A26/A29/A30）**
- 为什么：§1 概念表里没有「读取 usage 账本」的概念；calls 只给每条调用记录的 `usage` 字段，不是账本条数。HOST §4 的只读 DB 查询没有表名/列名约定。至少 9 条用例的核心断言（零记账、恰好 1 条、K 条）在黑盒下无法判定，要么全部「宿主未声明」，要么实现者各猜各的。
- 修法：在契约里定义观察方式。优先用 `usage-metering-and-budgets` 的读取概念（按工作区列出记录，字段含 requestId）；宿主未声明该模块时，改为在 module-map 声明只读 DB 的账本表名及 requestId/workspaceId/tokens 列，并写进 §0。然后把「记账条数」统一换成「以 requestId 关联的账本行数」。

## 应修

**S1 [安全] 取消不记账会被白嫖（R18、R21、不变量 1；A17）**：流式调用读完全部 delta、在 `usage` 事件前断开，即可免费使用，且上游仍会按已生成 token 计费，违背 MODULE「能对上供应商账单」。修法：取消时按已产出内容估算并记账（`source:estimated`、`status:cancelled`），或至少记已知输入 token；若有意不记，要在 decisions.md 补一条决策并写明滥用上限（如在途护栏 + 取消次数限制）。A17 的断言同步改成「有 estimated 记账」或「按决策断言」。

**S2 [安全] clientIp 取值规则在默认配置下可被伪造（R36、§5 `trustedProxyCidrs` 默认空；A18）**：业界做法是先看 TCP 对端是否在受信网段，不在则忽略 XFF、直接用对端地址；在则从右向左跳过受信跳。契约默认受信列表为空却仍取「XFF 最右侧」，这个值仍由客户端控制；A18 发送 `1.1.1.1, 2.2.2.2` 并期待 `2.2.2.2`，在默认配置下反而奖励了错误实现，而测试也不知道对端地址是什么。修法：重写 R36——受信列表为空时 clientIp = 对端地址（验收只断言它不等于 XFF 里任何伪造值）；A18 需要先在 params 声明 `trustedProxyCidrs`（含测试对端地址）才测 XFF 分支，否则该断言记宿主未声明。该规则本属 `web-security`/`rate-limiting`，见 G13。

**S3 [安全] 幂等的三个漏洞（R30；A23-A25）**：
(a) 同键首个请求仍在途时第二个同体请求到达：未规定（应等待首个结果或 409/429，不得再打一次上游并记账），无用例，并发重放是资深审查者的头号攻击点。
(b) 首次调用失败（5xx、provider_unavailable）是否被缓存重放：未规定。缓存失败会把故障钉死一整个窗口，不缓存则需明说「仅成功结果可重放」。
(c) A25 允许跨租户同键返回 409，这会暴露他租户键的存在性，与 R30「跨租户不得命中」的精神相悖。修法：A25 只允许「按新调用处理」；补并发同键用例和失败不缓存用例。

**S4 [一致] 幂等重放需要持久化响应内容，与「默认不落库」冲突（R30 vs §8、D13、MODULE 坑 19）**：返回「同 `id`、同 content」必须在窗口内（最长 7 天）存着模型输出，但契约在 §6 只规定键摘要，没有规定 content 的加密、保留期和删除。修法：在 §6 明确「幂等结果属于受限的落库例外：仅存响应体、加密、窗口到期即清除、随 audit-and-data-export 的删除请求清理」，并在 D13 加例外说明。

**S5 [一致] 哪些拒绝会留记录前后不一（R22 vs 不变量 1 vs §2 状态枚举 `rejected`）**：R22 说「通过校验并进入生成阶段」才留记录，不变量 1 说「除 400/413/422 外一次逻辑调用恰好 1 条记录」（会把 401/404/409/402/429/503 not_ready 都算进去）。402/429/409/model_not_found/gateway_not_ready 到底有没有记录，两种读法都合规，A26/A29 因此无法断言记录数。修法：列一张「错误码 → 是否留记录 → 是否记账」表，替换 R22 与不变量 1 的叙述；未认证和非成员（无工作区上下文）明确为无记录。

**S6 [一致] 不变量 5 与 R27 互斥（不变量 5「provider_unavailable 表示已尝试上游，attempts ≥ 1」vs R27「熔断打开期间 503 provider_unavailable 且不调上游」）**：熔断快速失败时 attempts 为 0，没有任何实现能同时满足两条。修法：改为「`provider_unavailable` 的 `attempts` ≥ 0，熔断快速失败为 0，其余 ≥ 1」，并写明熔断快速失败是否留 `failed` 记录与 0 token 记账。

**S7 [一致] 流式在「首个字节前」出错怎么回，未规定（§2 流式事件、R15；A14）**：§2 写死「出错时 start→delta→error」，但 402/429/404/503（熔断）、上游首包失败属于流开始前的错误，应回 §4 对应状态码的 JSON，还是 200 + SSE `error`？A14「假模型注入失败 → 出现 error 事件」只有在实现选择「先发 200 再重试」时才通过；选择「重试/回退后再开流并返回 503 JSON」的实现同样合理却会被判失败。修法：规定「在发出 `start` 之前的所有错误按非流式 JSON + §4 状态码返回；`start` 之后只能用 `error` 事件」，并规定流中途失败是否允许重试（建议不允许）。A14 改为注入「首个 delta 之后失败」。

**S8 [一致] A10 自相矛盾（plan A10、R11）**：期望 `effectiveMaxTokens = M`，同时 ≤ `P.maxOutputTokens`。当模型上限 M > 全局上限时（默认全局 4096），effective 必须是全局上限而非 M，两条断言互斥。修法：期望写成 `effectiveMaxTokens = min(M, P.maxOutputTokens)`，上游收到的 maxTokens 同值；再补一条「请求值小于上限时原样使用」的正向断言。

**S9 [一致] A19 的退避下限与「抖动」冲突（R24、A19「耗时 ≥ retryBaseDelayMs」）**：业界推荐的 full jitter 在 [0, base·2ⁿ] 内取随机，实际延迟可小于 base，合规实现会随机失败。而且抖动本身黑盒不可观测。修法：A19 只断言 attempts=2、成功、总耗时 < `requestTimeoutMs`；R24 里「指数+抖动」降为建议（见 S16）；若要保留下限，在契约里明确「延迟 ∈ [0, base·2ⁿ⁻¹]（full jitter）」并只断言上界。

**S10 [一致] 熔断的计数口径和 A22 的循环未定义（R27、§5；A22）**：
- 「连续失败」按尝试计还是按逻辑调用计？只算瞬时类失败，还是含上游 4xx？按全局、按 provider 还是按模型/工作区计？若按逻辑调用计，A22 里「首个 503」可能只是重试耗尽，紧接着的请求仍会打上游，用例会判错。
- 熔断是全局状态，A22 跑完会污染后续用例；「DELETE fake-model 复位」不会复位熔断。
- 半开探测成功即关闭，A22 只写了「可再试」，没有断言成功。
- 修法：写明「按 provider 计、仅计瞬时类失败、按尝试计」；A22 先断言出现熔断（上游计数停止增长），再推进 `circuitOpenMs`、注入成功、断言 200 且后续继续 200；用例末尾需要宿主提供的复位手段（例如推进时钟 + 成功调用）。

**S11 [一致] 配置分层前后矛盾（decisions D2/D16 vs R3、R5、§6、A03、A04）**：D2 说「凭据与端点走环境变量，运行时配置只放非敏感开关」，R3/R5/A03 却要求通过 config.update 修改端点；R4/§6/A04 要求「持久化凭据加密」，而 D16 说「尽量不落」。读者无法判断凭据与端点是否进运行时库。修法：定一个口径（建议：凭据与端点仅环境变量，config 只含别名/限值/回退链/可见性），据此重写 R3 的触发方式、R4/§6、A03/A04；R3 的「运行期不可用」改用别的可触发条件，例如假模型钩子把 provider 置为不可用。

**S12 [可执行] config 形状、模型可见性、回退链都没有定义（§2、R5、R6、R7、R25；A03-A07、A21）**：契约没有 config 的字段表，A05 无法构造「schema 非法」的值；A06/A07 需要「只对 W2 可见的模型」，但没说可见性怎么配（按工作区？按角色？来自 feature-flags？）夹具如何创建；A21 需要「配置主模型的回退链和改别名」，字段同样没有。修法：§2 增加 config 对象 schema（`models[]{name, providerModel, maxInputTokens, maxOutputTokens, supportsStreaming, visibleTo, fallbacks[]}`、`aliases`、限值）和示例；写清楚 `visibleTo` 的取值，以及验收如何用公开接口造出 W2 专属模型。

**S13 [可执行] 假模型钩子能力不足以跑 A19-A22/A28（contract §0 假模型、HOST §3）**：§0 只列了延迟、一次性失败、持续失败、固定 usage、读回请求。实际还需要：按模型名区分失败（A21 要主模型失败、备用成功）；指定失败类型（401、400、429、5xx、超时、连接错——A19 的「失败」是哪种？）；上游返回 `Retry-After` 头（A20）；省略 usage（R19 估算路径）；返回缓存/推理 token（R20）；返回无法解析的响应（`provider_invalid_response`）；错误文本带标记（A28）；流式中途失败（A14）。修法：把这些列为 §0 的必选钩子能力，并给出 PUT 载荷示例；缺哪项，对应用例记宿主未声明。

**S14 [可执行] 启动类与跨模块前置用例缺少可执行路径（R1/R2/R5/R29/R33；A01、A02、A05、A12、A29）**：
- A01/A02 需要验收 harness 自行带环境变量启动/重启宿主，且要知道非 fake provider 的 `MODEL_PROVIDER` 取值和凭据变量名——契约只出现了 `MODEL_PROVIDER`，其余未定义，HOST §1 也未规定如何带自定义环境启动。
- A05「有审计事件」没写通过哪个接口读（audit-and-data-export 的读取概念未引用）。
- A12 需要 auth 能「禁用账号/制造未验证账号」，auth 契约不一定暴露；且未验证账号可能根本拿不到凭据，用例退化为一种场景。
- A29 需要 usage-metering 把预算「置为耗尽」，接口未指明。
- 修法：§0 补环境变量名表与 harness 启动方式；审计读取、账号禁用、预算置零各自引用对应模块的概念名；拿不到则记宿主未声明。

**S15 [追溯] 多条 MUST 没有用例或只有半条用例**：见下方「追溯缺口」清单，共 12 项。修法：补用例或把对应表述降为建议。尤其 R19 的 estimated 路径、R21 的失败记 0、R24 的两类超时、R27 的半开恢复、R22 的失败/拒绝记录，直接影响「能对账」这个核心卖点。

**S16 [可观察] 不能在 HOST 黑盒下判定的 MUST（R4「日志」、R5「持久化加密」、R24「抖动」、R30「键只存摘要」、R32「不自建 rpm 限流」、R35 之外的「不改写内容」等；contract §6/§8）**：HOST §3b 要求不可测规则放进「建议，验收不测」。R4 的日志、加密完整性、抖动算法、「不自建限流」是负命题，不可判定。幂等键摘要和凭据明文虽可经 DB 只读查询，但没有对应用例（A04 只覆盖凭据）。修法：R4 拆成「响应/错误/记录无凭据」（MUST）和「日志无凭据」（建议）；其余移入 §8；或为幂等键补一条 DB 只读用例（用已知键，在库中全表搜索明文）。

**S17 [一致] R12 语义混乱（R12、§2 模型字段 `maxInputTokens`；MODULE S5「上下文窗口」）**：R12 用 `估算输入 + effectiveMaxTokens > maxInputTokens` 判定，把输出预算也算进「最大输入」，MODULE 写的却是「上下文窗口」。模型目录里没有窗口字段。`truncate:true` 的截断对象（丢最早的消息？是否保留 system？）和「按截断后重算」的算法未规定，也没规定估算器；effectiveMaxTokens 本身就大于 `maxInputTokens` 时的行为也未定义。修法：模型目录加 `contextWindow`，判定改为 `估算输入 + effectiveMaxTokens > contextWindow`；写明截断策略（保留 system、从最早的非 system 消息丢）以及无法截断时仍回 422。

## 建议

- **G1 [文字]** 规则编号缺 R13（R12 之后直接是 R14），MODULE 和追溯表都未提及。补一条或重排并同步全部引用。
- **G2 [缺口]** 错误优先级未规定：未认证 + 非法 JSON、非成员 + 超大体、模型不存在 + 预算耗尽，先返回哪个？写一张检查顺序表，否则状态码用例在组合场景下互相矛盾。
- **G3 [缺口]** calls：只有 `limit`，没有游标/排序约定；`limit=0/101/abc` 的行为未定义；普通成员能否看到他人调用（MODULE §5 说据角色判断，契约未写）；429 洪泛下记录无限增长的存储 DoS。
- **G4 [缺口]** 截断可能丢掉 system 消息（见 S17），会使 `prompt-injection-and-guardrails` 的系统提示失效；流式输出已发 delta 后不应静默重试（会重复文本）。
- **G5 [缺口]** R33 只是「调用前查预算」，并发下仍会超支。成熟做法是按 `effectiveMaxTokens` 预占额度再结算；至少在 §8 写明由 `usage-metering-and-budgets` 的硬停负责，网关调用预占接口。
- **G6 [缺口]** 熔断与回退的交互：主模型熔断时，是直接走回退还是 503？熔断作用域（全局/按工作区）会导致一个租户的坏请求拖垮其他租户，需写明。
- **G7 [缺口]** `metadata` 只限 ≤16 键，没有键值长度/类型限制，原样回显并进记录，可能携带 PII；入站 `X-Request-Id` 是否采纳（日志注入/伪造）未规定。
- **G8 [缺口]** 「估算 token」的估算器未规定误差范围，A11 靠它构造输入，估算偏差可能让用例在合规实现上不稳定；建议规定「按字符数 ÷ 固定系数保守估算」或在 params 声明系数。
- **G9 [缺口]** 对 `supportsStreaming:false` 的模型调用 stream 的行为和错误码未定义。
- **G10 [缺口]** 上游响应体大小上限、畸形响应只有一个 `provider_invalid_response`，没有用例（见追溯缺口）；上游 `Retry-After` 可能是超大值或 HTTP 日期，透传前应封顶/规范化。
- **G11 [可执行]** A28 只检查响应体，R4/R28 还要求记录里没有标记，建议同时读 calls；A17 的 `cancelled` 记录是异步写入，需写明轮询超时。
- **G12 [越界]** R29 里「账号被禁用/未验证 → 401」是 `auth` 的行为，网关只需透传 auth 的结论；契约里重复定义会与 auth 契约漂移。
- **G13 [越界]** R36 clientIp 提取属于 `web-security`/`rate-limiting`/`observability` 的公共能力，网关只需记录宿主提供的可信 IP；A18 因此变成跨模块用例。
- **G14 [可观察]** MODULE「十个不可妥协」第 1 条（不得直接引用厂商 SDK）、M5/D18（假与真同一条代码路径）在黑盒下不可判定，且 M5 对应的 R2 实际是「生产禁假」，映射不准。移到契约 §8 的建议，MODULE 里标注「验收不测」。

4. R26「回退目标不可见则按无回退处理」：A21 只有可见的正例，缺负例。
5. R27「半开探测成功即关闭」：A22 只写「可再试」。
6. R30「同键头与体不一致须一致」「键只存摘要」：无用例，且该不一致的错误码未在 §4 指定。
7. R32「rate-limiting 拒绝原样透传」「透传上游 Retry-After」：A20/A26 只测网关自己的 429；上游头需假模型能返回头（见 S13）。
8. R22「失败/被护栏拒绝也留记录、不可改」：只有 A17 的 cancelled，缺 failed 与 rejected。
9. R5「成功变更写审计」：A05 写了断言但没有读取途径（见 S14）。
10. R34 正向：本工作区能看到自己的记录且看不到别人的；A27 只测非成员 404。
11. R23 的「上游 400 不重试」「5xx/超时/连接错重试」，以及错误码 `provider_rejected`、`provider_invalid_response`、`internal_error`：§4 有码、用例无。
12. R3/R4「日志无凭据」属不可观察，应移出 MUST（见 S16）。

## 其他核对结论

- 数值一致性：D9/D10/D11/D12 的默认值与 §5 一致（3 次/30s/60s、深度 1、阈值 3/30s、窗口 86400）；MODULE S3 的 1-64/默认 8 与 §5 一致；`attemptTimeoutMs` 上限 120000 可大于 `requestTimeoutMs` 下限 5000，建议在 §5 加约束「attemptTimeoutMs ≤ requestTimeoutMs」。
- 状态码表（§4）内部没有同 code 跨两个状态码；但 stream 的 `error` 事件 code 是否沿用 §4、`provider_rejected` 对上游 408 的处理（既不重试也不是 429）存在空档。
- 未发现「信任最左 XFF」「重算存量哈希」「非恒定耗时比较」「金额用浮点」类错误；R36 的问题是「受信列表为空」时的行为（S2）。
- 时区/金额：本模块不涉及货币计算，token 为整数，无问题。
