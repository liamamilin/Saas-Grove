# async-jobs 认知模板（背景任务 / 长任务引擎）

> 读者是要在自己技术栈里实现本模块的编码 agent。硬规则见 `contract.md`（黑盒可验收），用例见 `acceptance-plan.md`，待拍板的取舍见 `decisions.md`。本文件讲"成熟版长什么样、正确行为是什么、哪里会翻车"。

## 必读摘要（一页）

**一句话**：异步任务模块 = **持久化的任务生命周期引擎**：提交、排队、执行到第几步、能不能停、出错怎么重试、结果怎么取、进程挂了怎么续。它不负责业务逻辑，只负责把"很慢、可能失败、可能要人干预"的工作变成可观察、可取消、可重放、可审计的记录。

**三个真正的难点**：

1. **执行是"至少一次"**：崩溃、被杀、租约过期都会让同一步再跑一遍。成熟版不承诺"恰好一次"，而是让每步带稳定**效果键（effectKey）**：重跑前先查效果键 → 外部副作用只发生一次。幂等要落到具体副作用（发信、扣款、写第三方 API）。
2. **取消是协作式的**：请求取消 → `cancelling` → 执行者在步骤边界看到信号 → 停止 → 落终态 `cancelled`。强杀会留下"副作用已发生、状态没记录"的空洞，用户见失败就重试 → 副作用两次。
3. **任务要活得比进程久**：队列、步骤、结果、幂等键全部落库；执行者用**租约 + 心跳**领任务，租约过期自动回收。进程内存队列 = 重启即丢任务。

**十条不可妥协的不变量**：

1. 状态机封闭：`queued → running → succeeded/failed/cancelled`。
2. 终态不可变。
3. 进度单调不减、0..100，只有 `succeeded` 是 100。
4. 服务端权威字段（`status`/`progress`/`attempt`/`steps`/`result`）客户端写不进去。
5. 同 (工作区, 幂等键) 至多一个任务；同键异体 → 409。
6. 每步 `effectKey` 跨尝试稳定 → 副作用至多一次。
7. 重试时**已成功步骤不重跑**。
8. 取消后不再启动新步骤、不产生新副作用；已发生副作用不回滚。
9. 状态必须落库；执行者失联由租约回收，不允许永久 `running`。
10. 保留期到，`payload`/`metadata`/`result` 的个人数据必须清掉。

**对外形状**：7 个概念（submit/get/list/cancel/retry/result/token）、6 个状态、每种情况一个错误码（一景一码，见 `contract.md` §3）。先定数字：并发与队列上限、载荷与结果上限、最大尝试次数、超时、租约过期、退避、保留期、令牌 TTL（界限见 `contract.md` §5）。

**最容易翻车的 5 处**：HTTP 请求里直接执行任务；用内存 map/进程内锁防重复；取消 = 强杀；客户端能提交 `status`/`progress`；把 `X-Forwarded-For` 最左侧当客户端 IP。

## 这个模块是什么

**用户问题**：有些工作 HTTP 请求内做不完——批量导出、报表生成、数据同步、大文件处理、AI 批处理、长时间建模。它们需要：进度可见、能中止、能重试、失败可查原因、多人共享同一份状态、进程重启不丢。

**边界**：它是**生命周期引擎**，不是工作流引擎。业务逻辑写在宿主注册的"任务类型处理器"里；模块提供队列、状态、进度、取消、重试、超时、租约、结果与令牌。

**不是什么**（先排除，别做成"什么都干"）：不是定时调度器（定时器负责触发 submit）；不是 DAG/分支编排器（步骤线性有序）；不是消息总线；不是"恰好一次"事务系统；不大文件存储（那是 `file-storage`）。

## 成熟版应该有什么（按成熟度分层）

### MVP（能让业务上线）

1. 持久化队列 + 提交接口（先落库再回 202 与任务 id）。
2. 执行者与租约（领任务 → 执行 → 落结果 → 释放租约）。
3. 状态查询与错误分类（用户输入错 vs 内部故障）。
4. 取消（只能取消尚未开始的任务）。
5. 固定次数重试 + 明确终态，失败原因落库可查。

### V1（可靠，不再半夜被叫醒）

6. 多步骤 + 步骤级 attempts（进度由步骤推导）。
7. 重试断点续跑（从失败步骤继续，已成功步骤不重跑）。
8. 副作用去重（每步稳定 `effectKey`，不重复发信/扣费/写第三方）。
9. 进度语义（0..100、单调不减、只有成功才 100）。
10. 幂等提交（`Idempotency-Key`，重试提交不建两个任务）。
11. 超时与租约回收（失联任务不永久 `running`、不永久占槽）。
12. 容量上限（并发 + 排队，超限明确拒绝 429 而非无限堆积）。
13. 结果大小上限（大结果截断或转存对象存储，任务只留引用）。
14. 一次性访问令牌（可过期、可吊销、绑定单一任务）。

### 成熟（生产级，多租户 SaaS）

15. 优先级 + 公平调度（同优先级 FIFO，低优先级不被饿死）。
16. 失败隔离（毒任务不堵整条队列，按队列/类型有独立并发上限）。
17. 保留期与数据清除（到期清除结果与个人数据，留最小墓碑）。
18. 审计（谁在何时提交/取消/重跑/取结果）。
19. 可观测性（排队/执行时长、失败率、重试次数、队列深度的指标 + 日志 + 追踪，带 `job.id`）。
20. 手动重跑与运营处置（失败列表、选择性重跑、可重试/不可重试分类）。
21. 来源 IP 正确解析（取**最右侧不受信任**的 `X-Forwarded-For` 跳）。
22. 写接口来源校验（复用 `web-security` 的 Origin 规则，跨源写拒绝）。

### 领先（规模化与体验）

23. 分片与并行步骤（并行度可配、可限速，避免打爆第三方）。
24. 背压与自适应并发（按队列深度/下游延迟调节）。
25. 多队列/多区域分池（按租户等级或区域隔离）。
26. SLO 与告警（排队 P95、成功率、超时率；毒任务自动隔离）。
27. 任务模板（把"参数化的作业"沉淀为模板）。

## 每项的正确行为（要点版）

- **提交**：先落库再返回 202；id 不透明不可枚举（≥128 bit 随机）；服务端权威字段永不接受客户端输入；未知类型直接 400。
- **幂等**：`Idempotency-Key` 按 (工作区, 键) 去重；同键同体返回**原任务**，同键异体 409，并发同键只建一个；键只存摘要。
- **执行**：领任务 → 写租约 → 执行 → 续租约 → 落结果 → 释放租约；只在**步骤边界**检查取消信号。
- **重试**：区分"可重试"（超时、限流、5xx）与"不可重试"（参数非法、权限不足）；退避有界带抖动；耗尽落 `failed` + `retries_exhausted`。
- **取消**：协作式；`queued` 直接 `cancelled` 且**一步都不跑**；`running` 先 `cancelling` 再 `cancelled`；取消后不启动新步骤、不产生新副作用；**不回滚已发生的副作用**。
- **进度**：由步骤推导、只增不减；别在步骤内部写细粒度进度（写多了就是噪声）。
- **结果与令牌**：结果内联有上限，超出截断或转 `file-storage` 只留引用；一次性令牌绑定单一任务、单次使用、只存哈希。
- **超时与租约**：任务超时释放槽位；worker 失联由租约回收重排；两者时间源统一且能被测试时钟推进。
- **持久化与隔离**：队列、步骤、结果、幂等记录全落库（内存只放租约）；任务、步骤、结果、令牌绑定单一工作区，跨工作区一律"不存在"。
- **容量**：并发上限（超出排队）、队列上限（超出 429 + `Retry-After`）、载荷上限（超出 413）、尝试次数上限（超出 `failed`）。

## 容易做错的地方（具体到会出什么事故）

1. **在 HTTP 请求进程里执行任务** → 一次滚动更新跑掉一半任务，用户看到"已提交"却永远没结果。
2. **用内存 map / 进程内锁防重复** → 多实例或重启后锁失效，同一任务跑两次：重复扣款、重复发信。
3. **取消 = 强杀执行进程** → 副作用已发生但状态没落库，任务显示失败，用户重试 → 副作用第二次（"账已扣、记录没写"）。
4. **重试没有效果键** → 一次网络抖动引发重试，把 1000 条数据写两遍、给用户发 3 封完成通知。
5. **客户端能提交 `status`/`progress`/`attempt`** → 前端显示"已完成"但后端什么都没做；伪造 `attempt` 让重试预算失效。
6. **取 `X-Forwarded-For` 最左侧当客户端 IP** → 客户端自己写这个头即可伪造 IP：绕过按 IP 的限制、污染审计。正确做法：**从最右侧起跳过受信代理，取第一个不受信任的跳**。
7. **队列无上限** → 一个慢任务占满 worker 与连接；突发提交打爆内存/DB；重试风暴让队列翻倍。
8. **毒任务无隔离** → 必失败任务反复重试堵在队头，正常任务延迟飙升（队头阻塞）。
9. **错误体带堆栈/SQL，或结果无上限内联** → 前者被截图外传即成安全事件，后者撑爆响应体与 DB 行。
10. **令牌明文落库或回显** → 数据库泄露 = 全部结果链接泄露。哈希升级不能靠"拿明文重算摘要"（明文不可得），要**双键并存**直到旧令牌全部过期。
11. **保留期到了只删列表不删 payload** → 个人数据仍可取回，删除请求无效（合规事故）。
12. **状态机不封闭** → 出现 `succeeded` 且 `error` 非空、`finishedAt` 为空的组合，用户看到"半成功"。
13. **时间源不统一**（一处墙钟、一处业务时钟）→ 超时/租约/令牌 TTL 互相打架，问题只在生产复现。

## 与其他模块的接口（只列含义）

| 模块 | 本模块向它要什么 / 给它什么 |
|---|---|
| `auth` | 身份与凭证；账号状态（停用/未验证）→ 决定令牌是否失效、任务是否继续 |
| `workspaces-and-permissions` | 工作区归属与读写授权判定；成员可见性 |
| `rate-limiting` | 写接口的**请求速率**限制（IP/账号维度；本模块不另做一套） |
| `usage-metering-and-budgets` | 运行与尝试次数的计量；预算耗尽时拒绝新提交 |
| `ai-model-gateway` | 步骤内调用模型；重试不得重复计费（配合 `effectKey`） |
| `ai-retrieval` | 步骤内检索；结果按 `effectKey` 去重缓存 |
| `prompt-injection-and-guardrails` | 载荷来自不可信来源时，进步骤前必须过护栏 |
| `llm-observability-and-evals` | 任务内模型调用带 `job.id` 关联，评测可按任务回放 |
| `email-transactional` | 完成/失败通知邮件；模板名 `async-jobs.<name>`，链接放 `data.link` |
| `notifications` | 站内通知（完成/失败） |
| `file-storage` | 大结果与产物存对象存储，任务只存引用与校验和 |
| `webhooks-outbound` | 任务完成事件外发回调；本模块只发事件，不自己发 HTTP |
| `audit-and-data-export` | 生命周期审计事件（提交/取消/重跑/取结果） |
| `observability` | 指标、日志、追踪，携带 `job.id` 与 `attempt` |
| `web-security` | 写接口的 Origin/CSRF 校验与允许来源集合 |
| `internationalization` | 错误码是稳定英文标识，展示文案由 i18n 提供 |

## 不做什么

- 不做定时/周期调度：定时器负责触发 submit；不做 DAG/条件分支编排：步骤线性有序。
- 不承诺"恰好一次"执行：提供"至少一次执行 + 效果键去重"。
- 不提供副作用撤销（refund/rollback）：那是业务模块的事。
- 不存大文件本体、不流式传大结果：交给 `file-storage`。
- 不做跨区域强一致调度、不做自定义脚本执行：类型处理器由宿主注册。
- 不负责前端进度条 UI 与文案：只提供稳定状态与错误码。
- 不自己做请求级限流与 IP 封禁：交给 `rate-limiting` / `web-security`。
- 不在日志与错误里输出 payload 原文与第三方凭据。
