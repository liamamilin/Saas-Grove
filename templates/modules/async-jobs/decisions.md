# async-jobs：需要人来拍板的决策点

每条给出**推荐默认**与**选别的后果**。括号内是契约条目。

1. **执行语义：至少一次 + 效果键，还是追求"恰好一次"？** **推荐**：至少一次执行，每步一个稳定 `effectKey` 去重副作用（R-STEP-1）。**否则**：要"恰好一次"就得引入分布式事务或去重存储，故障面暴涨，强做通常只是把坑挪到第三方调用上。
2. **取消：协作式还是强杀执行进程？** **推荐**：协作式——先 `cancelling`，执行者在步骤边界自行停止（R-CANCEL-1）。**否则**：强杀留下"副作用已发生、状态未落库"的空洞，用户见失败即重试 → 副作用第二次。
3. **幂等键：作用域、保留期、存法？** **推荐**：作用域 (工作区, 键)，保留 ≥ 客户端最大重试窗口（默认 7 天），只存摘要、不回显明文（R-SUB-6）。**否则**：全局作用域会互相撞键；保留期短于重试窗口 → "我重试了却多一个任务"；明文入库 = 库泄露即可重放。
4. **任务类型：白名单注册还是动态执行？** **推荐**：启动期注册的白名单 + 参数校验，未知类型 400（R-SUB-2）。**否则**：把类型名当脚本/模板路径动态执行 = 远程代码执行入口。
5. **队列载体：数据库轮询还是专用消息中间件？** **推荐**：起步用数据库轮询 + 租约，吞吐上来再换。**否则**：先上中间件会引入"已回 202 但没进队列"的双写不一致。
6. **租约、心跳与超时怎么定？** **推荐**：`staleAfterSeconds=60`、心跳 ≤ 租约的 1/3、默认超时 300s 且单任务可覆盖有上限；超时与租约同一时间源（R-TIME-1、R-TIME-2）。**否则**：租约过长 → 崩溃后长时间假 `running`；过短或心跳抖动 → 被重复回收重复执行；不设超时 → 毒任务永久占槽。
7. **重试次数、退避，以及耗尽之后怎么办？** **推荐**：`maxAttempts=3`，指数退避 base 5s、单次上限 300s，区分可重试/不可重试错误；耗尽即 `failed` + `retries_exhausted`，由人决定手动重跑（R-RETRY-1、R-RETRY-2）。**否则**：无限重试会在下游故障时形成重试风暴，把永久失败变成"永远排队的任务"。
8. **并发与队列上限？** **推荐**：每工作区并发 1~4、排队上限 20，超出 429 + `Retry-After`（R-LIMIT-1）。**否则**：不限并发 → 单租户打爆下游；不限排队 → 提交无反馈、用户反复提交。
9. **进度由谁写？** **推荐**：由步骤推导、只增不减、仅成功为 100（R-PROG-1）。**否则**：客户端可写 → 显示"已完成"但后端没做；进度回退 → 前端进度条倒退。
10. **结果的大小与分享方式？** **推荐**：内联上限 64KB，超出截断或转 `file-storage` 只留引用（R-RESULT-1）；分享用一次性令牌 + TTL 15 分钟 + 邮件投递，绑定单一任务（R-TOKEN-1~4）。**否则**：无上限 → 一个大结果撑爆响应与 DB 行；长期可分享链接泄露后无法收敛且缺访问审计。
11. **令牌哈希算法升级？** **推荐**：双键并存——旧哈希与新哈希同时保留，直到旧哈希签发的令牌全部过期（R-TOKEN-5）。**否则**：直接砍掉旧哈希会让升级期间存量令牌立刻失效；想"用明文重算摘要"校验旧令牌行不通（明文不可得）。
12. **保留期、数据清除与任务标识？** **推荐**：默认 30 天，到期清除 `payload`/`metadata`/`result`（R-DATA-1）；任务 id 用不透明随机串（≥128 bit，R-SUB-1）；跨工作区返回 404 且与"不存在"同形（R-AUTH-2），同工作区权限不足才 403（R-AUTH-4）；错误体只含稳定英文 `code` + `message` + `requestId`。**否则**：只删列表不删载荷 → 个人数据仍可取回（合规事故）；可推导 id + "存在但无权限"错误 = 可枚举漏洞。
