# webhooks-outbound 模块模板（客户可见的出站 Webhook）

## 必须先读（一页）

**这个模块做什么**：平台把业务事件推到**客户自己的服务器**。客户在平台注册一个 URL（端点），平台在事件发生时用 HTTP POST 把事件发过去，并附上签名，客户据此验真伪、识别重复、处理失败。它只管"平台→客户"这一段。

**五件必须做对的事**（其余都是细节）：

1. **签名能独立复算**：交付请求必带 `X-Webhook-Id`、`X-Webhook-Timestamp`、`X-Webhook-Signature`；签名串 = `<时间戳>.<原始请求体字节>`，HMAC-SHA256，小写 hex，头里写成 `v1=<hex>`。客户拿这三个头 + 手上的原始 body 就能自己算，不需要 SDK。
2. **重试语义稳定**：同一次投递的多次尝试，`X-Webhook-Id` 与请求体字节**完全不变**，只有时间戳和签名变。客户据此去重。
3. **重放 ≠ 重试**：重放是一次**新的**投递（新 `X-Webhook-Id`），但请求体字节与事件 id 不变，签名时间戳刷新到当下（客户才验得过）。
4. **失败不吞掉**：网络错、超时、4xx、5xx 都必须落一条投递记录，写明尝试次数、HTTP 状态、失败原因；到点必重试，次数用完必须转终态。
5. **租户隔离**：端点与投递记录严格按工作区隔离，别人的资源一律 404（不泄露"存在与否"）。

**三个最常见的事故**：签名密钥明文落库或能被 GET 读出 → 任何人都能伪造客户的入站请求；重试时重新序列化请求体 → 客户验签永远失败；没有租户上下文时静默不投递 → 客户收不到事件，且平台这边一条记录都没有。

配套文件：`contract.md`（黑盒契约 + 规则→用例追溯表）、`acceptance-plan.md`（29 条黑盒用例）、`decisions.md`（需人来拍板的决策点）。

## 这个模块是什么

- **边界**：入站方向（客户→平台的回调）和"业务事件本身的定义"都不属于它。它只消费别人发出来的领域事件，往客户 URL 上投。
- **核心对象**：端点（endpoint）、事件（event）、投递（delivery）、投递尝试（attempt）。一次事件打到 N 个端点 = N 条投递；每条投递有 M 次尝试。
- **消费者**：买方的客户。他们会自己写去重、自己验签、自己决定是否重放。所以**语义稳定**比功能多更重要。
- **交付形态**：一次投递 = 一次 HTTP POST（JSON）+ 3 个签名相关头。投递必须异步执行，管理接口不等目标响应。

## 成熟版应该有什么（按 MVP → 成熟分层）

**MVP（能跑通一次投递）**
- M1 端点注册：按工作区增删查端点（URL + 订阅的事件类型）。
- M2 签名密钥一次性下发 + HMAC 签名交付。
- M3 事件发布：按订阅投递到各端点（异步，至少一次）。
- M4 有限次重试：失败后退避重试，次数有上限。
- M5 投递日志：能看到投递状态、尝试次数、HTTP 状态码。

**可用（v1，能上生产）**
- M6 URL 校验与出站安全：只允许 http/https、禁凭据 URL、禁私网/链路本地目标。
- M7 端点启停与订阅更新：客户能停用某个端点而不删它。
- M8 密钥轮换：换密钥时旧密钥有一段双活窗口。
- M9 重放：客户能把某次投递原样再发一次。
- M10 幂等键：同一个业务事件重复发布只投一次。
- M11 留存策略：日志到期清理，响应体只留片段。
- M12 权限：只有具备 webhook 管理权限的成员能改端点、看全量日志。
- M13 签名自检接口：客户能贴一组头+body 让平台告诉他验签是否通过。

**成熟（可运营）**
- M14 端点健康度：连续失败自动停用，恢复后自动或手动启用。
- M15 事件目录与负载版本：事件类型有目录，负载带 schema 版本。
- M16 客户自助门户：客户自己查端点、看日志、点重放、导出。
- M17 出口 IP 固定：给客户一张放行清单（客户侧防火墙只放行平台出口 IP）。
- M18 指标与告警：投递成功率、延迟、重试量可观测并可告警。
- M19 端点归属验证：新增端点时做一次所有权挑战，确认是客户自己的服务器。
- M20 负载脱敏开关：按事件类型决定是否带敏感字段。
- M21 批量/定时重放与死信重投：跨一段时间批量重放失败的投递。

## 每项的正确行为

- **M1** 端点属于**当前工作区**，创建返回 201 与端点 id；同一 URL 可注册多次，互不影响。
- **M2** 明文密钥**只在创建/轮换响应里出现一次**；之后任何读接口都不返回明文。签名覆盖**整个实际发出的 body 字节**。
- **M3** 一次发布对每个"订阅了该类型且处于启用状态"的端点各产生**一条**投递；不匹配也要说清楚（返回匹配到的端点数），不能静默。
- **M4** 失败后进入"等待下一次"，退避间隔单调不减；未到 `nextAttemptAt` **不得**再试，到点**必须**再试。
- **M5** 投递记录含：投递 id、端点 id、事件类型、事件 id、状态、尝试次数、下次重试时间、每次尝试的 HTTP 状态与失败原因。
- **M6** 非法 scheme、带凭据的 URL、缺主机 → 400；`http://` 指向非回环地址 → 400；私网/链路本地/运营商级 NAT 字面量目标 → 400。**回环地址只在测试模式下放行**（验收需要一个本地接收器）。
- **M7** 停用的端点**不接收**新投递，但历史记录与配置保留，随时可恢复。
- **M8** 轮换后新密钥立即生效；旧密钥在双活窗口内**仍然能验签通过**，窗口过后一律拒绝。旧密钥靠"并存两份"实现，**不能**靠"留个摘要再重算"（摘要不可逆，重算必然失败）。
- **M9** 重放产生新的投递 id 与新的尝试链；原投递的状态与尝试次数**不变**；任何终态的投递都能重放。
- **M10** 同一工作区内相同幂等键在窗口内只产生一次投递；并发提交相同幂等键也只产生一次。
- **M11** 投递记录到期删除；客户响应体最多留 1024 字节片段。
- **M12** 写操作要求 webhook 管理权限，缺失返回 403；读权限可以更宽。跨工作区一律 404。
- **M13** 自检接口对正确签名放行、对篡改/过期/错密钥给出可区分的失败原因，且**不泄露**任何密钥信息。
- **M14** 连续失败达阈值自动停用；停用后不再投递；恢复后不自动重投旧事件。
- **M15** 事件类型有目录与版本；负载版本变化时旧事件仍按旧版本投递。
- **M16** 门户是本模块 API 的前端，**不新增**后端能力，不绕过权限。
- **M17** 出口 IP 集合稳定且有文档；轮换出口 IP 要提前通知并保留旧 IP 一段时间。
- **M18** 指标按工作区/端点维度可查；告警基于"成功率突降"而不是"单次失败"。
- **M19** 新增端点先发一次挑战请求，客户回带令牌才算激活；未验证端点不接收业务事件。
- **M20** 脱敏在**投递前**完成，日志里也不留原文；不可逆脱敏必须保证客户拿到的字段名稳定。
- **M21** 批量重放复用单次重放的语义（新投递 id、同 body），并且可限量、可暂停。

## 容易做错的地方（具体到会出什么事故）

1. **重试时重新序列化 JSON** → 键顺序/空格一变，客户按收到的字节算出的签名对不上，客户系统静默丢弃所有事件。必须签"实际发出的字节"。
2. **签名串漏了时间戳或用了发送时刻而非头里的值** → 客户按自己实现算不出同一个值，验签必失败。
3. **没有版本前缀（直接放裸 hex）** → 以后换算法/换密钥时无法同时兼容新旧，客户被迫停机升级。
4. **轮换密钥立刻废掉旧密钥** → 客户没来得及更新就全量丢事件，且他们自己查不出原因。
5. **签名密钥明文落库 / GET 能读出** → 数据库泄露或越权即可伪造客户的入站请求（假"付款成功"、假"工单关闭"）。密钥必须加密存储、只一次性下发。
6. **重放沿用原时间戳与原签名** → 客户按防重放窗口直接拒收，重放功能等于没有。
7. **重放改写原投递的状态** → 客户的排障视图被污染，"这条到底成功没有"永远说不清。
8. **没有租户上下文就静默返回** → 事件被无声丢弃，客户收不到、平台查不到，双方都以为对方坏了。
9. **失败不落记录 / 失败后无限重试** → 前者客户投诉没收到却无从查证；后者对客户服务器造成放大攻击，客户会直接封禁你的出口 IP。
10. **4xx 当成可重试** → 客户的错误配置（404/401）被重试放大；应视为永久失败，只有 429、5xx、网络错误与超时才重试。
11. **跟随 3xx 跳转** → 客户服务器把请求 302 到内网地址，平台替客户打了内网（SSRF）；且客户以为只收到一次。
12. **投递日志无限增长、完整保存客户响应** → 存储被单个大客户打爆；客户的响应里常带着 token，落库即泄露。
13. **跨工作区用 403 而不是 404** → 通过状态码差异就能枚举出"别家有没有这个端点"。
14. **只信 `X-Forwarded-For` 最左边一跳** → 客户伪造最左值即可污染日志/限流判定。
15. **事件体不设上限** → 一个大 payload 打爆内存与客户服务器。

## 与其他模块的接口

| 模块 | 接口含义 |
|---|---|
| auth | 提供会话与账号状态（停用/未验证）；本模块所有接口都需要已认证会话 |
| workspaces-and-permissions | 解析当前工作区与成员权限（webhook 管理权限），本模块的所有隔离判定都基于它 |
| async-jobs | 承载投递执行与"延迟到下次重试"的调度 |
| rate-limiting | 管理接口与事件发布的限流，避免一个客户刷爆平台出口 |
| notifications | 端点连续失败被自动停用时通知客户（站内信/邮件） |
| email-transactional | 若需要邮件通知走它；outbox 模板名形如 `webhooks-outbound.<name>`，链接放 `data.link` |
| observability | 投递成功率、延迟、重试次数的指标与告警 |
| audit-and-data-export | 端点增删改、密钥轮换、重放的审计记录与导出 |
| feature-flags | 灰度新的事件类型或新的投递/重试策略 |
| usage-metering-and-budgets | 按投递量计费或设配额时，读取本模块的投递计数 |
| web-security | 出站请求的 SSRF 防护、证书校验、出口 IP 策略 |
| file-storage | 投递日志/审计导出的文件落地 |

## 不做什么

- 不接收客户的入站回调（客户→平台的方向不在本模块）。
- 不定义业务事件本身：事件类型与负载由各业务模块给出，本模块只负责投递。
- 不做事件总线/消息队列的实现细节，那属于 async-jobs。
- 不做客户门户的前端 UI，只提供 API；UI 由宿主负责。
- 不发送邮件或站内信，只把"该通知了"这件事交给 notifications / email-transactional。
- 不依赖任何特定第三方网关或厂商 SDK，也不托管客户的端点。
- 不做入站限流的实现，只承受 rate-limiting 的判定。
- 不保存客户的完整响应体，也不把事件正文写进日志文件。
- 不负责让第三方厂商的事件目录来决定本平台发什么事件。
