# webhooks-outbound 决策点（需要人来拍板）

每条给出推荐默认与"选别的会怎样"。★ 表示一旦定下就难改。

## D1 ★ 签名方案与版本前缀
- **推荐默认**：HMAC-SHA256，签名串 = `<时间戳>.<原始 body 字节>`，小写 hex，头里写 `v1=<hex>`，时间戳单独成头。
- **选别的后果**：只放裸 hex → 换算法或密钥时无法新旧并存，客户被迫停机升级；时间戳塞进 body → body 格式一改就全线验签失败。

## D2 ★ 签名密钥怎么存、怎么轮换
- **推荐默认**：加密存储（可逆），明文只在创建/轮换响应出现一次；轮换时新旧两份并存，旧密钥按窗口到期销毁。
- **选别的后果**：只存摘要 → 算不出正确签名（签名需要原文；这是"存哈希"的唯一例外）；"留摘要再重算"续命 → 摘要不可逆，重算必失败；轮换即废旧密钥 → 客户没更新就全量丢事件。

## D3 失败怎么分类
- **推荐默认**：5xx、429、网络错误、超时 → 可重试；其余 4xx（400/401/404）→ 永久失败，不重试。
- **选别的后果**：4xx 也重试 → 客户错误配置被放大成打垮客户的流量；5xx 当永久失败 → 一次抖动就变永久丢事件。

## D4 ★ 跳转与私网目标
- **推荐默认**：不跟随 3xx（记 3xx 为失败）；生产拒绝一切回环/私网/链路本地目标，`TEST_MODE=1` 只放行回环。
- **选别的后果**：跟随跳转 → 必须每跳重做 SSRF 校验，否则平台替客户打内网；生产放行私网 → 直接是 SSRF 入口；一刀切禁回环 → 联调与验收都做不了。

## D5 重放语义
- **推荐默认**：重放 = 新投递 id + 完全相同的 body 字节 + 刷新到当下的签名时间戳；原投递的状态与尝试次数不动；任何终态都能重放。
- **选别的后果**：沿用原时间戳 → 客户防重放窗口直接拒收，重放等于没有；复用原投递 id → 客户分不清"重试"与"重放"。

## D6 幂等键是否强制
- **推荐默认**：强制支持 `Idempotency-Key`，同工作区同键在窗口内只投一次，重复请求返回首次的事件 id 与投递 id。
- **选别的后果**：不强制 → 上游一次网络重试就变成两次业务投递，客户重复入账。

## D7 尝试次数与退避
- **推荐默认**：总尝试次数 3~10（由 `params.maxAttempts` 声明），指数退避加抖动，用尽后转终态 `failed`。
- **选别的后果**：上限太高 → 长期故障的客户被持续打；退避不带抖动 → 端点集中恢复时形成尖峰。

## D8 投递是否异步
- **推荐默认**：投递走 async-jobs 的延迟队列，管理接口入队即返回，不等目标响应。
- **选别的后果**：同步投递 → 客户一个慢接口就拖住业务请求，超时行为不可预期。

## D9 跨租户错误码
- **推荐默认**：别家资源一律 404（`endpoint_not_found` / `delivery_not_found`）。
- **选别的后果**：用 403 → 靠状态码差异就能枚举出别家有没有这个端点。

## D10 日志留存与响应片段
- **推荐默认**：投递记录保留不超过 30 天（`params.retentionDays`），目标响应体最多存 1024 字节片段。
- **选别的后果**：存完整响应 → 客户响应里的 token 落库即泄露；不截断 → 一次大响应就能把存储打爆。

## D11 事件类型是否用清单限制
- **推荐默认**：不强制清单，任意非空字符串都可订阅；清单作为可选增强（`params.eventTypes`）。
- **选别的后果**：强制清单 → 上游发新类型忘了加，客户静默收不到；完全无清单 → 客户订阅到平台永不发的类型，投递为空却查不出原因。

## D12 是否提供签名自检接口
- **推荐默认**：提供（给一组头 + body，回是否通过与失败原因）；失败原因可区分（过期/不匹配/未知版本）但绝不回显密钥。
- **选别的后果**：不提供 → 客户只能靠对比日志排查，定位一次签名问题要几天。
