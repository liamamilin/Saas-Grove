# file-storage 需要人拍板的决定

每条给出默认选项与"选另一个会怎样"。默认项已写进 `contract.md` 的 MUST；改动默认项等于改动契约，需要同步改 contract 与验收计划。

## D1 下载走应用还是走存储
**选项** A 应用中转 + 一次性票据（推荐）｜B 存储直连预签名地址
**后果** 选 A 能即时撤销、能复核租户、能审计每次取字节，代价是应用带宽与内存压力（大文件可例外走 B）；选 B 省资源，但租户复核与撤销只发生在签发那一刻，地址进了日志就等于长期泄露。

## D2 上传是三段式还是一步到位
**选项** A 领票据 → 直传 → 完成校验（推荐）｜B 应用代收
**后果** 选 B 少一次往返、实现简单，但应用内存承载文件体，且无法在入库前判断实际字节与真实类型（伪装成图片的 HTML 会落地）；选 A 多一次交互，换来限额与类型真正生效。

## D3 令牌长什么样、存什么
**选项** A ≥128 bit 随机令牌 + 库中只存 SHA-256（推荐）｜B 用户可猜或短令牌
**后果** 选 A 令牌可放进 URL 且被查库拿到也无法还原；选 B 必须改用慢哈希（不可放进 URL、不可高频比对），且要额外设计找回通道。

## D4 哈希方案要换怎么办
**选项** A 新旧摘要双键并存，旧令牌自然过期后下线旧键（推荐）｜B "重算"库里旧摘要
**后果** 选 B 不可行——库里没有明文，根本算不出旧摘要；强行迁移只能把所有未过期令牌作废，用户手里的链接集体失效。

## D5 类型策略用允许列表还是拒绝列表
**选项** A 默认允许列表（推荐）｜B 默认拒绝列表
**后果** 选 B 新类型默认放行，一个没被想到的危险类型就绕过去了（SVG、XML、JS 变体）；选 A 宿主必须按业务补全列表，补不全表现为"某个类型传不上去"，比"传上去被执行"安全得多。

## D6 下载时 Content-Type 怎么给
**选项** A 只有 png/jpeg/gif/webp 可内联，其余一律 `attachment`（推荐）｜B 按用户声明的类型原样回显
**后果** 选 B 就是存储型 XSS 的入口：用户传 HTML/SVG，你按声明回源渲染，脚本在你的域名下执行、能读同源 Cookie；选 A 浏览器无法内联渲染用户内容，代价是没有图片预览之外的在线预览。

## D7 配额在本模块还是计费模块
**选项** A 本模块按 workspace 占用字节卡上限，计费模块只收数（推荐）｜B 完全交给 usage-metering-and-budgets
**后果** 选 B 配额会滞后于实际占用（计费链路有延迟），一个大租户可以在延迟窗口里写满存储；选 A 需要两个模块口径一致（占用字节的算法必须写进契约）。

## D8 配额什么时候记账
**选项** A 领票据即按声明字节占位，删除或拒绝后释放（推荐）｜B 只按 ready 文件的实际字节
**后果** 选 B 额度只在完成后才扣，一批并发完成可以瞬间超限（先斩后奏）；选 A 会让未完成的票据也占额度，所以 pending 过期回收必须存在（R17）。

## D9 删除是软删还是硬删
**选项** A 软删 + 异步物理清理（推荐）｜B 立即硬删
**后果** 选 B 审计与数据导出无法复现"删过什么"，误删不可挽回，物理删除失败也没有重试入口；选 A 需要一套清理任务（交给 async-jobs），并明确保留期。

## D10 pending 回收靠定时还是靠惰性
**选项** A 由 async-jobs 定时清理（推荐）｜B 只在请求时顺手判断
**后果** 选 B 长期没人访问的工作区里，过期票据永远留在库里（占额度、占元数据），除非碰巧有人来查。

## D11 客户端 IP 怎么取
**选项** A 宿主声明 `trustedProxyHops`，从 `X-Forwarded-For` 右取（推荐）｜B 直接取最左一项
**后果** 选 B 客户端随手伪造一个头就能污染审计里的 IP，事故追溯指向错误的人；选 A 需要宿主准确声明前面有几层可信代理，多一层少一层都会取错。

## D12 上传失败要不要通知用户
**选项** A 发 outbox 消息（template `file-storage.upload_failed`，链接放 `data.link`，推荐）｜B 静默失败
**后果** 选 B 用户只看到上传没成功，不知道字节已被丢弃、也不知道配额为什么涨；选 A 通知会打扰人，所以只在"字节已落地但校验失败"时发。
