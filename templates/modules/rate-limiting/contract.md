# rate-limiting 契约（黑盒可验证）

本文件只写从外部能看见的行为：下列 MUST 必须在 HTTP、Cookie、outbox、数据库只读查询上可被检验，实现方式不限。宿主启动、测试钩子与依赖顺序见 `HOST.md`；概念名由宿主在 `module-map.json` 中映射，本文件不猜路径。

## 1. 前置条件

- 宿主必须在 `module-map.json` 中声明**至少一个限流端点**，否则本模块视为未实现（记"宿主未声明"，不计失败也不计通过）。
- 宿主必须先满足 auth 与 workspaces-and-permissions（`HOST.md` 第 5 节）；本模块的用例需要它们创建的账号与会话。

## 2. 概念（宿主在 `module-map.json` 里映射）

| 概念 | 用途 | 未声明时 |
|---|---|---|
| `rate-limiting.limits` | 限流条目表（在 `params` 中声明，条目通过 `concept` 指向下列概念之一） | 宿主未声明 |
| `auth.login` | 登录端点：爆破与账号维度限流的主要被测对象 | 跳过 |
| `auth.signup` | 注册端点：注册 spam 限流 | 跳过 |
| `auth.password_reset_request` | 找回密码端点：邮件炸弹限流（宿主可声明 `auth.forgot_password` 等别名） | 相关用例跳过 |
| `rate-limiting.authenticated_endpoint` | 一个**已认证**且声明为受账号维度限流的端点 | 跳过 |

验收只读 `module-map.json`，不猜路径；概念缺失时该用例记"宿主未声明"，单独统计。

## 3. 参数声明（宿主写在 `module-map.json` 的 `params` 里）

```json
{
  "params": {
    "rate-limiting": {
      "limits": {
        "login": {
          "concept": "auth.login",
          "accountMax": 5,
          "ipMax": 20,
          "windowSeconds": 60
        }
      },
      "trustedProxies": ["127.0.0.1/32", "::1/128"],
      "failureMode": "fail-open",
      "storage": { "kind": "database", "tables": ["rate_limit_counters"] },
      "errorCodeField": "error.code"
    }
  }
}
```

- `limits.<name>.concept`：条目作用的端点概念（一个端点可有多个条目）。
- `accountMax` / `ipMax`：账号维度 / IP 维度的单窗口上限；**缺哪个维度就没有该维度的配额**。`windowSeconds`：窗口长度（秒）。
- `trustedProxies`：可信代理 CIDR 列表；未声明即没有可信代理。`failureMode`：`fail-open`（存储不可用时放行）或 `fail-closed`（返回 503）。
- `storage.kind`：`database` 或 `external`；`storage.tables` 列出存计数的表。
- `errorCodeField` / `errorCodeValue`：429 错误码的字段路径与期望值，默认 `error.code` / `rate_limited`。

**数值界限（契约给界，宿主声明实际值）**：`accountMax ≤ 10`、`ipMax ≤ 100`、`windowSeconds ≤ 60`；未声明时验收按界限测（扫描到首次出现 429 即止，且触发不晚于界限 + 1 次）。阈值**不得硬编码在脚本里**，一律从 `params` 读取。

## 4. MUST 规则

每条给出规则、宿主必须能映射的概念、黑盒验法。案例编号见 `acceptance-plan.md`，追溯表在第 9 节。

### R-01 声明前置（概念：`rate-limiting.limits`）
- 规则：宿主至少声明一个限流条目（概念 + 上限 + 窗口），验收能读到其数值。
- 验法：读 `params`；缺失即本模块未实现。

### R-02 键空间隔离（概念：任意两条已声明条目）
- 规则：计数按 (限流条目, 维度, 归一化标识的哈希) 分桶；不同条目、不同维度、不同账号的计数互不影响。
- 验法：条目 A 耗尽后条目 B 仍放行；账号 A 耗尽后同 IP 的账号 B 仍放行；来源 C 在来源 B 耗尽后仍放行。

### R-03 客户端 IP 的确定与归一化（概念：任意受限端点）
- 规则：候选链 = `X-Forwarded-For` 条目（自左向右）+ 直连对端地址；从右向左跳过可信代理（`params.trustedProxies`），第一个非可信跳即客户端 IP；全为可信跳时用直连对端地址；直连对端不可信时**完全忽略** `X-Forwarded-For`。入键前必须归一（IPv6 压缩形式统一、去掉端口与方括号、IPv4-mapped 统一）。**不得取最左跳。**
- 验法：验收脚本直接在 HTTP 请求头写 `X-Forwarded-For`（逗号分隔多值，不依赖真实代理）；无可信代理时轮换该头不得绕过；可信代理时 `A, B` 与 `B` 必须同桶。

### R-04 账号维度键（概念：`auth.login`、`rate-limiting.authenticated_endpoint`）
- 规则：账号维度键 = 已认证请求取账号 id、凭据型端点取提交的账号标识（规范化后）的哈希；键中**不得含账号状态字段**，也不得含明文邮箱。账号维度计数与来源无关。
- 验法：账号 A 在来源 1 耗尽后在来源 2 仍被拒；账号 A 耗尽不影响同 IP 的账号 B。

### R-05 配额触发与状态码（概念：`auth.login`、`auth.signup`、`auth.password_reset_request` 等任意受限端点）
- 规则：同一桶在一个窗口内计数达到 `max` 后，后续请求一律返回 **429**（不得是 401 / 403 / 402 / 503），触发不晚于第 `max + 1` 次、不得提前。
- 验法：连打 `max + 1` 次检查状态码。

### R-06 失败计入配额（概念：`auth.login`）
- 规则：请求只要到达限流点就计数，无论最终 2xx 还是 4xx（密码错、账号不存在、参数非法同样占配额）。
- 验法：用错误密码连打 `max + 1` 次，最后一次必须是 429 而非 401。

### R-07 不去重，含重放（概念：`auth.login`、`auth.password_reset_request`）
- 规则：请求内容、幂等键、token 完全相同的重复请求**各计一次**，不得因重复而复用配额；重放已用过的单次令牌不得被当作新配额放行，也不得因此免计配额。
- 验法：连发同一请求 `max + 1` 次，第 `max + 1` 次是 429；同一找回密码 token 连打两次，两次都被计数且第二次不是 2xx（令牌已用过）。

### R-08 并发原子（概念：任意受限端点）
- 规则：`max + 2` 次并发请求中放行（2xx）数 **≤ max**；并发结束后该桶计数已达 `max`（再发 1 次必须 429）。不得先查后加导致超发或丢计数。
- 验法：并发发起 `max + 5` 次并统计 2xx 与 429，随后补发 1 次。

### R-09 窗口过期放行（概念：任意受限端点）
- 规则：最后一次被计数请求之后超过 `windowSeconds`，同一桶必须重新放行；计数器会过期，不存在永久锁死。
- 验法：`POST /api/__test__/clock {advanceSeconds: windowSeconds + 1}` 后重发必须放行。

### R-10 429 不延长窗口（概念：任意受限端点）
- 规则：返回 429 的请求本身不重置窗口、不延长窗口长度；窗口仍按最后一次被计数请求起算。
- 验法：触发 429 后推进 `windowSeconds - 1` 秒仍是 429，再推进 2 秒（累计超过窗口）必须放行。

### R-11 `Retry-After`（概念：任意受限端点）
- 规则：429 响应必须带 `Retry-After` 头，整数秒，`1 ≤ 值 ≤ windowSeconds + 1`。
- 验法：读响应头。

### R-12 错误体与稳定错误码（概念：任意受限端点）
- 规则：429 响应体是 JSON，含可机器识别的错误码（默认 `error.code = "rate_limited"`，字段路径见 `params.errorCodeField`），且不含"用户不存在 / 已禁用 / 未验证"之类账号状态词。
- 验法：解析 429 响应体。

### R-13 不可缓存（概念：任意受限端点）
- 规则：429 响应必须带 `Cache-Control: no-store` 或含 `no-store` / `no-cache` 的值，不得被客户端或中间层缓存。
- 验法：读响应头。

### R-14 不回显（概念：任意受限端点）
- 规则：429 的响应体与响应头不得出现原始客户端 IP、原始邮箱、账号 id、token 等标识。
- 验法：在 429 响应全文检索本次用过的 IP 串、邮箱串、账号 id 串。

### R-15 端点隔离（概念：任意未被 `limits` 覆盖的已映射端点）
- 规则：限流只作用于已声明的端点；未声明端点不受影响（不存在全局一个桶）。
- 验法：耗尽一个条目后访问另一个未受限端点必须成功。

### R-16 会话不失效（概念：`rate-limiting.authenticated_endpoint` 或任一已认证端点）
- 规则：限流不得使已签发的会话失效，也不得改写成功响应的业务内容。
- 验法：登录成功并触发限流后，用同一会话访问未受限端点必须成功。

### R-17 健康检查豁免（概念：宿主固定路径 `/api/health`）
- 规则：`GET /api/health` 在任何限流状态下都返回 200（探针与就绪检查不被限流）。
- 验法：耗尽配额后再请求。

### R-18 测试支撑接口豁免（概念：宿主固定路径 `/api/__test__/*`）
- 规则：`/api/__test__/*`（outbox、clock、清空计数）不受客户端限流影响，否则验收自身会被卡死。
- 验法：耗尽配额后再调用。

### R-19 枚举安全（概念：`auth.login`、`auth.password_reset_request`）
- 规则：同一端点对**账号状态不同**（不存在 / 存在但凭证错 / 未验证 / 禁用）的请求，状态码与错误码必须完全一致，响应不得出现账号状态词；限流不得让其中一种状态变成 429 而其他状态不是。
- 验法：四种账号各发一次，比较状态码与 `errorCodeField` 值。

### R-20 触发点一致（概念：`auth.login`）
- 规则：限流触发位置与账号状态无关：对不存在账号连打，第 `max + 1` 次同样是 429，与对存在账号的触发点一致。
- 验法：两种邮箱各连打到首次出现 429，比较出现 429 的请求序号。

### R-21 限流键不取自客户端可伪造头（概念：任意受限端点）
- 规则：客户端 IP 只能来自 R-03 定义的链；不得取自 `X-Real-IP`、`X-Client-IP`、`Forwarded` 等客户端可自行设置的头。
- 验法：轮换这些头，计数不变。

### R-22 存储哈希（概念：`params.storage`）
- 规则：限流存储中的身份标识必须是哈希形态，不得明文保存 IP、邮箱、账号 id；数据库**任何表**都不得出现本模块用过的原始客户端 IP 明文；若 `params.storage.kind = "database"`，`params.storage.tables` 列出的表内不得出现明文邮箱或明文账号 id，存储值必须呈现为不可逆摘要形态。
- 验法：用 `DATABASE_URL` 只读查询：任何表检索原始 IP 串应为 0 命中；声明的限流表检索原始邮箱与账号 id 串应为 0 命中。

### R-23 无副作用（概念：`auth.signup`）
- 规则：被 429 拒绝的请求不产生业务副作用（不创建账号、不扣费、不发邮件、不入队）。
- 验法：用新邮箱触发注册限流后，该邮箱随后登录必须失败（账号未创建）。

### R-24 参数界限（概念：`params.rate-limiting.limits`）
- 规则：`accountMax ≤ 10`、`ipMax ≤ 100`、`windowSeconds ≤ 60`；宿主声明越界时，验收按契约界限测并记"声明越界"。
- 验法：读 `params` 比对界限。

## 5. 状态码与错误体（唯一真相，其他文件与此一致）

| 情况 | 状态码 | 响应体 |
|---|---|---|
| 超过配额 | **429** | JSON，含 `error.code`（默认 `rate_limited`）与人类可读 `message`；必带 `Retry-After`，必带 `Cache-Control: no-store` |
| 未超过配额 | 端点自身语义 | 端点自身语义（本模块不改写） |
| 认证失败 / 账号状态差异 | 由 auth 契约决定，但**各账号状态之间必须完全一致** | 本模块不区分账号状态 |
| 配额存储不可用 | 由 `params.failureMode` 决定：`fail-open` 放行 / `fail-closed` 返回 503 | `fail-closed` 建议同 429 信封但错误码不同 |
| 预算或套餐问题 | 402 / 4xx | 属 usage-metering-and-budgets、payments-billing，**不得**用 429 表达 |

## 6. 必须哈希存储的数据

| 数据 | 存储形态 | 说明 |
|---|---|---|
| 客户端 IP | 哈希（HMAC 优于裸 SHA-256） | 明文 IP 不得出现在任何表、任何日志、任何响应里 |
| 账号标识 / 账号 id | 哈希 | 账号维度键不得含明文邮箱 |
| 账号状态 | 不得入键 | 键里出现状态字段即制造枚举侧信道 |
| 令牌 / token | 不得入键 | 也不得出现在 429 响应里 |

## 7. 不变量

- INV-1 任一窗口内，某桶的放行数 ≤ 其 `max`。
- INV-2 拒绝永远是 429 + 同一错误码，不随账号状态、来源或语言变化（`message` 可本地化）。
- INV-3 被拒请求无业务副作用。
- INV-4 限流只决定放行与否，不改写业务响应内容。
- INV-5 同一标识在同一窗口内稳定映射到同一个桶。
- INV-6 计数器必然过期，不存在永久锁死。
- INV-7 同一账号的所有请求限流结果一致，不因凭据对错而不同。

## 8. 建议，验收不测

- 计数存储的实现（缓存服务 / 数据库表）与表结构、分区、索引。
- 哈希盐的轮换周期与密钥管理。
- 滑动窗口与令牌桶在数值上的细微差别（契约只要求触发点与放行数）。
- 成功响应是否附带 `X-RateLimit-Limit / Remaining / Reset`（建议附，不强制）。
- 限流判定的耗时量级与公平性；内部豁免名单的存储与界面。
- 429 `message` 的本地化文案（internationalization）；失败模式的具体降级实现。
