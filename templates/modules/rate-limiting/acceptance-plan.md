# rate-limiting 验收计划（黑盒）

## 1. 执行约定

- **数值从哪来**：M = 账号维度上限（`accountMax`）、I = IP 维度上限（`ipMax`）、W = 窗口秒数（`windowSeconds`），全部读 `module-map.json` 的 `params.rate-limiting.limits`；未声明时用契约界限（M ≤ 10、I ≤ 100、W ≤ 60）。两个维度任一耗尽即拒绝，因此**最先触发的序号 K = min(M, I)**。**脚本里不写死任何阈值。**
- **怎么隔离维度**：测账号维度用**同一个邮箱**连打；测 IP 维度用**每次不同的邮箱**（否则账号桶先满，IP 桶的问题被掩盖）。账号维度可被观察的前提是 I ≥ M + 1（否则 IP 桶先耗尽）。
- **每条用例开始前**：`DELETE /api/__test__/rate-limits` 清空计数；用全新账号（唯一邮箱），不共享状态。
- **路径**：只按 `module-map.json` 的概念取路径；`GET /api/health`、`GET /api/__test__/outbox?to=<email>`、`POST /api/__test__/clock {advanceSeconds}`、`DELETE /api/__test__/rate-limits` 是 `HOST.md` 规定的固定路径。
- **凭据从哪来**：账号用 `auth.signup` 创建；会话用 `auth.login` 换（Cookie 或响应体里的会话字段，字段名按 auth 契约）；单次令牌用 `GET /api/__test__/outbox?to=<email>` 取——outbox 的模板名是 `<模块>.<名>`（如 `auth.password_reset`），链接在 `data.link`，令牌明文在 `token` 字段，且明文只允许出现在名字含 `outbox` 的表。
- **怎么送 `X-Forwarded-For`**：验收脚本直接在 HTTP 请求头写该头，逗号分隔多值（如 `A, B`），不依赖真实代理；`X-Real-IP`、`X-Client-IP`、`Forwarded` 同样由脚本直接写。
- **账号状态**：不存在 / 存在但密码错 / 未验证 / 禁用，按 auth 契约能构造出来的状态取；某状态造不出来时，本用例只比较可得的状态，并在结论里注明。
- **未声明**：`params` 或概念缺失的用例记"宿主未声明"，不计失败也不计通过。
- **数据库**：只读查询 `DATABASE_URL`，仅用于检查限流存储是否明文（AC-27），不改数据。

## 2. 用例表

| id | given | action | expected | negative |
|---|---|---|---|---|
| AC-01 | `auth.login` 条目已声明，计数已清空 | 用 `auth.signup` 建的账号发 1 次正确登录 | 2xx；响应不是 429 信封；无 `Retry-After` | no |
| AC-02 | params 声明了 `auth.login` 的 M 与 I（K = min(M, I)） | 同一邮箱连打 K 次登录（密码错） | 全部不是 429（状态码等于端点自身语义，通常 401）；任何维度都不得提前触发 | yes |
| AC-03 | 同上 | 继续连打直到出现 429，最多到 K+1 次 | 首个 429 出现在第 K+1 次（params 已声明时不得早也不得晚）；状态码恰为 429，不是 401/403/402/503 | yes |
| AC-04 | 已拿到 429 响应 | 读响应头 | 有 `Retry-After`；值为整数字符串；1 ≤ 值 ≤ W+1 | yes |
| AC-05 | 已拿到 429 响应 | 解析响应体 | 是 JSON；`error.code`（或 `params.errorCodeField`）= `rate_limited`；不含"用户不存在/已禁用/未验证/not found/disabled/unverified" | yes |
| AC-06 | 已拿到 429 响应 | 读响应头 | `Cache-Control` 含 `no-store` 或 `no-cache` | yes |
| AC-07 | 已知本次用的 IP 串、邮箱串、账号 id | 检索 429 响应体与全部响应头 | 不出现这些串（大小写不敏感） | yes |
| AC-08 | `auth.login` 已耗尽；module-map 中存在未被 `limits` 覆盖的端点 | 请求该未受限端点 | 不是 429（限流不跨端点，也不存在全局桶） | yes |
| AC-09 | `auth.login` 声明 M 与 I，且 I ≥ M+2 | 账号 A 连打 M+1 次触发 429；再用全新账号 B（同 IP）发 1 次 | B 不是 429（账号维度独立；IP 桶仍有余量） | yes |
| AC-10 | 宿主声明了含回环的可信代理（可区分来源）；`auth.login` 声明 M 与 I，且 I ≥ M+1 | 账号 A 在来源 1 连打 M+1 次触发 429；换来源 2 用同一账号 A 发 1 次 | 仍是 429（账号维度与来源无关，跨来源累计） | yes |
| AC-11 | 宿主未声明可信代理（或不含回环）；params 声明了 I | 连发 I+1 次登录，每次用**不同邮箱**并轮换 `X-Forwarded-For`，同时轮换 `X-Real-IP`、`X-Client-IP`、`Forwarded` | 首个 429 出现在第 I+1 次（轮换这些头没有产生新桶，对端地址才是来源） | yes |
| AC-12 | 宿主声明了含回环的可信代理；params 声明了 I | ① 用 `X-Forwarded-For: A, B` 连发 I+1 次（每次不同邮箱）；② 用 `X-Forwarded-For: B` 发 1 次（新邮箱）；③ 用 `X-Forwarded-For: C` 发 1 次（新邮箱）；④ 用 `2001:db8::1` 发 1 次、再用 `2001:0db8:0000:0000:0000:0000:0000:0001` 连发 I 次（邮箱各不相同） | ① 第 I+1 次是 429（桶 = 最右侧 B）；② 仍是 429（同一桶，不是最左 A）；③ 不是 429（新桶）；④ 最后一次是 429（两种写法同桶，IP 已归一） | yes |
| AC-13 | 同 AC-12，来源 B 的桶已耗尽 | 用来源 C 与新邮箱发 1 次 | 不是 429（来源之间互不影响） | yes |
| AC-14 | 同一邮箱已用满 K 次但未触发 429 | `POST /api/__test__/clock {advanceSeconds: W + 1}`，再发 1 次 | 不是 429（窗口过期后放行） | yes |
| AC-15 | 已触发 429（连打 K+1 次） | 推进 W-1 秒发 1 次；再推进 2 秒发 1 次 | 前一次仍是 429；后一次不是 429（429 没有延长窗口，累计已超过 W） | yes |
| AC-16 | 账号 A 已由 `auth.signup` 创建（K = min(M, I)） | 用错误密码连打 K+1 次 | 第 K+1 次是 429 而不是 401（失败尝试同样计数） | yes |
| AC-17 | `auth.login` 条目已声明（K = min(M, I)） | 连发 K+1 次完全相同的登录请求（同一 body、同一幂等键） | 第 K+1 次是 429（重复请求不被去重） | yes |
| AC-18 | `auth.password_reset_request` 被声明为受限条目（其 M2、I2，K2 = min(M2, I2)） | 连打 K2+1 次找回密码请求 | 第 K2+1 次是 429（邮件炸弹被削掉） | yes |
| AC-19 | 可构造出的四种账号状态：不存在 / 存在但密码错 / 未验证 / 禁用 | 各发 1 次登录 | 四次响应的状态码相同、错误码字段值相同，且响应体不含账号状态词 | yes |
| AC-20 | `auth.login` 声明 M 与 I（K = min(M, I)） | 对不存在邮箱连打到首个 429（记序号 N1）；清空计数后对存在邮箱（错误密码）连打到首个 429（记 N2） | N1 = N2 = K+1（触发点与账号状态无关） | yes |
| AC-21 | 一个已存在邮箱与一个不存在的邮箱 | 各发 1 次找回密码请求 | 两次状态码相同、错误码相同；不能一个是 2xx 另一个是 429 | yes |
| AC-22 | 已触发 429 | `GET /api/health` | 200（探针不被限流） | yes |
| AC-23 | 已触发 429 | `GET /api/__test__/outbox?to=<本次邮箱>`；`DELETE /api/__test__/rate-limits`；`POST /api/__test__/clock {advanceSeconds: 1}` | 三者都成功（outbox 200 且能解析出 messages；DELETE 成功；clock 成功） | yes |
| AC-24 | 账号 A 已登录并持有会话凭据 | 触发账号 A 的限流；再用同一会话请求一个未被 `limits` 覆盖的已认证端点 | 该端点返回 2xx（限流不让会话失效，也不改写业务响应） | yes |
| AC-25 | `auth.login` 声明 M 与 I（K = min(M, I)）；已创建有效账号（正确密码） | 并发发 M+5 次正确登录请求（同一账号） | 2xx 数量 ≤ K（正确实现应恰为 K）；429 数量 ≥ 5；绝不允许 2xx 超过 K | yes |
| AC-26 | AC-25 刚完成 | 再发 1 次登录 | 429（并发后计数未丢失，桶已满） | yes |
| AC-27 | `params.storage.kind = "database"` 且给出表名；已知本次用的 IP 串与邮箱串 | 用 `DATABASE_URL` 只读查询全部表的可读文本列 | 任何表都不出现原始 IP 串；声明的限流表内不出现原始邮箱或账号 id；存储值呈哈希形态（长度 ≥ 32 的十六进制或等价摘要） | yes |
| AC-28 | `auth.signup` 被声明为受限条目（M2、I2、K2 = min(M2, I2)）；计数已清空 | 用全新邮箱连打 K2+1 次注册（最后一次 429）；`DELETE /api/__test__/rate-limits`；用该邮箱与密码登录 | 登录不是 2xx（被 429 的请求没有创建账号） | yes |
| AC-29 | 找回密码条目声明了 M2、I2、K2；确认重置的端点由 auth 契约给出且令牌可从 outbox 取到 | 用同一 token 连续请求确认端点两次；随后再对该端点连打 K2+1 次 | 前两次不是同时 2xx（令牌单次有效，重放被拒）；连打时第 K2+1 次是 429（令牌尝试同样计入配额，未被去重） | yes |

## 3. 硬负例分布

- **隔离**：AC-08（端点间）、AC-09（账号间）、AC-13（来源间）。
- **绕过与伪造**：AC-11（轮换可伪造头）、AC-12（XFF 最左 / 最右、IP 写法归一）、AC-17（重复请求去重）、AC-29（单次令牌重放）。
- **配额边界**：AC-02（不提前触发）、AC-03（触发点必须落在 K+1）、AC-14 / AC-15（窗口过期与不延长）。
- **竞态**：AC-25（并发不超发）、AC-26（并发不丢计数）。
- **枚举与泄露**：AC-19、AC-20、AC-21（账号状态一致）、AC-07（不回显）、AC-27（存储哈希）。
- **误伤与副作用**：AC-08、AC-22、AC-23（豁免）、AC-24（会话）、AC-28（无副作用）。
