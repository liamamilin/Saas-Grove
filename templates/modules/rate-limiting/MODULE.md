# rate-limiting 认知模板

> 面向编码代理：你要在买家自己的技术栈里落地按 IP / 按账号限流、滥用控制与 429 行为。
> 本文件讲成熟版应该是什么样，不给实现代码。契约见 `contract.md`，验收计划见 `acceptance-plan.md`，取舍见 `decisions.md`，宿主约定见 `HOST.md`。

## 必读摘要（一页）

**一句话**：给一次请求套配额——**谁**（客户端 IP / 账号）、**多长时间**（窗口）、**最多几次**（max）；超了返回 429 与 `Retry-After`，让客户端知道该等多久再试。

**三根支柱**
1. **认对人**：客户端 IP 只能取自 `X-Forwarded-For` 链的**最右侧非可信跳**或直连对端，**绝不取最左跳**；账号维度用账号 id（登录类端点用提交的账号标识）。
2. **算对账**：共享存储、原子自增、滑动窗口；**失败请求同样计数**；并发不得超发（先加后判，再决定放行）。
3. **回得对**：429 + 稳定错误码 + `Retry-After` + `Cache-Control: no-store`；不回显原始 IP / 邮箱；限流结果**不因账号状态而异**（不存在 / 存在 / 未验证 / 禁用都得一样）。

**最容易出事故的六处**
- 取了 XFF 最左跳 → 轮换一个头就绕过全部限流：撞库、注册 spam、邮件炸弹畅通。
- 只按 IP 或只按账号限流 → 分布式撞库、单 IP 批量注册畅通。
- 用进程内存计数 → 多实例的实际限额 = 声明值 × 实例数，保护形同虚设。
- 429 泄露账号存在性（存在 429、不存在 200）→ 账号枚举可被自动化。
- 计数器存储故障直接抛错 → 全站 500；静默放行 → 限流形同不存在。
- 429 被缓存 → 窗口过后客户端仍被拒，用户以为账号坏了。

**四条硬约束**
- 只限**显式声明的**端点，不做全局一个桶。
- 计数键用**哈希**，不落明文 IP / 邮箱 / 账号 id。
- 健康检查与测试支撑接口**永久豁免**。
- 计数窗口跟随**宿主测试时钟**，否则无法验收窗口过期放行。

**不归本模块**：上游模型调用速率（ai-model-gateway）、预算与额度扣减（usage-metering-and-budgets）、账号封禁与权限（auth、workspaces-and-permissions）、网络层 DDoS 防护。

## 这个模块是什么

限流是"在单位时间内限制某个来源能做多少次请求"的准入控制。它有两类配额维度：**按来源 IP**（防单机暴力）与**按账号**（防分布式撞库、防单个账号批量消耗资源）；两类通常**同时生效，任一耗尽即拒绝**。

它同时承担**滥用控制**的一部分职责：注册 spam、登录爆破、找回密码邮件炸弹、导出与上传滥用，都在限流这一层先被削掉流量。本模块只决定放不放行，**不解释业务语义**（配额用完不等于余额不足，那属于 usage-metering-and-budgets）。

成熟版与随手加个计数器的差别在三处：**只信可信代理给的来源**（直连对端不是自家代理时一律用对端地址）；**账目原子且共享**（所有实例写同一份计数，原子自增）；**拒绝可被客户端正确处理**（429 + 稳定错误码 + `Retry-After` + 不可缓存）。

## 成熟版应该有什么（按 MVP → 成熟分层）

### MVP（缺一不可，先做这些）

1. **少量关键端点有配额**：登录、注册、找回密码与验证码类端点各有一份单窗口最多 N 次的配额表。
2. **计数存共享存储**：多实例共用一个存储（数据库表或缓存服务），不是进程内存。
3. **超限返回 429**：带 `Retry-After`（整数秒）与稳定错误码，响应不缓存。
4. **豁免名单**：健康检查与内部测试接口永不受限流影响。
5. **计数键哈希化**：IP 与账号标识只以哈希形式出现在键名与存储里。
6. **失败尝试同样计数**：密码错、账号不存在、参数非法都占配额。

### 成长期

7. **双维度配额**：同一端点同时有 IP 上限与账号上限，任一耗尽即 429。
8. **可信代理判定**：显式声明可信代理 CIDR；正确解析 XFF 链；IP 入键前归一化。
9. **按端点分层的配额表**：不同端点不同阈值与窗口（登录严、上传宽、读接口可宽），不再全局共用一个桶。
10. **滑动窗口语义 + 原子计数**：并发下放行数不超过 max。
11. **失败模式策略**：计数器存储不可用时明确选择放行或拒绝，并告警。
12. **标准限流响应头**：`X-RateLimit-Limit / Remaining / Reset`（建议）。
13. **枚举安全**：限流维度不含账号状态字段；不同账号状态的响应完全一致。
14. **限流指标**：429 次数、拒绝率、耗尽时长（交给 observability）。

### 成熟期

15. **渐进惩罚**：重复违规升级（更长窗口、指数退避、临时封禁），TTL 到期自动解除。
16. **异常识别**：一个账号从大量 IP 出现、单 IP 大量账号、同一凭据高频失败 → 告警而不是直接封。
17. **分层配额**：按套餐与工作区等级给不同阈值（与预算语义分离）。
18. **豁免名单可配置**：内部服务身份、受信网段可豁免，默认关闭且留审计。
19. **管理员可观测**：只读查询某来源当前计数、剩余、重置时间。
20. **跨区域一致性**：多区域共享或明确最终一致策略，避免各区独立放行。
21. **自适应阈值**：依据历史峰值与误杀率调整阈值，由 feature-flags 灰度。
22. **限流事件进审计**：429 激增、封禁、豁免变更可被 audit-and-data-export 复盘，且不含明文 IP。

## 每项的正确行为

| 能力 | 正确行为（可被外部检验的一句话） |
|---|---|
| 配额判定 | 同一桶在一个窗口内计数达到 max 后，后续请求一律 429；触发不晚于第 max+1 次，也不得提前。 |
| 失败计数 | 密码错、账号不存在、参数非法与成功请求一样占配额。 |
| 不去重 | 内容与幂等键完全相同的重复请求各占一次配额（防复制同一请求绕过）。 |
| 客户端 IP | 链 = XFF 条目（左→右）+ 直连对端；从右向左找第一个非可信跳；对端不可信时完全忽略 XFF。 |
| 账号维度 | 已认证请求用账号 id；登录类端点用提交的账号标识；两者都取哈希入键。 |
| 原子且共享 | 所有实例写同一份计数，原子自增；并发 N 次请求的放行数 ≤ max，不出现先查后加导致的超发。 |
| 窗口过期 | 距最后一次被计数请求超过 window 后同一桶重新放行；计数器会过期，不存在永久锁死。 |
| 429 不延长窗口 | 被拒请求本身不重置窗口、不延长窗口长度。 |
| 响应头 | 429 必须有 `Retry-After`（1 ≤ 秒数 ≤ window+1）与 `Cache-Control: no-store`。 |
| 响应体 | 429 是 JSON，含稳定机器码（默认 `error.code = "rate_limited"`），不含账号状态词。 |
| 不回显 | 429 的体与头不含原始 IP、邮箱、账号 id、token。 |
| 端点隔离 | 配额按条目隔离：A 条目耗尽不影响 B 条目；账号 A 耗尽不影响同 IP 的账号 B。 |
| 枚举安全 | 账号状态不同（不存在 / 存在 / 未验证 / 禁用）时，状态码、错误码、触发点完全一致。 |
| 哈希存储 | 限流存储与审计里不出现明文 IP / 邮箱 / 账号 id。 |
| 豁免 | `GET /api/health` 恒 200；`/api/__test__/*` 不受客户端限流影响。 |

## 容易做错的地方（具体到会出什么事故）

| 错误做法 | 事故 |
|---|---|
| 取 XFF 最左跳 | 每次换 `X-Forwarded-For` 就换一个桶：撞库与注册 spam 无限打。 |
| 无条件信任 XFF（不判可信代理） | 同一事故但更隐蔽：请求全落进攻击者指定的桶，运维看到 IP 很散却查不出原因。 |
| 只按 IP / 只按账号限流 | 同一账号从几十个 IP 并发爆破照样得手；或一个 IP 批量注册、批量发信打爆通道。 |
| 只统计成功（或只统计失败）请求 | 爆破与注册 spam 不计数；或成功但昂贵的请求（上传、大导出）不受限，成本失控。 |
| 先查后加（check-then-increment） | 并发 100 个请求全部通过，一次创建 100 个账号或扣 100 次费。 |
| 用进程内存计数 | 多实例的实际限额 = 声明值 × 实例数，压测看不出来、线上被突破。 |
| 固定窗口（按时间片取整） | 窗口边界流量翻倍（60s 窗口在 59 秒与 60 秒处各打满一次）。 |
| 429 也计数并刷新窗口 | 用户越点越久地锁死，工单暴涨，最后只能重启服务。 |
| 全局一个桶 | 热点端点吃光配额，其他端点对所有人 429，现象是整个站都坏了。 |
| 429 泄露账号存在性 | 存在账号 429、不存在账号 200，攻击者拿现成邮箱列表枚举有效账号。 |
| 429 回显原始 IP / 邮箱 | 客户端日志、工单截图、CDN 日志到处是用户标识；同时说明存储没哈希。 |
| 键里存明文邮箱 / 明文 IP | 存储一旦泄露即可定位用户并反查限流键。 |
| 限流命中后仍执行了业务逻辑 | 账号被创建但客户端收到 429，重试又触发一次扣费或一次发信。 |
| 不豁免健康检查 / 测试接口 | 部署探针被限流则滚动发布雪崩；验收脚本被 429 卡死，测出的失败全是假象。 |
| 没给 429 加 `Retry-After` | 客户端固定间隔重试，限流没削峰，反而放大成重试风暴。 |
| 429 被 CDN 或浏览器缓存 | 窗口早就过了，客户端还在被拒。 |
| IP 未归一化就入键 | `::1` 与 `0:0:0:0:0:0:0:1`、`1.2.3.4:5678` 与 `1.2.3.4` 各算一个桶，换写法即绕过。 |

## 与其他模块的接口（只列模块名与接口含义）

| 模块 | 接口含义 |
|---|---|
| auth | 提供已认证主体标识（账号 id）作为账号维度限流键；本模块限流其登录、注册、找回密码端点，但不重写响应语义。 |
| workspaces-and-permissions | 只用于按套餐与工作区等级取阈值；成员身份不作为限流键。 |
| usage-metering-and-budgets | 预算耗尽与限流是两种拒绝，可共用 429 信封但错误码必须不同（`rate_limited` / `budget_exceeded`）。 |
| async-jobs | 任务提交入口可被限流；worker 内部调用走服务身份豁免，避免队列自锁。 |
| ai-model-gateway | 上游模型调用速率归它；本模块只限进入应用的请求，避免重复扣配额。 |
| payments-billing | 支付发起与回调入口限流（防重复扣费、回调风暴）；业务语义由它定义。 |
| audit-and-data-export | 限流事件（429 激增、封禁、豁免变更）进审计，且不得出现明文 IP。 |
| prompt-injection-and-guardrails | 内容安全判定排在限流之后：被 429 的请求不应进入内容审核流程。 |
| email-transactional、notifications | 触发发送的入口由本模块限，实际发送速率由它们负责，两边不重复计数。 |
| web-security | CORS、Origin 与请求头校验归它；限流键不得取自客户端可伪造的头（除受信代理的 XFF）。 |
| observability、analytics | 接收本模块的 429 计数、拒绝率、耗尽时长等指标（不得含明文 IP）。 |
| feature-flags | 阈值与豁免名单可由 flag 灰度覆盖，便于安全调参。 |
| internationalization | 429 的 message 按请求语言本地化；本模块只保证错误码稳定不随语言变。 |

## 不做什么

- 不做上游模型调用速率与模型配额（ai-model-gateway）。
- 不做预算、额度、余额的扣减与结算（usage-metering-and-budgets、payments-billing）。
- 不做账号封禁、解封、角色与权限判定（auth、workspaces-and-permissions）。
- 不做内容安全审核与人机校验（prompt-injection-and-guardrails、web-security）。
- 不做网络层 DDoS 防护（交给边缘、CDN、WAF），也不做套餐售卖规则。
- 不改写 outbox 模板命名与邮件发送实现（email-transactional）。
- 不在限流里塞业务判定（如余额不足、套餐不支持），否则客户端无法区分配额问题与业务问题。
