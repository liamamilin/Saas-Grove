# ai-retrieval 独立审查 r1

对象：MODULE.md（10.4KB）、contract.md（15.0KB）、acceptance-plan.md（10.7KB）、decisions.md（4.8KB），对照 HOST.md 与 modules.json。只读审查，未读 .env。篇幅均未超限（contract 离 17KB 只剩约 2KB，再补规则要同步删减）。未发现乱码和厂商品牌名。第 3 节引用的模块名都在 modules.json 里。

总评：骨架正确，隔离、引用逐字、空库不生成这几条底线都抓对了。主要问题集中在验收层。一是有一条用例与规则互斥（AC-27）。二是检索类用例依赖"假嵌入"的行为，而 HOST 没定义这个行为。三是"原文"这个比对基准没有定义，AC-05 只做了模块自己和自己的比对。四是追溯表有几处对不上。

## 一、阻断（1）

**B-1 [一致] AC-27 后半与 R-38 互斥或不稳定**
- 位置：acceptance-plan AC-27；contract R-38、R-40。
- 原因：AC-27 后半发两个"相同幂等键"的并发 ING，期望"另一个 409 `idempotency_conflict`"。可它没说两个请求体是否相同。
  - 体相同时：R-38 要求"同键同体 → 200 且返回首个 documentId"。第二个请求在第一个提交后到达，合规实现必须回 200，用例判失败。
  - 若合规实现在第一个未完成时回 409，结果又取决于谁先落库，用例不稳定。
  - 体不同时：409 是对的，但这与 AC-12 重复，且不是并发特有的风险。
  - 结论：体相同时没有合规实现能稳定通过。
- 修法：拆成两个断言。
  - (a) 同键异体并发：恰好一个成功，另一个 409 `idempotency_conflict`。
  - (b) 同键同体并发：两个响应都只能是 `{200/201 且 documentId 相同}` 或 `{一个成功 + 一个 409 且 code ∈ {idempotency_conflict}}`，最终文档数 == 1。
  - R-40 同步写明"同键同体并发允许其一返回 409 in-flight 或 200 重放，但不得产生两份文档"。

## 二、应修（13）

**S-1 [可执行] "原文"基准没有定义，引用比对是模块自己和自己比**
- 位置：contract 第 3 节（`start/end` 文档级偏移）、R-26/R-27、第 7 节"原文可被取回"；AC-05、AC-06、AC-29。
- 原因：
  - 契约没说偏移指向什么文本：是上传字节解码后的文本，还是解析/归一化后的文本。PDF 和 Markdown 解析后字符串与原字节并不相同。D-10 还说文档要做空白归一化，若归一化后再切，偏移就和上传内容错位。
  - 也没有任何概念能取回"整篇原文"（只有 DOC、CHS、CHK）。
  - AC-05 只比较"命中 text"和"CHK 的 chunk 区间"，两者都是模块产出，同源造假也能通过。
  - 唯一接近原文的是 AC-29 的"含 99.9%"。
- 修法：
  - 契约规定：对 text/plain、text/markdown，偏移基于"上传字节按 UTF-8 解码后的字符串，不做任何改写（不折叠空白、不剥 Markdown 语法）"。PDF 另说明基准是"提取文本"，并要求 CHS 的全部 chunk 拼接可还原它。
  - AC-05 增加一步：夹具文本已知，断言 `fixture_text[start:end] == hit.text`（按 `offsetUnit` 切片）。
  - AC-29 同理，对中文夹具做同样断言。

**S-2 [可执行] 假嵌入的行为未定义，`no_context` 分支不可达、也没有用例**
- 位置：HOST 第 3 节"假模型"（只有延迟、故障、usage、记录请求，无嵌入语义）；contract R-29、R-32、第 4 节 `contextStatus`；AC-02、AC-03。
- 原因：
  - 纯向量检索对非空库总能返回最近邻，除非有相似度阈值。契约没有阈值概念，也没说假嵌入怎么产生。
  - "有文档零命中 → `no_context`"在黑盒下造不出来，AC-02、AC-03 只测了 `empty_kb`。
  - AC-05 的"查独特词"能否命中，也取决于假嵌入。
  - R-29/R-32 的后一半因此名义上有用例，实际无断言。
- 修法：
  - 在 contract 第 2 节增加参数 `query.minScore`（可选），并在 HOST 的假模型里规定确定性嵌入。例如对文本取 SHA-256 展开为固定维度向量；再加"含 `__ORTHOGONAL__` 的输入返回与任何库内向量余弦为 0 的向量"，以便造"零命中"。
  - 增加一条用例 AC-31：有 ready 文档，查询用正交串，断言 `contextStatus=no_context`、`hits=[]`；ANS 同样无补全请求。
  - 若宿主不用阈值，则 `no_context` 记"宿主未声明"。

**S-3 [一致] 失败文档与去重死锁；MODULE 承诺的"可重试"没有对应概念**
- 位置：MODULE 底线 1、第 4 节"失败文档直接删掉不留错误"；contract R-11、R-12，第 1 节概念表。
- 原因：
  - R-11 保留失败文档，R-12 对"同工作区同内容"一律 409。于是 `embedding_failed` 这种瞬时故障之后，用户重传同一文件被 `duplicate_content` 拦住。
  - 没有重试概念，也没有"failed 不参与去重"的规则，用户只能先删再传。
  - MODULE 写了"失败…可重试"，契约和用例里却没有。
- 修法：
  - 加规则：去重与幂等只对 `state ∈ {pending, processing, ready}` 的文档生效；`failed` 文档同内容重传返回 201 新文档（或提供 `ai-retrieval.document.retry` 概念）。
  - 加一条用例：造 `failed`（空文本 PDF），再上传同内容，不得 409。
  - 同时写明 DEL 之后同内容可重新上传（见 G-1）。

**S-4 [可执行] AC-28 令牌用例的检查顺序和令牌使用方式都没写**
- 位置：contract R-41、第 4 节 TOK；AC-28。
- 原因：
  - AC-28 对同一枚令牌连续做"成功 → 重放 → 推进时钟后再用 → 另一工作区使用"。第 3 步令牌既已消费又已过期，该回 `token_consumed` 还是 `token_expired`？第 4 步又是已消费又已过期又跨工作区，该回 404 还是 410？
  - 契约没有给出检查先后。同一规则下，不同顺序的合规实现会有一半判失败。
  - 契约也没说令牌怎么随 ING 提交：放头、放字段，还是替代会话？TOK 本身要不要登录、绑定哪个工作区，R-01 的"全部概念未认证 401"对令牌上传是否适用，都没说。
- 修法：
  - 写明优先级：工作区归属（404）→ 过期（410 `token_expired`）→ 已消费（410 `token_consumed`）。
  - 用例按状态拆成三枚新令牌：
    - 令牌 1：用一次，再重放。
    - 令牌 2：创建后推进时钟，再用。
    - 令牌 3：在另一工作区用。
  - 令牌的携带方式（`Authorization: Bearer` 或头 `X-Ingest-Token`）和它是否替代会话，要在契约或 `params` 里声明。

**S-5 [一致] R-18 允许尾部被丢掉，与 MODULE "覆盖完整"不一致**
- 位置：contract R-18、INV；MODULE 不变式链"逐字、覆盖完整"。
- 原因：R-18 只要求首 chunk `start=0`、相邻相接。末块 `end` 不必等于文档长度，丢掉文档最后一段的实现也合规。检索不到末尾内容却不报错，正是"静默漏数据"。
- 修法：增加"末 chunk 的 `end` 必须等于文档文本总长度（按 `offsetUnit`）"。AC-29 在重建拼接时断言 `concat(chunks) == fixture_text`。

**S-6 [缺口] 同一用户属多个工作区时的隔离，以及 LIST/DOC/DEL 如何选工作区**
- 位置：contract R-02、R-05、R-06；AC-14 ~ AC-17。
- 原因：
  - 所有隔离用例都是"另一个账号"的视角。真实事故更常见的是：同一用户有 W1、W2，检索或列表把两边的 chunk 合并返回。
  - R-02 只规定 ING/Q/ANS 能显式指定工作区。LIST、DOC、CHK、DEL 的工作区从哪来没说。
  - R-05 和 R-02 对 ANS 完全没有用例（AC-16 只测 Q，AC-17 只测 ING 和 Q）。
- 修法：
  - 加用例：同一账号有 W1、W2，分别上传带不同唯一标记的文档。在 W1 上下文下，Q、ANS、LIST 都不出现 W2 内容；用 W1 上下文读取 W2 的 documentId 返回 404。
  - AC-16、AC-17 补上 ANS。
  - 契约说明 LIST/DEL 的工作区选择方式（沿用会话当前工作区或 `workspaceScope`）。

**S-7 [缺口] 删除与进行中摄入的竞态；删除后的去重与重放**
- 位置：contract R-33 ~ R-36、R-38；AC-23 ~ AC-26。
- 原因：
  - 在 `processing` 时 DEL，异步任务随后写入 chunk，删除后文档"复活"，同时违反 R-33、R-34。这是异步管道的典型缺陷，AC-23 只删 ready 文档。
  - 删除后同内容重传是否 409，也没说。软删行若还占着唯一索引，用户就删不干净也传不回去。
  - 同一幂等键在文档删除后重放，会返回已删文档的 id 还是新建，也没说。
- 修法：
  - 加规则：删除后摄入任务必须停止、终态不得晚于删除而写入 chunk；删除后同内容重传 201；删除后的幂等键重放不得返回已删文档（建议返回 404 `not_found` 或按新请求处理，选一种写死）。
  - 加用例：DEL 处于 `pending/processing` 的文档（用假模型延迟拉长处理），等待片刻后断言 Q 不命中、只读 DB 无正文。

**S-8 [可观察] R-34 只扫"文本列"，漏掉 bytea、jsonb、向量里的正文**
- 位置：contract R-34、第 7 节；AC-24；acceptance-plan 执行约定第 7 条（"扫描全部文本列"）。
- 原因：
  - 实现常把原始上传字节存进 `bytea`，或把 chunk 文本放进 `jsonb`。"文本列"扫描对它们是盲区，合规证据不成立。
  - 向量本身可被反演，D-04 写了"向量硬删"，契约没有任何规则或观察办法。
  - AC-24 也没说标记词若出现在 `title` 或 `filename` 里怎么算。
- 修法：
  - 扫描范围改为"所有 text/varchar/json/jsonb/bytea 列（bytea 先转文本）"。
  - 夹具的唯一标记只放在正文，不放进标题和文件名。
  - 契约补一句"向量与派生数据同时删除"，可观察性由 R-33 的"Q 不再命中"承担。

**S-9 [一致] 参数下界导致不可执行**
- 位置：contract 第 2 节；acceptance-plan 约定 2、AC-04、AC-10。
- 原因：
  - `ingest.maxBytes` 下界 1 KB，而"可接受文件 = 上限 − 1 KB"得 0 字节，与 R-16 的"空文件 400"冲突。
  - AC-10 要求文档 ≥ 3 × `chunk.maxChars` 字符（最大 12000），可能大于宿主声明的 `maxBytes`，造不出夹具。
  - AC-04 写成"≤ 声明上限 − 1 KB"，一个几百字节的文件也满足，R-13 的边界根本没测到。
  - `query.defaultTopK` 可以大于 `query.maxTopK`。
- 修法：
  - 下界改为 `ingest.maxBytes` ≥ 16 KB，且 `maxBytes ≥ 4 × chunk.maxChars`。
  - 约定 2 改为"可接受边界文件 = `maxBytes − 1 KB`"，AC-04 另加一次接近上限的上传。
  - 约束 `defaultTopK ≤ maxTopK`。

**S-10 [追溯] 追溯表有错配，几条规则没有真正的断言**
- 位置：contract 第 10 节；acceptance-plan 各 AC 的 expected。
- 原因（逐条核对）：
  - R-07 → AC-27：AC-27 是同工作区并发，不是跨工作区幂等。"幂等键作用域=工作区+概念"没有任何用例（跨工作区同键各自成功）。
  - R-36 → AC-14：AC-14 不涉及删除，只有 AC-26 有效。
  - R-21 → AC-04、AC-05：二者 expected 里都没有 `embeddingModel`、`embeddingDimension`，R-21 实际无断言。
  - R-39 → AC-12：契约声明"明文键 0 命中"，AC-12 的 expected 里没有只读 DB 扫描。
  - R-37 → AC-04、AC-13：只验正则，没有对夹具字节自行计算 SHA-256 比较。
- 修法：
  - 更正追溯表。
  - AC-04/AC-05 补回显断言（并与 DOC 的 `embeddingModel` 一致）。
  - AC-12 补 DB 扫描。
  - AC-04 补 `sha256(fixture) == contentDigest`。
  - 加跨工作区同幂等键用例。

**S-11 [一致] R-28 的上下文预算与 R-26 的"不得截断"互相拉扯**
- 位置：contract R-26、R-27、R-28；第 2 节界限（`chunk.maxChars` 可达 4000，`maxContextChars` 可低至 1000）。
- 原因：
  - 单个 chunk 可能超过整个上下文预算。命中是整块还是子区间，R-27 允许子区间，R-26 说"不得截断"，没有统一说法。
  - 超预算时是丢弃命中、截断命中，还是 0 命中（此时是 `no_context` 还是 `ok`），没规定。
  - 实现各取所需，AC-10 的断言只能碰运气。
- 修法：
  - 写明：命中 `text` 是所属 chunk 的完整文本（`start/end` 即 chunk 区间）；超预算时按排名丢弃后续命中，保证至少一条且单条不超预算；`maxContextChars ≥ chunk.maxChars` 作为参数约束。
  - R-27 随之改为"命中区间 == chunk 区间"。若坚持允许子区间，需要写出截取规则。

**S-12 [可执行] AC-18 与 AC-03 的时序和日志范围不可控**
- 位置：AC-18、AC-03、AC-29、AC-30；HOST 第 3 节假模型。
- 原因：
  - AC-18 写"刚上传立即查询"，在快速宿主上文档已 `ready`，用例空转通过。必须用假模型的延迟注入把文档卡在 `processing`，用例里没写。
  - AC-03、AC-29 读取假模型记录，而记录是全局的，不按工作区分。并行跑用例会互相污染；用例也没写"先 DELETE 清空记录再操作，或按本用例唯一标记过滤"。
  - 假模型的 PUT 请求体字段（延迟、故障、记录）HOST 里没给形状，AC-30 的 `ingest.failureField` 只是个"未声明时降级"的占位名。
- 修法：
  - 在 HOST 假模型里固定 JSON 形状：`{latencyMs, failNext, failMode:"embedding"|"generation", record:true}`。
  - 用例改为"先 DELETE 清空 → PUT 延迟 → 上传 → 断言 `processing` → 立即 Q"。
  - 记录读取用唯一标记过滤。
  - `failureField` 改名，不再放在 `ingest.` 前缀下。

**S-13 [缺口] 命中必须按相关度排序，没有这条规则**
- 位置：contract R-25；MODULE 第 3 节"检索"；decisions D-09。
- 原因：R-25 只要求"两次结果一致、同分按 chunkId 升序"。"分数降序"没写，返回顺序固定但乱序的实现也合规；顺序混乱的 topK 在 ANS 里会让前几条引用不是最相关的。
- 修法：加"命中按 `score` 降序，同分按 `chunkId` 升序（字节序比较）"。AC-09 断言相邻 `score` 非递增。

## 三、建议（16）

1. **[文字]** contract 第 5 节写"`code` 为 `<kebab_case>`"，但所有 code 都是 snake_case（`not_found`、`duplicate_content`）。统一写成 snake_case。
2. **[一致]** R-24 "`min(topK, maxTopK)`"与 R-16/AC-22 的"越界 400"是两种互斥策略（钳制 vs 拒绝）。R-24 里的 `min` 实际永远不会生效，删掉。
3. **[一致]** R-30 是 ⟺，MODULE 第 3 节写成 ⟹。意味着拒答时 `text` 必须为空串，不能返回"没有找到相关信息"。写明这点，并在 decisions D-06 里说明拒答话术由上层负责。
4. **[追溯]** ANS 的 `status` 取值 `insufficient_context`、`unsupported` 没有触发条件，也没有用例，不知道什么时候返回。给出定义或删掉 `unsupported`。
5. **[文字]** R-15 "至少支持…其余类型必须 415"措辞自相矛盾（至少支持 ⟹ 可以多支持）。改成"仅支持这三种，其余 415"。
6. **[安全]** 文件类型只看 MIME 与扩展名。增加一条"以内容探测为准：声称 `text/plain` 的二进制可执行内容应 415 或 `parse_failed`"。文件名只作元数据，响应里不得原样回显为 HTML；MODULE 第 4 节点名了路径穿越，契约和用例里没有对应项。
7. **[缺口]** 畸形 id（非 UUID）该 404 还是 400，没写。应与不存在同为 404，否则 400/404 的差异可被用来探测 id 格式。
8. **[缺口]** R-14 只测带 Content-Length 的超限。MODULE 第 4 节点名了"只信客户端 Content-Length"，应加一条：不带 Content-Length 的分块上传超限同样 413。
9. **[缺口]** 边界值：恰好 `maxBytes`、`topK == maxTopK`、`query` 恰好 `maxQueryChars`（包括中文和 emoji 的计数口径：码点还是 UTF-16 单元）都应被接受，目前只测了越界一侧。
10. **[缺口]** PDF 解析面：超大页数、压缩炸弹、加密 PDF，以及 PDF 成功路径（有文本层）都没有用例。AC-19 只测"无文本层失败"。`text/plain` 成功和"纯空白内容 → `empty_content`"也没有用例。
11. **[缺口]** 嵌入失败路径：R-11 的 `embedding_failed` 没有用例；R-42 只覆盖嵌入故障，没覆盖生成模型故障（ANS 的 503）。
12. **[安全]** ANS 把检索到的文档正文放进生成提示词，本模块自己要对注入负第一责任。MODULE 第 5 节把它全推给 `prompt-injection-and-guardrails`。建议在 MUST 之外加一条："文档文本进入提示词时用不可伪造的定界符包裹，并声明为不可信数据"，并要求前端对 `text` 做转义，避免存储型 XSS。
13. **[可观察]** 第 5 节末尾"任何账号状态（已验证、未验证、被禁用）下返回同一 code"是规范性语句，既不在 MUST 表里，也没有用例。要么编号入表补用例，要么删除。
14. **[越界]** 第 9 节的 `X-Forwarded-For` 条目讲的是客户端 IP 口径，属于 `rate-limiting`/`web-security`，本模块并不限流。删除或改为引用。方向（取最右侧非受信跳）本身是对的。
15. **[越界]** R-44 与 MODULE 第 5 节：outbox 邮件属 `email-transactional`，MODULE 却把通知模板挂在 `notifications` 下。统一口径，第 5 节补上 `email-transactional`。

## 五、各项检查的小结

1. 安全/领域正确性：令牌只存哈希、幂等键只存哈希、不可见一律 404、去重按工作区，这些都符合业界做法。XFF 取最右侧非受信跳也是对的。没有发现"重算存量哈希令牌"这类做不到的建议。问题在于 R-34 观察不全（S-8）、注入防护全部外推（建议 12）、文件内容探测缺失（建议 6）。
2. 可观察性：第 9 节把不可测项放得比较干净。个别 MUST 受假模型定义缺失影响，实际不可判定（S-2、S-12）。
3. 一致性：除 B-1，还有 S-3、S-5、S-9、S-11 与建议 1 ~ 3。
4. 追溯：见第四节。
5. 可执行性：令牌携带方式、假模型形状、假嵌入语义、`workspaceScope` 之外的工作区选择方式都没给，影响 AC-18、AC-28、AC-30 等。
6. 越界与引用：见建议 14、15。模块名均有效，无品牌名。
7. 文字：见建议 1、5；其余无错字、无乱码。
8. 缺口：见 S-6、S-7、建议 6 ~ 12。
