# workspaces-and-permissions：需要人来拍板的决定

每条给出**推荐默认**与**选别会发生什么**。D1~D4 会改契约形状，开工前必须定。

| # | 决策点 | 推荐默认 | 选别的后果 |
| --- | --- | --- | --- |
| D1 | 租户标识怎么传（路径 vs header） | 路径 `{workspaceId}` 为主，宿主可改用 header `X-Workspace-Id`；两处都送且不一致 → 400 | 只用 header：租户 id 常被存本地并被篡改，错误难查；只用路径：租户 id 进 URL 与日志，枚举要靠一律 404 抹平 |
| D2 | 角色固定还是可自定义 | 内置 owner/admin/member/viewer + 工作区级自定义角色，权限取自固定 13 项目录 | 完全自定义：目录与升级防护重做，容易造出含 `workspace.delete` 的角色发给 admin；完全固定：客户要"只读财务"这类角色只能 fork |
| D3 | 邀请已有账号的人 | 一律走邀请（哪怕账号已存在），三种账号状态响应完全相同 | 直接拉人进租户：响应体泄露"这个邮箱有账号"，变成邮箱枚举；还会让被禁用的人提前获得租户可见性 |
| D4 | 身份主键用 email 还是 user_id | `user_id` 唯一；email 只用于展示与邀请绑定，比较前 trim + 转小写 | 用 email 当唯一键：换邮箱、大小写、别名都会多出成员记录，权限判定漂移且难清理 |
| D5 | 移除成员/删租户：软删还是物理删，PII 留不留 | 软删除（`deleted_at` 非空、行保留）+ 清个人数据 + 窗口内可 restore | 物理删：审计断链、用量与账单对不上账；保留 PII："删除我的数据"请求无法落地（合规风险） |
| D6 | owner 能否有多个、能否自己降级 | 恰好一个 owner；他人降级/移除最后一个 owner → 409；owner 自我降级/移除 → 403（须先转移）；转移时原 owner 降 admin | 允许多 owner：护栏消失，交接靠人盯；允许自我降级：一次误操作就让租户没人能管 |
| D7 | 删租户时其他模块的数据怎么办 | 只标记租户已删，各模块按 workspace 状态处置（计费停、检索停、数据留） | 级联物理删：用量与账单记录被抹，账对不上；也容易删掉别的模块正在写的数据 |
| D8 | 权限判定要不要缓存 | 实时查（每次请求读成员关系）；必须缓存则 TTL 极短且变更时主动失效 | 缓存 60 秒：被降权或被移除的人这段时间照样能读写删，是可被直接利用的窗口 |
| D9 | 状态型上限默认值 | 每用户 20 个租户、每租户 100 条 pending 邀请、邀请有效期 7 天、保留窗口 30 天（实际值由宿主在 `params` 声明） | 太低：批量运营被自己打断；太高：一个账号就能刷爆邮件配额、把邀请表撑大 |
| D10 | 成员 email 谁能看 | 单独的 `member.read_email` 权限，viewer 看不到 | 全员可见：成员列表就是现成的邮箱名单，可拿去撞库或群发骚扰 |
| D11 | 邀请令牌怎么存、怎么演进 | ≥32 字节安全随机 + 只存 SHA-256（或更强）摘要；换算法时新旧摘要并行，直到旧令牌全部过期 | 明文入库：一次备份泄露即沦陷；靠"重算摘要"给旧令牌续命：摘要不可逆，等于绕过 TTL，链接泄漏即长期有效 |
| D12 | 本期接不接企业目录（SSO/SCIM） | 不做，身份只有一种来源；"外部身份映射到角色"留成 L3 | 现在做：多一套映射表与权限归属规则，复杂度远超模块本身；不做：企业客户上线前必须补 |
| D13 | 事件与邮件的边界 | 只发事件（模板名 `workspaces-and-permissions.<名>`，链接放 `data.link`），发送交给 email-transactional | 本模块直接发信：退信、重试、模板渲染都自己做一遍，还与 notifications 重复 |

## 拍板顺序

开工前定 D1~D4（接口形状、角色模型、邀请语义、身份主键），它们决定 schema 与契约；联调前定 D5~D9（数据生命周期与安全窗口）；上线前定 D10~D13。
